### T-050 — Verification core: NIN/BVN, liveness, levels

- **Touches:** `src/modules/trust/**`, migration `trust_*`
- **Depends on:** T-040, T-045, T-031
- **Acceptance criteria:**
  - Schema per M6 §6 (requests, NIN/BVN outcomes, liveness, provider call log, append-only level change log).
  - Raw NIN/BVN never stored or logged: masked display value plus keyed HMAC plus provider reference only. A test scans logs and tables after a verification run for the raw number.
  - `KycProviderAdapter` with a deterministic fake (dev/test) and a Dojah adapter disabled until credentials exist (feature flag).
  - Verification runs asynchronously in jobs; results push to the client over the socket.
  - `verification.level_attained` and `.level_revoked` drive `users.verification_level` in identity; level 2 requires NIN or BVN plus liveness.
  - Endpoints per M6 §11 user surface; status endpoint for J2 and VF1.
- **Status:** Done (2026-10-06). Plan: `docs/superpowers/plans/2026-10-06-t-050-verification.md`. Migrations `0029_trust_schema` (generated) and `0030_trust_level_changes_append_only` (custom; the level log is the record of WHY a user may transact, and a record that can be rewritten is not one). **The module's shape is forced by D1: the raw number must never be stored, logged, or sit in Redis in plaintext — and the obvious way to run a provider call in a job breaks the last of those silently.** BullMQ job data is a Redis value that outlives the job, so `POST /verification/{nin,bvn}` seals the WHOLE claim — number, name, date of birth — with `ENCRYPTION_KEY` into `IdentityCheckJob.sealed`, and `trust.identity-check` is the only code in the program that opens it; the job is added with `removeOnComplete: true` so the ciphertext does not outlive the work either. Sealing only the number while the name and DOB rode along in the clear is the half-measure that reads as compliance, so the claim is sealed whole. What persists is §6.3's three things and nothing else: a `*******8904` mask, an HMAC-SHA256 under `IDENTITY_HMAC_PEPPER` domain-separated `trust:nin`/`trust:bvn` (so a leaked NIN row cannot confirm a guess against the BVN table, which matters because the two are frequently one person's two numbers), and the provider's reference. **Decision Q7's fake is the whole provider story and it is deliberately not a pass-through.** `fake-script.ts` is pure and scripted by the number's trailing digit — `…0` stalls, `…1` fails, `…2` goes to review, `…3` throws, everything else passes — so the four non-happy branches are the DEFAULT rather than something a test must remember to configure, and scores spread by band (85–99.99 passing, 55–74.99 review) rather than sitting at 100. It signs its work `provider = 'FAKE'`, a real member of the `kyc_provider` enum, so "which identity levels were attested by nobody" is one query the day credentials arrive; and `loadConfig` REFUSES TO BOOT a production process on `TRUST_KYC_PROVIDER=FAKE`, because a fake granting real identity levels in production is not a mistake anyone should be able to make quietly. The Dojah adapter exists, is selectable, fails at boot naming its three missing variables, and **rejects every call** — its header carries the three endpoint names and the one design question a real integration must settle first (Dojah's liveness endpoint takes IMAGES, and this module holds only an M20 file reference, so somebody must decide between streaming bytes through a backend M20 deliberately keeps out of the path and handing Dojah a signed URL). There is no request construction and no response mapping, and the absence is the point: a mapper written against a response nobody has received reads like working code and is rewritten the day it is first run. **The T-028 split is `fake-script.ts`/`dojah.requests` (pure) against `*.client.ts` (the seam), constructed once in `jobs/providers.ts` and reachable only from `jobs/`** — the fake is named `*.client.ts` despite reaching nothing, because it occupies that seam and anything else would leave the easiest adapter to misuse outside the rule. Level 2 needs a verified NIN _or_ BVN **plus** liveness (`domain/levels.ts`), the grant writes `verification_level_changes` and moves `users.verification_level` through identity's new `applyVerificationLevel` **in one transaction** — a deliberate deviation from D6's "M1 subscribes", because the relay would leave `GET /verification/status` reporting the old level on the one screen whose purpose is to say "you are verified now"; identity still computes nothing. Services and jobs take a `TrustStore` port rather than a `Db` (files' `jobs/store.ts` pattern, widened) so the decisions are unit-testable, with every SQL statement in `bind-store.ts`. **From review, the defects that mattered, and they were all one shape — state reasoned about once at the top of a function and then written without re-checking:** a user re-submitting their OWN verified NIN hit the §6.3 index against their own row and was parked in `MANUAL_REVIEW` — which holds their one in-flight slot, which the expiry sweep deliberately skips, and which nothing can decide until T-052 — with a duplicate-identity fraud signal published about them to Risk and a payload that would have violated T-052's own `first_user_id <> conflicting_user_id` check; there is now a submit-time guard (409 before a provider call is spent) and a self-duplicate branch in the job. `grantLevel` called identity's writer BEFORE checking "already at or above", so a redelivered level-2 grant reaching a `BUSINESS_VERIFIED` user committed the downgrade and appended no row to explain it — the exact disagreement between the column and the append-only log the log exists to prevent; the decision is now `decideLevelChange` in `domain/levels.ts`, asked under `FOR UPDATE` before anything is written. Every request `UPDATE` was unguarded, so a job finishing after the sweep expired its request overwrote `EXPIRED` with `APPROVED` and granted level 2, and a redelivered job could drag a `MANUAL_REVIEW` request back to `PROVIDER_PENDING` where the sweep would then silently close the human case; all three writes now carry a status predicate and report whether they applied, and the job grants nothing and says nothing when they did not. And the fake's `provider_reference` was a truncated unkeyed SHA-256 of the raw NIN, persisted in the column D1 lists as safe — a rainbow table over a 10^11 space, invisible to both D1 scans because they look for the literal digits; it is random per call now, which is also what a real provider returns. Also from review: the 409 for an in-flight check now distinguishes "with our team" from "still running", because telling a user stuck in review that they will get a result shortly is advice they act on by retrying; and `.env.example` gained the five new variables plus a new `test/config/env-example-parity.test.ts` that fails on any undocumented variable — it immediately caught three `SOCKET_*` variables undocumented since T-027. **For T-051 and T-052:** the barrel exports the schema, the five events (prefixed `trust.verification.*`, because the platform bus enforces `<module>.<aggregate>.<action>` and refuses the spec §9 table's two-segment names at import), `VERIFICATION_SOCKET_EVENT`, and the module builder, which takes the socket gateway — `createModules` now builds the socket module into a `const` before the array so trust can be handed it, and keeps it last so start order is unchanged.
- **Deferred:** **`duplicate_identity_flags` and `kyc_review_queue` are T-052's tables and are not built**, so a `MANUAL_REVIEW` request — one NIN in ten under the fake — has no way to be decided: it holds the user's in-flight slot, the sweep skips it on purpose, and the only exit today is hand-written SQL. The 409 says so rather than promising a result. `verification.override` and its dual approval are T-052's too. **`revokeLevel` and `trust.verification.level_revoked` are implemented, exported and called by nothing** — D6's revocation half needs either a provider webhook or T-052's analyst override, and an endpoint needs T-037's RBAC rows. **No Dojah call has ever been made from this repository**: the adapter refuses, and the first live call is still the test that matters. `verification.provider_degraded` is not published — `kyc_provider_calls` records the shape (`error_kind`) an error rate needs, but nothing computes one yet. `verification_documents`, `business_verifications`, `bank_account_name_matches`, `address_checks`, `social_proof_claims`, `enhanced_due_diligence_reviews` and levels 3–4 are T-051's. §12's recommendation stands and is NOT acted on: the identifier HMAC rides on identity's `IDENTITY_HMAC_PEPPER` rather than its own key, deliberately, so there is one secret to move to KMS rather than two — but §12 names that key as the one here whose leak has an irreversible cross-account consequence, and "M6 ships" is the trigger it was written for. Known minors left in: `verification_requests.metadata` is `text` where §6.2 says `jsonb` (unused today); `attemptCount` counts lifetime submissions, not §9's rejections-in-30-days, so T-100 must do its own windowing despite the field's comment; expiry publishes `trust.verification.rejected`, so a provider outage reads to the user as a rejection and feeds §9's auto-ticket rule; `PROVIDER_PASSED`/`PROVIDER_FAILED` are declared in the enum and never written (the lifecycle jumps straight to `APPROVED`/`REJECTED`); the liveness "nothing to match" path writes a row with `provider_reference = 'not-called'`, a sentinel in a NOT NULL column; `expireStale` has no `LIMIT` and publishes one outbox row per request inside one transaction; and the fake simulates no latency, so nothing here has ever waited on a slow provider. No `shared-types` wire schemas or `api-client` hooks: the web ticket that renders verification owns the client contract.
