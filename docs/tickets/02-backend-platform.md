### T-024 — Domain events: outbox and typed bus

- **Touches:** `src/platform/events/**`, `platform` schema (`outbox`, `processed_events`)
- **Depends on:** T-021, T-023
- **Acceptance criteria:**
  - `publish(tx, event)` writes to `platform.outbox` inside the caller's transaction; nothing is published if the transaction rolls back (test).
  - A relay job moves outbox rows to subscriber queues at least once, in order per aggregate.
  - `subscribe(eventType, handler)` records `eventId` in `processed_events` within the handler's transaction; a replayed event is a no-op (test).
  - Envelope per M1 §11; event types and payloads are zod-typed in `shared-types`.
  - The in-process emitter exists for lossy, recomputable effects only, and its docs say so.
- **Status:** Done (2026-10-05). Plan: `docs/superpowers/plans/2026-10-05-t-024-events-outbox.md`. `publish(tx, …)` writes the envelope through the caller's transaction; the worker-only relay claims rows with `FOR UPDATE SKIP LOCKED`, fans out one BullMQ queue per subscriber and marks the batch published in the claiming transaction; each subscriber's `processed_events` marker is written in the handler's own transaction, so a failed handler is retried whole. Ordering into the queues is kept by a fleet-wide advisory lock plus a commit watermark (`created_xid < pg_snapshot_xmin(…)`), since `seq` is allocated at INSERT and not at COMMIT. Beyond the plan: an `outboxMetrics` backlog gauge, exponential backoff on failing ticks, a deadline on the enqueue phase, quarantine of unprocessable rows, batched pruning, and `processed_events` kept 90 days so a marker outlives the 30-day failed-job window that could redeliver it. `ModuleContext` gained `events`, `emitter` and `db`. The migration also creates two prune-support indexes beyond the plan's one.
- **Deferred:** ordered _execution_ is not guaranteed — a handler that fails waits out its backoff while BullMQ runs the next job for that subscriber, so handlers must be commutative or carry their own guard (a per-aggregate delay gate needs the job token plumbed through the queue factory); the commit watermark is cluster-wide, so a long transaction anywhere on the instance stalls delivery until `WATERMARK_TIMEOUT_MS` (5 s), after which rows publish possibly out of order, counted in `outboxMetrics.watermarkTimeouts`; a row that repeatedly fails to enqueue is retried forever rather than quarantined; no index on `(aggregate_type, aggregate_id)` until a replay tool needs it; no outbox replay/backfill tooling; subscriber dispatch keys on event type only, so a version mismatch dead-letters rather than being routed to a handler for that version.

### T-025 — HTTP cross-cutting: pagination, idempotency, rate limits, validation

- **Touches:** `src/platform/http/{paginate,idempotency,rateLimit,validate,route}.ts`, `platform.idempotency_keys`
- **Depends on:** T-021, T-023
- **Acceptance criteria:**
  - `defineRoute({ method, path, scope, permission?, retryable?, paginated?, rateLimit?, schema })` is the only way to register a route. A registry test fails if any `GET` returning a collection is not `paginated`, or any mutating route lacks an explicit `retryable` decision.
  - Idempotency: unique on (scope, key, actor); same key and same body returns the stored response with `Idempotent-Replayed: true`; same key and different body returns 422; concurrent duplicates wait on a short Redis lock. Tests cover all three.
  - Rate limiting via `rate-limiter-flexible` on Redis, keyed per IP, per identifier and per user; responses carry `Retry-After`.
  - Request and response validation from zod schemas.
- **Status:** Done (2026-10-05). Plan: `docs/superpowers/plans/2026-10-05-t-025-http-cross-cutting.md`. `defineRoute` is the only way a route exists: `KomtruModule.routes` is a `RouteDefinition[]`, and `mountRoutes` checks the registry at boot, so a collection without `paginated` or a mutating route without an explicit `retryable` fails the process rather than shipping. The chain is rate limit (IP and user) → parse → rate limit (identifier) → idempotency → handler → response validation, so a malformed body cannot buy unmetered requests on a metered route; a response that breaks its own schema is a 500 and a Sentry report, not a client error. Idempotency claims `(scope, key, actor)` before the handler and completes it after, with takeover of a claim abandoned by a dead process and release of a failed one. Rate limits are Redis-backed per IP, user and identifier, fail **closed** with a 503 when Redis cannot answer (the routes that declare a limit are the ones worth brute-forcing). Cursors are base64url and a tampered one is a 422. The statelessness test now asserts two API instances share one rate-limit budget and one idempotency store, closing T-023's deferred item. Every write by an idempotency owner is fenced on an `owner_id`, and the owner renews a Redis lease while it works, so a slow-but-alive handler is never taken over and a superseded attempt can neither overwrite the new owner's response nor delete its claim. New dependency: `rate-limiter-flexible` 11.2.1.
- **Deferred:** cursors are opaque but unsigned (a client can still mint a syntactically valid one; the values are type-checked, and signing with the T-026 HMAC helper is the fix if a cursor ever carries a scoping value); the limiter key has no environment segment, so staging and production must not share one Redis; the platform guarantee is "at most one _recorded_ completion", which cannot make a non-transactional handler exactly-once — money and custody handlers must do their work in one transaction (stated in the file header); `paginated: 'page'` has no `pagedPage()` helper to match `cursorPage()`; `scope` and `permission` are recorded but unenforced until T-030/T-031, and every caller resolves to `anon`, so per-user limits and per-actor idempotency are inert until then; a body with no schema on a retryable route is hashed as the client sent it, so key order is the client's.

### T-027 — Socket gateway

- **Touches:** `src/modules/socket/**`
- **Depends on:** T-023, T-031
- **Acceptance criteria:**
  - Socket.IO attached to the API's HTTP server with the Redis adapter (`komtru:sock:` prefix); CORS from config.
  - Handshake authenticates with the same access token as HTTP; every user joins a personal room.
  - `emitToUser`, `emitToRoom`, and a `registerRoomAuthorizer(prefix, fn)` hook for feature rooms (trade, dispute, hub).
  - Sessions are re-validated when the user's session epoch bumps; revoked sockets disconnect.
  - Test: an event emitted on instance A reaches a socket on instance B.
- **Status:** Done (2026-10-06). Plan: `docs/superpowers/plans/2026-10-06-t-027-socket.md`. One Socket.IO server for the whole backend, built **unattached** so `createModules` stays a pure function of the process's connections — `server.ts` contributes two lines (`socketModuleOf(modules)?.attach(server)` after `listen`, and `socketDrain(modules)` at the head of the shutdown closers) rather than reordering its boot around one module. The handshake is **not a second identity system**: the credential goes to identity's own `resolvePrincipal`, injected as an `authenticate(token) => Promise<Actor>` port, so a socket is admitted on exactly the conditions an HTTP request would be and the refusal carries the same `AuthFailure` code the 401 would (`TOKEN_MISSING`, `SESSION_REVOKED`, `EPOCH_STALE`…), which is what lets a client tell "refresh and retry" from "you are signed out". Every user joins `user:<id>` whatever scope they signed in under — that is what makes `emitToUser` a one-liner — plus `<scope>:<id>`, so a staff-only push never reaches their consumer app. **The heart of the ticket is the fourth criterion, and it is the one HTTP gets for free:** `resolvePrincipal` re-reads scope, status, epoch, roles and permissions from Postgres on every request, so a revocation stops the caller on their _next request_ — and a socket has none. It can sit open for hours having been authenticated once, which is the exact shape of bug M1 D5 exists to prevent. So the gateway manufactures the missing request: every socket keeps the credential it presented and a timer re-runs the _same_ `resolvePrincipal` over every distinct credential (deduplicated by token — six tabs share one access token and must cost one query, not six). The verdicts are literally the HTTP verdicts, with no second authorisation path to drift, and the mechanism depends on nothing but the process being alive. **A push was rejected as the guarantee** — publish the bumped user id, every instance drops their sockets — because a push is lossy _and silent when it is lost_: a Redis blip, an instance mid-restart, or one revocation path whose author forgot the call, and the socket lives forever with nothing to notice. `gateway.disconnectUser` is that push, offered as the fast path (T-039's suspend should call it straight after the kill-switch transaction; the Redis adapter carries `disconnectSockets` to every instance), never as the guarantee. **The staleness bound, stated honestly:** a socket holding a _live_ credential is re-decided every `SOCKET_REVALIDATE_INTERVAL_SECONDS` (30 by default). A socket whose token has lapsed is worse and the number has to be said out loud — `resolvePrincipal` rejects on `exp` before it queries anything, so while a token is expired the gateway can learn _nothing_ about that session. Review caught the first version measuring the grace from the last successful check, which could be an instant before `exp` and therefore stacked the grace on top of the whole ten-minute token lifetime: eleven minutes of blindness, free to any client that simply never answered. The clock now starts when a credential first fails, so the bound is one interval plus one grace (~90s) and a quiet client cannot extend it. **Everything else review found was a client-reachable crash or a leak, and all of it is fixed with a test that failed first:** a non-function in a listener's ack slot, or an `auth:token` while Postgres was away, became an uncaught exception that `platform/run.ts` turns into `stop(1)` — one crafted packet from any token-holder was a full-process DoS; a credential check that never settled held the overlap latch forever and _silently_ stopped re-validation for the life of the process (nothing in this repo sets a `statement_timeout`), so every check now has a deadline; `auth:token` accepted a token for the same user under a _different scope_ while scope rooms are joined only once, stranding a consumer principal in a staff room — scope changes are refused and cost a reconnect; the connection was recorded inside `io.use`, but socket.io abandons a socket whose transport dies mid-handshake _without_ firing `disconnect`, so every aborted connection leaked a table entry, and recording moved to the `connection` event; and a live websocket keeps `server.close()` from ever completing, so every shutdown burned the full 5s drain and then destroyed the sockets abruptly — `socketDrain` closes them first. **The guide's §8 registry has a security hole this does not:** a room name is `<prefix>:<id>` and personal rooms are room names too, so an unreserved `user` prefix plus a chosen id is a way into somebody else's inbox. `RESERVED_ROOM_PREFIXES` is derived from `SESSION_SCOPES` (so a fourth scope cannot open the hole), `assertRegisterablePrefix` refuses a reserved prefix at boot, and `isJoinableRoom` runs _before_ any authorizer is consulted — a buggy feature module never even sees a `user:` request. Ids are `[A-Za-z0-9_-]{1,64}`, which excludes the `:` separator, and `emitToRoom` re-checks on the emit side so a backend caller cannot broadcast into an invented room either. Authorizers default-deny three ways (unregistered, threw, rejected) and a feature module's bug can never crash the connection. New config: `SOCKET_ENABLED`, `SOCKET_PATH`, `SOCKET_CORS_ORIGINS` (falling back to `ALLOWED_ORIGINS`, since the apps that call the API are the apps that open sockets; empty means no browser connects, and that is logged at boot naming both variables), `SOCKET_REVALIDATE_INTERVAL_SECONDS`, `SOCKET_CREDENTIAL_GRACE_SECONDS`. The guide's `SOCKET_REDIS_URL` and `SOCKET_AUTH_TOKEN_SECRET` are deliberately **not** added: the adapter uses `REDIS_URL` under its own `komtru:sock:` key (its channels are `komtru:sock:#/#`, which cannot collide with BullMQ's `komtru:bull` keyspace), and there is no second secret because EdDSA needs none — `SOCKET_AUTH_TOKEN_SECRET` is `JWT_SECRET`'s mistake repeated. Dependencies: `socket.io` 4.8.4, `@socket.io/redis-adapter` 8.3.0, `socket.io-client` 4.8.4 (dev, tests only). No migration. **For the modules that will consume this:** `gateway.registerRoomAuthorizer(prefix, fn)` is called once at `start()` by whoever owns the prefix, a second claim is a boot failure, and the authorizer receives the whole `Principal` — re-resolved at handshake and on every sweep — so it reads roles and permissions from there and never from a token.
- **Deferred:** `gateway.disconnectUser` has no caller yet; T-039's suspend is where it belongs, and until then the sweep is the only path. `verifiedAt` and `credentialExpiredAt` are wall-clock `Date.now()`, so an NTP step moves the grace window — a monotonic source would be more honest for a deadline. No per-user or per-IP connection cap and no reconnect-rate signal: the guide's §12 puts connection-rate abuse in M13, and nothing here feeds it. The sweep costs one indexed query per distinct credential per interval, which is fine at Nigerian consumer scale and is the number to revisit before the interval can be raised. The socket module contributes no health check, deliberately: `/health/ready` asserts an exact `{postgres, redis}` shape in `test/integration/processes.int.test.ts`, and a gateway whose adapter connections are down is not a reason to pull an instance out of the load balancer for HTTP. Sticky sessions are not required for correctness (the adapter handles cross-instance fan-out) but the ALB idle timeout must be raised above its 60s default, which is a deployment concern no ticket owns yet. The client protocol is `room:join` / `room:leave` / `auth:token` with `auth:refresh` / `auth:revoked` coming back; T-013's frontend socket provider has to send `auth:token` whenever it refreshes, or every socket takes a grace-window disconnect and reconnects. JWKS-based verification by an edge proxy is not used: the gateway verifies in-process with identity's own signer.

### T-029 — Isolate the integration suite's shared Redis and queues

- **Depends on:** T-023, T-025

  - The full infra suite (`KOMTRU_INFRA_TESTS=1 pnpm --filter @komtru/backend-api exec vitest run`) passes 20 consecutive runs with no failure. Today it fails roughly one run in three.
  - The three known flakes are covered by that run and named in the ticket's status when it closes: `notifications.int.test.ts` "dead-letters against a provider that always fails" (dead-letters after one provider attempt where the test configured two, and the row stops at `FAILED` instead of `DEAD_LETTERED`), `notifications.int.test.ts` "makes no provider call at all when SMS is in dry run", and `idempotency.int.test.ts` "runs again once a stored record is past its lifetime".
