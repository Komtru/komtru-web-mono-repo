- **Status:** Done (2026-10-06). Plan: `docs/superpowers/plans/2026-10-06-t-040-files.md`. Migrations `0027_files_schema` (generated) and `0028_files_access_log_append_only` (custom; `file_access_log` can only grow, because it is the record of who looked at a KYC document and a record that can be rewritten is not one). **The module's shape is forced by one fact: the bytes never touch this backend.** The browser uploads straight to Cloudinary with a signature the API computes locally, so "the client says it uploaded" and "Cloudinary confirms it landed" are two different facts and only the second may serve bytes — which is why `file_upload_state` (`PENDING` → `RECONCILING` → `READY` | `REJECTED`) exists beside the spec's `file_status`, and why `POST /files/:id/finalize` answers **202** and hands the reconciliation to `files.finalize-upload` rather than asking a provider on the request path (design §4.4). The job writes the size and the content type **Cloudinary actually received**, not what the client declared when it asked for the ticket, and rejects — tombstoning, with the reason — anything oversize or of a type the category forbids; the size ceiling lives there and only there, because Cloudinary's upload API has no size parameter outside an upload preset, so the bytes are already stored and already metered by the time we can see them. **The T-028 split is `cloudinary.signing.ts` (pure: a SHA-1 and some string building, which a request handler calls) against `cloudinary.client.ts` (the only file in the module that reaches the network, constructed once in `jobs/providers.ts` and reachable only from `jobs/`).** The one place the boundary was worked around rather than obeyed is `domain/queues.ts`, which holds the queue names and job payloads **outside** `jobs/` so the finalize and tombstone routes can enqueue without importing a directory the scanner taints — the review confirmed this composes rather than leaks, because a future import _into_ `queues.ts` would make that file itself the violation. `CUSTODY_EVIDENCE` is this ticket's new category (design §7.2's `park_custody_events.photo_file_id`), images only, `PRIVATE_CASE` only, audited like KYC and dispute evidence, and **deliberately absent from the `POST /files/upload-url` body**: design §7.3 says the hub is resolved server-side from the agent's assignments and never trusted from a client, and M20 has no Park knowledge to resolve it with, so T-092 calls `createUploadTicket` through the barrel with the hub it established. Camera-capture metadata is `capture_received_at` (written once, from the **database** clock, when the server is first told the bytes landed) plus `capture_hub_id`; there is no column for a client-supplied capture time and the request body is a `z.strictObject`, so a park agent whose phone is a day fast gets a 422 rather than a custody photo stamped in the future. Retrieval runs one pure decision (`domain/access.ts`) and writes the audit row before it refuses: **"no such file" and "not yours" are byte-identical 404s**, because distinguishing them turns the endpoint into an existence oracle that leaks whether a dispute exists at all, and `TOMBSTONED` → 410 is the single exception, since it says nothing an authorised caller did not know. `PUBLIC` files get a signed non-expiring delivery URL (what an `<img src>` needs); every restricted class gets the Admin download URL whose `expires_at` is _inside_ the signature. Rotation is quota-aware round-robin with `SELECT … FOR UPDATE` on `storage_pool_rotation` — without it two concurrent uploads read the same predecessor and the pool degenerates under exactly the concurrency rotation exists for — and it fails closed when every account in a pool is unusable, never falling back. `files.sync-usage` is the only writer of `storage_accounts.status` and publishes its ops events **only on a transition**; a failed poll leaves status alone, because a network blip is not a quota fact. New config: fifteen `CLOUDINARY_*` variables across five prefixes plus `FILES_MAX_UPLOAD_BYTES`, `FILES_UPLOAD_TICKET_TTL_MINUTES`, `FILES_SIGNED_URL_TTL_SECONDS`, `FILES_QUOTA_NEAR_PCT`, `FILES_QUOTA_DISABLED_PCT`; two new problem codes, `FILE_TOMBSTONED` and `FILE_STORAGE_UNAVAILABLE`, because clients branch on `code` and a 410 carrying `NOT_FOUND` would collapse the one refusal D4 keeps distinguishable into the 404 that hides "not yours". No `file.*` RBAC permission: the admin and internal routes reuse `user.close`, `user.update`, `audit.view` and `role.grant`, since a new code needs a row in identity's twelve-role matrix. **From review, the two real defects, and they compounded:** only the admin endpoint enqueued the destroy job, so the three other tombstone paths — M15's data-subject sweep through `tombstoneByUploader`, the abandoned-ticket sweep, and the rejection branch of reconciliation — flipped the row and **left the bytes on Cloudinary**, which for an NDPR deletion of a KYC document is a compliance failure and for the sweeps is the free-tier ceiling the whole five-account pool exists to avoid; `module.ts` now subscribes to its own `files.file.tombstoned`, which every path publishes in the same transaction as the row change, so the bytes follow the row by construction rather than because each caller remembered. And the finalize job id is the file id while BullMQ keeps a failed job for 30 days, so once it dead-lettered — after a default budget of ~30 **seconds**, against a job whose own comment justifies throwing on the grounds that a large photo over a slow mobile link needs much longer — every later finalize answered 202 and did nothing, until the sweep tombstoned a file that had actually landed; the spent job is now cleared before the enqueue and the budget is 8 attempts from 15s. Both survived twelve tasks of TDD because each half was tested and **the seam was not**; there is now coverage that a tombstone leads to a destroy, on all four paths. Also from review: `GET /admin/files/:id` was added because without it `INTERNAL_ONLY` and role grants were unreachable over HTTP and `file_access_log.accessed_by_admin_id` could never be written by a real request — three branches of `decideAccess` were dead code; `grantAccess` became `ON CONFLICT DO NOTHING` plus a re-select, since a read-then-insert loses exactly the at-least-once race it was written for; `capture_received_at` moved from `new Date()` to SQL `now()` (the security property held either way, the audit property did not); the register endpoint now names its three missing variables to the SUPER_ADMIN executing the D6 runbook instead of telling them "try again shortly"; `POST /files/upload-url` gained a 30/minute limit, being the only consumer endpoint that spends storage quota; and the quota thresholds are compared **after** defaulting, so lowering only the disabled one no longer leaves `NEAR_QUOTA` silently unreachable. **For T-041/T-050/T-055/T-061/T-080/T-092/T-100/T-104/T-108:** the barrel exports `createUploadTicket` (which takes `captureHubId` and a `scope`), `retrieveFile`/`subjectFrom`, `grantAccess`/`revokeGrant`/`listGrants`, `requestTombstone`/`tombstoneByUploader`, `findServableFile`, the five events and the category/visibility tables as data. It exports nothing that returns a URL without an access decision, nothing that resolves a credential, and no storage-account write — there is exactly one path from a file id to bytes, and the second path is the one that is wrong after somebody changes the policy.
- **Deferred:** **M20 §8's consumed events are not wired** — `compliance.retention_policy_applied` and `compliance.dsr_fulfilled` (T-104) and `dispute.opened` (T-080) do not exist yet, and subscribing to an event nobody publishes is a handler that can only be wrong by the time it fires; `tombstoneByUploader` and `grantAccess` are exported for those tickets to build on, and both now destroy/dedupe correctly. **D3 is not met for `PUBLIC` files:** the spec says even a public file gets a short-lived URL, and this issues a tamper-proof but non-expiring one, because Cloudinary's free tier has no token auth and the only genuinely expiring mechanism serves as an attachment that would break an `<img src>` gallery — the URL is per-file, cannot be walked to another asset, and dies when the asset is destroyed, but it is a deviation and it is here rather than only in a code comment. **No call in this repository has ever been made against a live Cloudinary account**; shapes follow the published Admin API docs and every test runs against a local stub, so the first live call is still the test that matters — confirm `credits.used_percent` on `GET /usage` first (the field has moved between API versions; `fetchUsage` throws rather than reading its absence as zero), then whether the Admin `download` endpoint requires the `format` parameter that `buildExpiringDownloadUrl` currently omits, since every restricted retrieval rides on that URL. The consumer routes are `CONSUMER`-scoped and the staff read is a separate path, because `RouteScope` is one scope per route and `assertRouteInvariants` rejects a duplicate path; a `LOGISTICS` agent still cannot read a file back over HTTP, which T-092 owns. `DISPUTE_REVIEWER` can read the grant list but not create a grant (`user.update` is SUPER_ADMIN and OPERATIONS_ADMIN only), which is fine if T-080's automatic grant is the real path and a trap if it is not. `PROFILE_PHOTO` uploads work but nothing consumes them until T-041. Known minors left in: `reject()` tombstones and sets `REJECTED` in two transactions, so a crash between them strands a row no sweep revisits; `destroyAsset`'s catch logs the raw provider error rather than the redacted shape `providerRequest` uses; a replaced singleton-pool account recovering to `ACTIVE` violates the singleton index and the sweep swallows the 23505 hourly with nothing naming the cause; the access-log keyset has no `id` tie-breaker, so identical timestamps could skip a row in a compliance read; `grants` and `storage-accounts` paginate in memory and `listGrants` has no `LIMIT`; `expiresAt` on an upload ticket is advisory above 60 minutes, where Cloudinary's own signature validity is the real bound; and the seed never reconciles a changed `cloud_name` for an account rotated under the same prefix. `file_records` rows are never pruned, and the append-only trigger means the `ON DELETE CASCADE` cannot run, so whichever ticket adds retention owns dropping it for its sweep. No `shared-types` wire schemas or `api-client` hooks: the web ticket that renders uploads owns the client contract.

### T-045 — Notifications delivery pipeline (M11)

- **Touches:** `src/modules/notify/**`, migration `notify_*`
- **Depends on:** T-024, T-028
- **Acceptance criteria:**
  - Templates as data with versions and locales; event-to-template mappings; one `notifications` row per send; attempt history.
  - Send jobs on BullMQ with backoff and up to `NOTIFY_MAX_ATTEMPTS`; dead-lettered security notifications publish `notification.dead_lettered` (support opens a ticket in T-100).
  - Security-critical templates bypass preferences and rate limits; others respect per-category, per-channel preferences (NP1) and per-user caps.
  - Adapters: Mailjet (email), Termii (SMS), FCM (push); IN_APP feed (`GET /notifications`, mark-read) also pushed over the socket.
  - Outside production, SMS and push run in dry-run mode by default (`NOTIFY_SMS_DRY_RUN`, `NOTIFY_PUSH_DRY_RUN`): the message is rendered, recorded and logged with the recipient masked, but never sent. Local runs keep live provider keys (T-003), so this is what stops them texting real people. A test proves no provider call is made in dry-run mode.
  - Identity templates (OTP, new-device, password changed, session reuse) seeded; every later module ticket adds its own templates and mappings.
- **Status:** Done (2026-10-05). Plan: `docs/superpowers/plans/2026-10-05-t-045-notifications.md`. Migrations `0016_notify_schema` (generated) and `0017_notify_append_only` (custom; `notification_delivery_attempts` can only grow). **The idempotency boundary is `notify.notifications.id`**: a uuid v5 over `(eventId, templateKey, channel, userId)` (`domain/identity.ts`), inserted `ON CONFLICT DO NOTHING` inside the subscriber's own transaction, so an event redelivery, a handler retry and two bindings racing all land on one row; the provider call is then gated on a conditional `UPDATE … WHERE status IN ('QUEUED','FAILED')` (`services/delivery.service.ts`), which is what actually stops a second SMS when the platform's `processed_events` marker is not in play (an operator retrying a 29-day-old failed job). Proven end to end in `test/integration/notifications.int.test.ts` by deleting the marker and handing the subscriber queue the same envelope again. Preferences and the per-user cap are decided by one pure function (`domain/decide.ts`): a security-critical template bypasses both, a `SECURITY`-category one is never rate-limited even if its flag is missing, and a security-critical message with no verified address is recorded `DEAD_LETTERED` with `notify.notification.dead_lettered` published (support's hook, T-100) rather than suppressed — `PUT /notification-preferences` refuses to store a `SECURITY` opt-out at all, since a setting the pipeline ignores is a lie. Templates are data: the shipped catalogue (`domain/catalogue.ts`) is zod-parsed at import, checked by `assertCatalogueIntegrity` as the first thing `start()` does (a placeholder no binding supplies, a mapping with no template, a `SECURITY` template missing its flag, or a key with nothing in the default locale stops the process at boot naming the offender), then insert-only-synced so an operator's edit is never stamped over — a copy change is a new `version`. Bindings (code: which event, which template, how to pull recipients and variables out of a payload) live in `domain/binding.ts` and are **empty**: no module publishes a user-facing event yet, so T-031/T-034 and T-068 add theirs next to the templates already seeded. New config: `NOTIFY_DEFAULT_LOCALE`, `NOTIFY_MAX_ATTEMPTS`, `NOTIFY_RETRY_BASE_DELAY_MS`, `NOTIFY_RATE_LIMIT_WINDOW_MINUTES`, `NOTIFY_RATE_LIMIT_MAX_PER_WINDOW`, `NOTIFY_SMS_DRY_RUN`, `NOTIFY_PUSH_DRY_RUN` (the last two default to true outside production and are new in `.env.example`), `MAILJET_*`, `TERMII_*`, `FCM_*`. Two small platform additions: `ModuleContext` now carries `config` and `logger` (a module has no other way to see a tuning variable), and `providerRequest` sends a string body verbatim (FCM's OAuth2 token exchange is form-encoded). Seven findings from the whole-branch review were fixed: a missing provider credential now dead-letters instead of recording `SENT` (a delivery record that lies about an OTP is worse than none), with a production boot check that names the variable; a send job that finds no committed row throws so BullMQ's backoff retries it in milliseconds, instead of returning quietly and leaving the user to the once-a-minute sweep; `releaseStuck` judges a `FAILED` row on `last_attempt_at`, not `queued_at`, so it no longer adds a second job alongside a live retry chain, and it is bounded by a `LIMIT`; `markSent`/`markFailed`/`markDeadLettered` write back only while the caller still holds the claim, so a stalled worker cannot drag a delivered message back to `FAILED`; a disabled or deleted mapping row no longer switches off a security-critical send; a template that cannot be rendered dead-letters its own channel instead of rolling back the whole fan-out; and `WHATSAPP`/`VOICE` raise rather than quietly going out as plain SMS.
- **Deferred:** **quiet hours** — M11 names preferences and the per-user cap as the only gates on a send and specifies no time-of-day window, and a quiet-hours rule that deferred a security message would be exactly the silent suppression D2 forbids; `decideDelivery` is pure and takes everything as arguments, so M17 (T-048) can add the rule when it decides one. The admin endpoints of M11 §7 (dead-letter list, manual retry, `PUT /admin/notification-templates/:key`) need the RBAC catalogue (T-033) and the admin action log. `WHATSAPP` and `VOICE` are in the enum and route to the SMS queue (so the dry-run gate covers them) but have no adapter: `deliver()` raises `UnrecoverableError` rather than delivering one as an SMS the user did not choose. Email is plain text (`TextPart`); rich templates are copy authoring, M17's. `NOTIFY_QUEUE_ENABLED` is in `.env.example` but deliberately unimplemented — a flag that silently stops every notification is worse than a queue that is visibly down. Socket push for the IN_APP feed is T-027's: the row plus `notify.notification.sent` are the durable half, and the gateway subscribes. No `shared-types` wire schemas or `api-client` hooks for the feed and preferences (the web ticket that renders them owns the client contract). FCM's access token is cached per process, not shared; invalid device tokens are reported in the log, not retired (M1 owns `devices.push_token`). Delivery webhooks (`DELIVERED`, `delivered_at`) are unused: no provider callback is wired. `notifications` rows are never pruned — the append-only trigger on the attempt history means the cascade cannot run, so whichever ticket adds retention owns that, and it should also redact `rendered_body` for `SECURITY` rows, which today keeps every OTP ever sent readable indefinitely. The per-user cap is read-then-charge, so N worker processes can admit up to N extra in a window (the safe direction, and the comment says so), and it buckets on event time, so a replayed backlog charges a window that has already closed. Email has no dry-run flag of its own: it relies on `MAILJET_SANDBOX` (forced to `true` for the local target by `pnpm env:backend`) and, since the review, on a missing credential dead-lettering rather than pretending to send — `NOTIFY_EMAIL_DRY_RUN` would be the symmetric fix. `queued_at` comes from the database clock while `sent_at` and the sweep's cutoffs come from the app clock.
