# Epic 03 — Identity & access (M1)

Spec: `docs/specs/module-01-identity-and-user-management.md`. Decision C2 (design §5): staff, logistics and Park Agents are capabilities on one `users` row, separated by session scope.

### T-030 — Identity schema

- **Touches:** `src/modules/identity/infrastructure/postgres/schema/**`, migration `identity_*`
- **Depends on:** T-021, T-026
- **Acceptance criteria:**
  - Every M1 §5 table, enum, index and constraint, with `capability_type` holding `MERCHANT`, `MERCHANT_MEMBER` and `STAFF` (the opt-in `SELLER` capability is dropped, design §6.3), including: composite same-user FKs for primary email and phone (`ON DELETE SET NULL (column)`), verified-uniqueness partial indexes on normalised email and E.164 phone, the username format and pair `CHECK`s with the `::text` cast, `admin_role_assignments` four-eyes `CHECK`s and the dual-approval trigger, `session_scope` enum with `CONSUMER`, `STAFF`, `LOGISTICS`.
  - `identity_audit_log` is append-only: the trigger raises on update or delete and `komtru_app` lacks the privilege (both tested).
  - Integration tests prove: uppercase usernames rejected by the DB; one verified owner per email or phone under concurrent inserts; one primary per user; dual-approval roles cannot be inserted without an approver.
- **Status:** Done (2026-10-05). Plan: `docs/superpowers/plans/2026-10-05-t-030-identity-schema.md`. All 22 M1 §5 tables live in an `identity` schema under `src/modules/identity/infrastructure/postgres/schema/`, pinned by a census test that asserts the exact set of tables, indexes, CHECKs, foreign keys and triggers. Enums deviate from M1 §5.1 exactly as this ticket directs: `capability_type` is MERCHANT / MERCHANT_MEMBER / STAFF (design §6.3) and `session_scope` gains LOGISTICS (design C2). `pgcrypto` is not created — `gen_random_uuid()` has been in `pg_catalog` since Postgres 13. **`drizzle.config.ts` changed:** its glob `./src/modules/*/schema.ts` did not reach this layout, so `./src/modules/*/infrastructure/postgres/schema/*.ts` was added alongside it. **`grantRuntimeAccess()` changed:** it now grants `komtru_app` USAGE (never CREATE) on `public`, which closes T-021's deferred "no USAGE on public for extensions" item. Without it the `citext` operators are invisible to the runtime role and `username = 'janedoe'` silently resolves to `text =`, missing `JaneDoe` while the unique index still fires — a wrong answer, not an error. Four hand-written migrations: `0004` the citext extension, `0007` the composite same-user keys (`ON DELETE SET NULL (column) DEFERRABLE INITIALLY DEFERRED`), `0009`/`0014` the dual-approval trigger, `0012` `appendOnly('identity.identity_audit_log')`. Beyond the spec, from review: `admin_role_self_approval` and `admin_action_self_approval` CHECKs, because M1 §5.7's four-eyes rule names only approver≠grantor and left the grantee free to approve their own elevation; the dual-approval trigger skips a row being revoked (it previously made an unapproved grant unrevokable by the app) and takes `FOR SHARE` on the role, with a second trigger refusing to set `requires_dual_approval` while unapproved live grants of that role exist; and every `DESC` index is `NULLS FIRST`, because drizzle's `.desc()` emits `NULLS LAST`, which `ORDER BY … DESC` cannot walk (measured: a Sort over the whole match set instead of an Index Scan under LIMIT). Errors a service can key on: `KT001` append-only, `KT002` dual approval. **For T-031/T-032/T-033:** the module barrel is `src/modules/identity/index.ts`; `user_emails.email_normal` and `user_phones.phone_e164` must be written from `normaliseEmail()` / `normalisePhone()` in `src/platform/identifiers.ts` — the database enforces E.164 format but cannot recompute `email_normal`, so an unnormalised write defeats the verified-uniqueness index.
- **Deferred:** no seed rows for `roles`, `permissions`, `role_permissions` or `reserved_usernames` (T-033, T-037); M1 §15 anonymisation and `user_addresses` are T-039 and T-042. Review minors left to the tickets that own the behaviour: `user_emails.email` and `email_normal` are unrelated columns, so a row pairing a victim's display address with an attacker's normalised one is accepted and `user_emails_email_idx` would then resolve the victim's address to it (T-032 must write both from one `normaliseEmail()` call); `users.primary_email_id` need not point at the row flagged `is_primary`, nor at a verified one (T-032); `user_phones.country_code` is NOT NULL while `normalisePhone()` returns it optionally for non-geographic E.164 numbers, and `phone_e164_format`'s `{7,14}` rejects a handful of valid short numbers (St Helena, Niue) — neither can receive an SMS OTP (T-032); `admin_role_active_unique` treats an expired but unrevoked grant as live, so a lapsed time-boxed grant blocks a regrant until `revoked_at` is set (T-037); `mfa_factors_one_default` lets a PENDING factor hold the default slot against an ACTIVE one (T-036); `mfa_factors.phone_id` and `sessions.parent_session_id` may cross users, as M1 §5.8 defines them (T-031, T-036); `KT001`/`KT002` are not exported as TypeScript constants (T-037 should add them when it first catches one); `verifyLockdown()` still asserts only negatives, so it does not positively prove the `public` USAGE grant took — a non-owner `GRANT` raises rather than degrading silently, and the grant is asserted in `test/db/roles.int.test.ts`.

### T-031 — Sessions, tokens and principal resolution

- **Touches:** `identity/domain/session/**`, `identity/services/{session,principal}.service.ts`, `identity/http/middleware.ts`
- **Depends on:** T-030, T-023
- **Acceptance criteria:**
  - EdDSA (Ed25519) access JWT, 10-minute TTL, carrying `sub`, `scp`, `epc`, `sid`; JWKS endpoint.
  - Opaque 256-bit refresh tokens stored as SHA-256, rotated on every use; replaying a consumed token revokes the whole family and publishes `identity.session.reuse_detected`.
  - Kill switch: `sessions_epoch` cached in Redis; suspension bumps the epoch, revokes all sessions and makes `/auth/refresh` re-check user status, all in one transaction (the M1 D5 test that catches the epoch-only bug).
  - `authenticate({ scope })` middleware applied at router level; the principal re-resolves roles and logistics membership on every request and caches nothing on the token.
  - Scope isolation suite: a token of each scope is rejected by routers of the other two scopes; a consumer refresh token can never mint a staff or logistics session.
  - TTLs: consumer 30 days sliding; staff 30-minute idle and 8-hour absolute (M1 C3); logistics uses the consumer TTLs unless the owner says otherwise.
- **Status:** Done (2026-10-06). Plan: `docs/superpowers/plans/2026-10-05-t-031-sessions.md`. EdDSA access tokens carry `sub`/`sid`/`scp`/`epc` and nothing else; everything that decides what a caller may do — scope, status, epoch, roles, permissions — is re-read from Postgres on every request by `resolvePrincipal`, in one indexed query. The `authenticate({ scope })` middleware the ticket names is **not** a per-router middleware: `defineRoute` is the only registration path, so `mountRoutes` enforces `route.scope` and `route.permission` for every route at once, which a router nobody remembers to wrap cannot match. The platform now owns the caller's shape (`src/platform/http/principal.ts`: `Actor`, `Principal`, `AuthFailure`) and identity fills it in; `idempotency.ts` and `rateLimit.ts` key on `actor.key`, the same `user:<uuid>` string as before. `KomtruModule` gained an optional `resolveActor` that at most one module may declare, and `src/modules/index.ts` became `createModules(deps)` because identity needs the process's connections before it can answer "who is calling". 401 means "refresh" (`UNAUTHENTICATED` / `TOKEN_EXPIRED` / `SESSION_REVOKED`, plus RFC 6750 `WWW-Authenticate`), 403 means "your credential is fine and the answer is still no" — a wrong-scope session must never be 401 or the api-client would refresh and then sign the user out of the app they are legitimately in. **The rotation-family integrity T-030 left open is enforced by the shape of one statement:** the child row is written by `INSERT … SELECT` in which `user_id`, `scope`, `family_id`, `amr` and `absolute_expires_at` are copied by Postgres from the parent and are never parameters, so no request body can move a session between users, scopes or families or extend the absolute deadline. **From review, the one real defect:** a family-wide revoke is a single `UPDATE`, and under READ COMMITTED its snapshot is taken when the statement starts — blocking on a row another transaction holds `FOR UPDATE` re-checks that row through EvalPlanQual but never re-scans for rows inserted meanwhile, so a rotation committing beside a revoke left its freshly minted child alive. The reuse alarm fired while the newest token still worked, and the same phantom defeated `revokeAllSessions`, so suspension leaked a session that could refresh into a token carrying the _new_ epoch — exactly the epoch-only kill switch bug M1 D5 names. Every write to one user's sessions now takes `pg_advisory_xact_lock` **before any row lock** (after it would deadlock a rotation against a revoke), with two tests that drive the interleaving deterministically by parking a rotation inside its open transaction. Also from review: `/auth/refresh` is `retryable: false`, because the idempotency gate stores a completed response as plaintext jsonb for 24 hours and this one carries both tokens — declaring it retryable would undo `sessions.refresh_token_hash` and hand a request-capturing attacker the child token with a 200 instead of tripping reuse detection; the epoch cache compares with `<` rather than `!==`, since `sessions_epoch` only increases and a cache entry left behind the database would otherwise 401 a valid token for a whole TTL; `req.ip` is checked with `net.isIP` before it reaches an `inet` column; and `assertRouteInvariants` now refuses a `permission` on a `PUBLIC` route, where it could never be checked. New config: `IDENTITY_SIGNING_KEY` (64 hex = a raw Ed25519 seed, which is what the live `.env` holds; the public half is derived, so there is no second variable to keep in sync), `IDENTITY_SIGNING_KEY_ID`, `IDENTITY_ACCESS_TOKEN_TTL_SECONDS`, `IDENTITY_TOKEN_ISSUER`, `IDENTITY_TOKEN_AUDIENCE`, `IDENTITY_EPOCH_CACHE_TTL_SECONDS`. `JWT_SECRET` is deliberately unused — EdDSA needs no shared secret. Dependency added: `jose` 6.2.12. No migration. **For T-032/T-037/T-039/T-086:** `createSession(tx, deps, input)` takes _your_ transaction so a login is atomic with its audit and device rows; the scope passed there is the only place a scope is ever chosen, and a refresh can never change it. Password change is `revokeAllSessions(tx, { userId, reason, exceptSessionId })`; suspension must do `bumpSessionsEpoch` + `revokeAllSessions` + the status change in one transaction, then `epochs.invalidate` after the commit (`applyKillSwitch` is the standalone version). `Principal.companyMembership` is carried on every request and is always `null` until T-086 supplies the `logistics_company_members` lookup to `createIdentityAuth`.
- **Deferred:** the consumer **absolute** TTL is 365 days — M1 pins only "30 days sliding" and the column is `NOT NULL`, so the number is this build's and is one constant in `domain/session/ttl.ts` for the owner to change. No grace window on a replayed refresh token: a benign cross-tab double-submit kills the family, which is what M1 D5 prescribes, but the mitigation belongs in T-017's route handler. Login routes (`/auth/{consumer,staff,logistics}/login`) are T-032's; `GET /me/sessions` and `DELETE /me/sessions/{id}` are not built by any ticket yet. JWKS publishes one key and has no rotation or overlap window. JWKS is served at `/v1/.well-known/jwks.json`, because `defineRoute` is the only way to register a route and every route mounts under `/v1`; the edge should alias the conventional root path. The `permission` check is a flat `has()` with no catalogue behind it until T-037. `resolvePrincipal` does not reject a session whose `consumed_at` is set — that is the refresh token's state, the access token beside it is bounded by its own 10-minute `exp`, and every revocation path revokes the whole family (endorsed in review, but it is the one place this ticket chose smoothness over the strictest reading of M1 §9.2). The per-IP budget on `/auth/refresh` is 300/min because Nigerian carrier-grade NAT makes one IP thousands of people; the per-token key is what bounds abuse, and neither bounds guessing (nothing needs to, at 256 bits).

### T-032 — Registration, OTP and password login

- **Touches:** `identity/services/{auth,otp,credential,contact}.service.ts`, `identity/http/auth.controller.ts`
- **Depends on:** T-031, T-045
- **Cannibalized:** `identity/domain/credential/hashing.ts`, `breach.ts` (T-001)
- **Acceptance criteria:**
  - Phone-first and email registration (HTML E2, E3), OTP challenges delivered through `notify` jobs (SMS via Termii, email via Mailjet), wrong-code state (E3b), login by email, phone or username (E4), forgot and reset password (AC2, AC3), change password revoking other sessions.
  - argon2id per the lifted parameters with transparent rehash; k-anonymity breach check behind `IDENTITY_BREACH_CHECK_ENABLED`.
  - Uniform failure responses: login latency for existing vs. non-existent users differs by less than 5ms over 1,000 samples; forgot-password responses are identical for known and unknown identifiers.
  - Rate limits per IP, per identifier and per device on every auth route; OTP verify attempts capped.
  - Terms acceptance captured at registration (TOS1) with versions; re-acceptance flow for updated terms (TOS2).
  - Events: `identity.user.registered`, `identity.email.verified`, `identity.phone.verified`, `identity.login.failed`.
- **Status:** Done (2026-10-06). Plan: `docs/superpowers/plans/2026-10-06-t-032-registration.md`. Nine routes, no migration. The account-opening half of M1 sits on T-030's schema and T-031's `createSession(tx, …)`: every one of register, verify-otp, login, forgot, reset and change is a single transaction, so the user row, the contact row, the credential row, the session, the `identity_audit_log` entry and the outbox event commit together or not at all — §S10's "audit failure fails the request" is structural rather than a rule each call site remembers. **`otp_challenges` is used as the general "prove you hold this secret" table:** §10.1's `resetToken` is a second row of that shape with a 256-bit secret in place of the six digits and `max_attempts = 1`, which is why the reset flow needs no second table, no Redis key and no migration, and why it inherits the expiry, the single use and the attempt cap that are already tested. **§S3 is the design of `login.service.ts`, not a rule applied to it:** `LoginResult` has exactly ONE failure variant, because a union carrying `NO_SUCH_USER` or `SUSPENDED` is one somebody eventually maps onto three status codes; `resolveLoginCandidate` runs ONE statement for an email, a phone or a handle, so the hit and the miss cost the same round trips; and `verifyAndRecord` takes `userId: string | null` so the MISS path cannot forget the decoy argon2 verification — the §17 timing suite injects a constant-cost hasher and measures the database work, which is where a real difference would hide, since the argon2 half is identical by construction and proving that costs two minutes of CPU. The status check runs AFTER the password work, never before. argon2id at m=19456/t=2/p=1 with transparent rehash on login, and the k-anonymity breach check runs OUTSIDE the transaction (`validatePassword`), because it is a three-second HTTP call and holding a Postgres connection and its row locks across a third party's availability is the wrong trade. **Two changes to notify were unavoidable and both are narrow:** `resolveDestination` treated an unverified contact as absent, so every registration OTP would have been recorded `DEAD_LETTERED` — the OTP is the thing that MAKES an address verified, and demanding verification first is a cycle no user can break — and dispatch fans out to every channel under a template key, so one `identity.otp.requested` would have emailed a phone code to an address the account does not have yet. `NotificationRecipient.channels` narrows the fan-out and `allowsUnverifiedDestination(templateKey)` is a code-level Set in notify's domain rather than a column, because `notification_templates` is operator-editable at runtime and "may this reach an unproven address" should need a deploy. Four bindings are now registered for the templates T-045 seeded and left inert. Cannibalized `hashing.ts` and `breach.ts` from the old repo (T-001), adapted so both take their configuration as arguments. New config: `IDENTITY_HMAC_PEPPER` (required to build the module, like the signing key), `IDENTITY_BREACH_CHECK_ENABLED`, `IDENTITY_MIRROR_PHONE_OTP_TO_EMAIL`, and `APP_TERMS_VERSION`/`APP_PRIVACY_VERSION` — the last two are NOT in `docs/specs/backend-apis.env`, so `pnpm env:backend` does not write them and `resolveTermsVersions` in `domain/terms.ts` applies the shipped default (identity owns a legal document's version; the config loader does not reach into a module for a constant). Dependency added: `@node-rs/argon2` 2.2.2. **Platform additions:** a `'device'` rate-limit key with `deviceFrom` (M1 §17 asks for per-IP, per-identifier and per-device to trigger independently, and behind carrier-grade NAT neither of the first two bounds an attacker walking identifiers from one handset — the fingerprint is a signal and never an authenticator, §S15); `RateLimitSpec.perKey`, so §S4's "5/min/identifier + 20/min/IP" is two windows rather than the tighter one shared; and `ApiError.extensions`, RFC 9457 extension members, which is how screen E3b gets its `attemptsRemaining`. **From review, nine real defects, three of them serious.** `/auth/otp/resend` answered 200 for a live forgot-password challenge and 422 for the decoy, so one extra unauthenticated request with the id the forgot response had just returned undid the whole uniform-response design — it now re-issues the decoy against its own stored `destination_hash` and returns no `maskedDestination` at all, since the client already has one from the call that created the challenge. §S4's per-destination budget counted ATTEMPTS rather than sends, and every refused attempt wrote a row, so three `/auth/password/forgot` calls an hour against a known number pushed the 24-hour window up faster than it drained and locked that person out of every OTP the platform could send them, permanently; a spent budget now writes nothing and hands back the caller's own live challenge. The same path also superseded the code already in the user's inbox, so a fourth tap on "Didn't get a code?" destroyed the code while the 429 said to wait — waiting would not have brought it back. Also: `insertUser`'s public-id collision retry ran inside an aborted transaction and could only ever raise 25P02 (a SAVEPOINT per attempt now, and 30 bits means this fires in the tens of thousands of accounts); a live 23505 from `markEmailVerified` aborted the caller's transaction, so the "clean 409" arrived on a COMMIT that was silently a ROLLBACK and refunded the OTP attempt charged a moment earlier; `verifyChallenge` marked whichever contact was primary when the code was presented rather than the one it was issued for, and fell through from an EMAIL challenge to a PHONE row, which is one `else if` away from a verification bypass as soon as T-036 adds a change-contact route — it now recomputes `destination_hash` from the row it is about to verify; the unverified-destination allowance is keyed on a template key that covers every purpose including `PASSWORD_RESET`, so it is now a FALLBACK (a verified contact always wins) rather than a preference; the §S6 supersede was global over a destination, so two accounts legitimately holding one unverified number could kill each other's codes; `completePasswordReset` burned its single-use token when the new password was merely REUSED, stranding the user behind a 3/hour endpoint; and an extension member named `detail`, `errors` or `instance` could forge a field the problem body writes conditionally. **For T-033/T-034/T-036/T-037/T-039:** `AccountDeps` (`services/auth.service.ts`) is the one bag of dependencies every controller takes, assembled once in `createIdentityAuth`; `nextStep(state)` in `domain/registration.ts` is the single answer to "what should the client ask for now" and three endpoints return it; `writeAudit(tx, …)` plus `AUDIT_ACTIONS` is §S10's record and `metadata` holds ids, hashes, counts and reasons only; `upsertDevice` in `device.service.ts` is the minimum a login needs and T-036 should absorb it; and `POST /auth/password/change` accepts no `currentPassword` exactly when `user_credentials` has no row, which is M1 §9.3's phone path setting a first password — the session itself, minted against a code we sent to a number the holder demonstrably controls, is the proof.
- **Deferred:** **the OTP code is written in clear to `platform.outbox.payload` and to `notify.notifications.rendered_body`, and neither is pruned.** M11 D1 says there is no send without an event and the seeded template renders `{{code}}`, so the code has to reach notify somehow; `otp_challenges` stores only the HMAC, and then the same code sits in the outbox keyed to a `userId` indefinitely. The branch's own tests read live codes out of it, which is the clearest demonstration of the problem. The honest fixes — encrypting outbox payloads, or an outbox retention sweep, or notify fetching the code through a short-lived call — are all platform decisions this ticket should not make alone. T-045 already flagged `rendered_body` retention; **this needs its own ticket, and it is the highest-value one on this list.** `POST /auth/register` answers **409** for an already-VERIFIED contact rather than a uniform response: M1 §17 names login, forgot-password and party lookup as the enumeration-critical endpoints and not register, and a client genuinely needs to send the user to sign in instead — but it is an address-probing surface, bounded only by a deliberately tight 5/min per-IP budget (the per-identifier key never repeats for an attacker walking a list). The uniform alternative — accept, send the owner a "someone tried to register with your address" message, and never say — is the better answer and is a ticket of its own. MFA is absent: `/auth/mfa/verify` and §10.1's `{ mfaRequired: true, mfaToken, factors }` login branch are T-036's, and §S7's step-up on a password change is satisfied here by the current password alone. Social login is T-034's; `invitationToken` (§10.1, T-035) is rejected by the strict body schema rather than accepted and ignored, so nobody ships a client that believes it works. Staff and logistics login are T-037's and T-086's — `createSession` is only ever called with `CONSUMER` here. `GET /me/sessions` and `DELETE /me/sessions/{id}` still belong to no ticket. `/auth/otp/resend` re-reads the destination from the user's PRIMARY contact, because `destination_hash` is an HMAC and there is nothing to recover: a challenge for a non-primary contact cannot be resent, which is fine while every challenge is for the primary one and stops being fine the moment T-039 adds a second address. The §17 timing suite injects a constant-cost hasher, so it measures the database asymmetry and not argon2; a locked account is still one `UPDATE` cheaper than a wrong password (sub-millisecond, and fixing it means writing on the locked path). `startPasswordReset` keys a miss on the trimmed lower-cased input rather than a canonical form, so probe traffic against unknown addresses gets a budget per spelling. `issueProofToken` writes a row carrying the same `destination_hash`, so completing a reset spends OTP send budget. `PASSWORD_HISTORY = 5` and the offline weak-password list (40 entries) are this build's numbers; M1 §5.5 and §S2 leave both open. `identity.password.changed` is used in place of §11's `identity.credential.password_changed`, because T-045 seeded a `notification_event_mappings` row for the shorter name and a notification that never fires is worse than a name one word off the table. There is no geo-IP, so `{{location}}` in the new-device template renders the IP or "an unrecognised location". A registration that exhausts the per-destination budget still returns 201 with `delivered: false` rather than refusing; the account exists and the client must say so.

### T-033 — Username system

- **Touches:** `identity/domain/username/**`, `identity/services/username.service.ts`
- **Depends on:** T-030
- **Cannibalized:** `identity/domain/username/skeleton.ts`, `reserved.ts` (T-001)
- **Acceptance criteria:**

- **Status:** Done (2026-10-05). Plan: `docs/superpowers/plans/2026-10-05-t-033-usernames.md`. Scope was usernames **and** the M1 §12 RBAC catalogue, which `src/platform/http/route.ts` already names as T-033's (`permission?: string` — "from the catalogue (T-033)") and which T-030 deferred here. Domain under `identity/domain/username/` (skeleton, reserved, policy, suggest) and `identity/domain/rbac/catalog.ts`; `identity/services/username.service.ts`; `identity/http/username.controller.ts` for the four §10.3 routes; `identityModule` registered in `src/modules/index.ts`. **No migration:** `KomtruModule` gains an optional `seed?: (db) => Promise<void>` hook, run by `pnpm db:migrate` after the migrations (and alone as a new `pnpm db:seed`), so the catalogue and the reserved namespace are reconciled from code on every deploy. It is idempotent, takes `pg_advisory_xact_lock` so two deploys cannot interleave, reconciles `role_permissions` downwards but never deletes from `reserved_usernames` (Trust & Safety owns that table at runtime), and writes `requires_dual_approval` in the INSERT because T-030's backfill trigger refuses the flip afterwards. The catalogue is `Record<PermissionCode, Record<RoleCode, Grant>>` with no `Partial`, so a 23rd permission is a **compile error** until it has a matrix row; `test/modules/identity/domain/rbac/matrix.test.ts` re-parses M1 §12.3's own markdown table and compares all 264 cells plus the counts (22 × 12, 105 grants, per-role totals) — both guards were exercised by temporarily adding `geo.manage` and confirming `tsc` and 14 cases fail. §12.3's footnotes are data (`TICKET_SCOPED_PII`, `READ_ONLY_TIME_BOXED`, `ADMIN_ACTION_APPROVAL`, `DOCUMENTED_USER_REQUEST`), and a conditional grant is a grant at the catalogue layer — T-037 enforces the condition. **Defects found in the cannibalized code** (`skeleton.ts`, `reserved.ts`): reserved matching folded only the candidate against the reserved word's canonical fold, so `@fiutterwave` was claimable beside a reserved `@flutterwave`; `BLOCKED_SUBSTRING_SEED` held literal words no skeleton can contain (`officialsupport` vs `oficialsuport`), so three of its four compound entries never fired; `collapseRuns` compared a code point against the last UTF-16 unit and never collapsed astral runs; and — found in review — the multigraph pass and the narrow-glyph pass are two independent axes, so a handle taking one substitution from each (`@adrn1n` for `admin`, `@vvailet` for `wallet`) matched neither fold. `skeletonVariants` now returns the closure of both passes in both orders: of 3,958 generated impersonations of the 89 seed words, 79 escaped before and 7 after (all one construction on `flutterwave`), with zero false positives over 67 plausible Nigerian handles.
- **Deferred:** **user-to-user confusable matching still compares the canonical fold only**, so `@delistore` is claimable beside `@dellstore` and `@iagosdeals` beside `@lagosdeals` — reserved words are better defended than storefronts, which is backwards. The honest fix is a `users.username_skeleton_narrow` column with its own UNIQUE index, which is a migration this batch forbids; a service-side scan would be a full table scan on a PUBLIC route and still a check-then-insert race, so the gap is documented at `holder()` in `username.service.ts` rather than papered over. **Needs its own ticket.** M1 §6.2's profanity and hate list is not seeded (locale-specific; belongs in `reserved_usernames` with `category = 'OFFENSIVE'` via T-037's `username.reserve`). §6.4's "notify all counterparties from the last 90 days" needs M3 trade data — `identity.username.changed` carries `from`/`to` and is the seam. `hasActiveTrade` and `hasCompletedTrades` are injected ports defaulting to `false` until T-061 supplies them, so the active-trade block and the verified-seller support gate are wired but inert. The cross-user quarantine race (A releases `@foo` as B claims it) spans two tables and cannot be an index; the cooldown and lifetime cap are serialised by `FOR UPDATE` on the caller's own row. Routes declare `scope` and read `ctx.actor` as `user:<uuid>`; T-031 supplies `resolveActor` and `authenticate({ scope })`, until which the three `/me` routes answer 401 to everyone.

### T-034 — Social login

- **Touches:** `identity/infrastructure/providers/{google,apple,facebook}.ts`, `identity/domain/social/linking.ts`, `identity/services/social.service.ts`
- **Depends on:** T-032

### T-036 — Devices, MFA and passkeys

- **Touches:** `identity/services/{device,mfa,passkey}.service.ts`
- **Depends on:** T-032
- **Acceptance criteria:**
  - Device registry with fingerprint and push token; TOTP enrol and activate (HTML TF1), recovery codes shown once (TF2), SMS OTP factor, WebAuthn passkeys, step-up for sensitive actions; removing a factor requires step-up.
  - MFA mandatory for any user holding a staff role (forced-setup state, M1 C4).
- **Status:** Done (2026-10-06). Plan: `docs/superpowers/plans/2026-10-06-t-036-devices-mfa.md`. Nineteen routes, four factor kinds, **no migration** — T-030's `devices`, `mfa_factors`, `passkey_credentials` and `otp_challenges` were enough, and the two places that wanted a column got a shape inside an existing `bytea` instead. **The §10.1 `mfaRequired` branch T-032 left unbuilt is a second SUCCESS variant, not a second failure, and that is the whole design.** `LoginResult` still has exactly ONE failure member; `MFA_REQUIRED` sits beside `SESSION`, and every statement that could reveal whether an account holds a factor is textually BELOW `login`'s single `return { outcome: 'REJECTED' }` — there is no early read, no discarded lookup, and `holdsAdminRole` is passed the literal `false` rather than queried, because `mfaRequirement` makes it inert for CONSUMER and a round trip that cannot change the answer is a round trip that can be measured. So the branch is reachable only by somebody who already holds the password, and an attacker who can see it has already won the thing enumeration is the first step towards. `login.mfa-enumeration.int.test.ts` holds that two ways: §17's timing comparison across an MFA account, a plain account and nobody, and — because a fast machine hides one indexed lookup inside 5ms — a COUNT of the statements the rejected path issues, through a `countStatements` helper that wraps both `pool.query` and the client `pool.connect()` hands drizzle for a transaction. `signIn` still has exactly one `throw`. `/auth/mfa/verify` answers the SAME 401 `INVALID_CREDENTIALS` for every failure and differs only by an `attemptsRemaining` extension, which is unreachable until the token itself has matched — so it cannot tell a real token from an invented one. **The `mfaToken` is an `otp_challenges` row**, as §10.1's `resetToken` already is (T-032): 256 bits, five minutes, five attempts, with `destination_hash` = the user id under a domain of its own, which keeps it out of §S4's per-destination send budget and out of `issueOtp`'s supersede. **Device rows are written in the transaction that creates the session and nowhere else** (T-031's rule): the challenge branch writes no device row and does not touch `last_login_at`, because a device row written at the password step would make `isNewDevice` false by the time the session opened and §S11's new-device notification would never fire for anybody using MFA. **TOTP is written, not installed** (`domain/mfa/totp.ts`): RFC 6238 over RFC 4226 with RFC 4648 base32 is forty lines of arithmetic over `node:crypto` and the specification publishes test vectors, so it is PROVED against all six SHA-1 rows of Appendix B rather than trusted to a package on the authentication path. SHA-1 is deliberate — every shipping authenticator implements HMAC-SHA1/6/30 and several ignore the URI's `algorithm`, and HOTP rests on HMAC's pseudorandomness, not on collision resistance. WebAuthn is the opposite call: CBOR, COSE keys and attestation parsing over attacker-supplied binary is not something to hand-roll, so `@simplewebauthn/server` 14.0.3 sits behind `infrastructure/webauthn/relying-party.ts`, the only file that imports it — the wrapper binds rpID/rpName/origins once and turns the library's THROWS into verdicts, because a browser prompt that timed out must not be a 500. The WebAuthn nonce lives in **Redis** and not in `otp_challenges`: that table stores only HMACs by design, and a server nonce has to be read back. **Two columns carry a shape rather than a value, both to avoid a migration this wave forbids.** `mfa_factors.secret_enc` holds `{v:1,secret,lastStep}` for a TOTP factor — the replay guard needs the last step SPENT, and `last_used_at` cannot yield it when the user's clock runs ahead; and one RECOVERY_CODE row holds the whole sealed sheet as HMACs, so `GET /me/mfa/factors` reads as a list of factors and spending one is a single row lock. **Recovery codes are not a second factor** (`domain/mfa/policy.ts`): an account holding only them has nothing to present that it was not already handed on a screen, so they neither trigger the login branch nor satisfy C4 — and removing the last real factor revokes the sheet with it. **§S7 step-up is a token, not a claim on the session**: `sessions.amr` is true for a session's whole 30 days and T-031's `Principal` carries no recency, so proving it is you NOW is a single-use `SENSITIVE_ACTION` row presented as `stepUpToken`. Its refusal is **403 `STEP_UP_REQUIRED`** and deliberately not 401: the access token is perfectly valid, and T-031's api-client answers a 401 with a refresh and then a sign-out, which would end a legitimate session in the middle of the action — the refusal is conditional and `acceptedFactors` rides back as an RFC 9457 extension member naming the remedy. **D2 C4 is split, deliberately:** `mfaRequirement` is the one pure function that answers "does this sign-in need a factor", and it reserves forced setup for the STAFF scope (§S13) because forcing an admin's CONSUMER session through it would lock them out of the very `/me` routes enrolment lives on; the half that IS enforceable today is enforced — `removeFactor` refuses to strip the last factor from a live admin role holder while `IDENTITY_STAFF_REQUIRE_MFA` is on. **From review, five real defects, one of them branch-breaking.** `testConfig()` had no `WEBAUTHN_ORIGINS`, and `createRelyingParty` refuses an empty list by design, so `createIdentityAuth` threw inside `beforeEach` in six infra suites — including this ticket's own §17 suite and T-032's, four of them previously green: the evidence the whole ticket turns on could not have been produced. **The enrolment ceremony and the login `mfaToken` shared one `(purpose, destination_hash)` family,** so signing in on a second device consumed a half-finished enrolment — the QR code the user had just scanned died with a 422 telling them to start again — and finishing any enrolment consumed a live sign-in challenge; they now hash the user id under two different domains. **`verifyFactor`'s TOTP branch read an unlocked row** and then wrote the spent step back, so two `/me/step-up` calls firing one shoulder-surfed code in the same millisecond both succeeded — exactly the one-use property the guard exists for; it now re-selects `FOR UPDATE`, as the RECOVERY_CODE branch already did. **`activateSmsFactor` passed the caller's `challengeId` straight to `consumeOtp`,** which recomputes its HMAC from the row's own purpose and destination and therefore verifies ANY live challenge of that user's — a live email-verification code could turn an SMS factor ACTIVE with nobody ever proving possession of the handset, which on a recycled Nigerian number (M1 D4) is a takeover path; the challenge is now resolved from the factor's own phone. And three integration tests activated TOTP with the CURRENT step and then presented that same step, which the replay guard correctly refuses ~97% of runs. New config: `WEBAUTHN_RP_ID`, `WEBAUTHN_RP_NAME`, `WEBAUTHN_ORIGINS`, `IDENTITY_STAFF_REQUIRE_MFA` (defaulting to **true** — §S13 is mandatory and the switch exists to relax it in a sandbox). `ENCRYPTION_KEY` becomes required in practice: `createIdentityAuth` now builds `createEncryption`, `createRelyingParty` and `createWebauthnChallengeStore` eagerly and lets each throw naming its variable, the way `createTokenSigner` and the pepper check already do. New problem code `STEP_UP_REQUIRED`. Dependency added: `@simplewebauthn/server` 14.0.3. **T-031's two homeless routes are taken:** `GET /me/sessions` and `DELETE /me/sessions/{id}` are built here, beside `/me/devices`, because they are the same screen; `revokeSession` kills the whole rotation FAMILY and not the named row, since revoking only the tip leaves a parent a thief holding the previous refresh token can still rotate from. **For T-037/T-034/T-039:** `mfaRequirement({ scope: 'STAFF', …, holdsAdminRole, staffRequireMfa })` is the forced-setup answer and `holdsLiveAdminRole(tx, userId)` supplies its third argument; `requireStepUp(tx, deps, { userId, token, acceptedFactors })` is the §S7 gate every sensitive route should call; `activeFactors(tx, userId)` is §7.4's "no active MFA factor" test and `listPasskeys` its "no passkey" test; and `completeMfaLogin` is only ever called with `CONSUMER` here, so a staff login needs its own caller.

That gap is T-032's and predates this ticket: its decoy pads the ~50ms of argon2, not the database, and closing it means an unauthenticated request WRITING a decoy row for every identifier matching nobody. binding it needs a column or a second domain and is worth doing when the second §S7 call site lands.
