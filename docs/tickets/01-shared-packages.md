### T-011 — `ui-kit` tokens, fonts and brand mark

- **Status:** Done (2026-10-05). Plan: `docs/superpowers/plans/2026-10-05-t-011-ui-kit-tokens.md`. The HTML declares the ticket's 52 properties, repeated identically across five `:root` blocks; `packages/ui-kit/scripts/extract-tokens.ts` generates `src/tokens.css`, `src/tokens.ts` and `packages/config/tailwind/preset.css` from them, and `packages/ui-kit/test/tokens.test.ts` re-parses the HTML to prove all three still agree.
- **Deferred:**

  - Tailwind's default _colour_ palette is retired (`--color-*: initial`) so every colour utility names a reference token; its spacing, radius, font-size and shadow defaults remain, because the reference itself uses off-scale values (11px, 13.5px, 2.5px rings).

  - `packages/ui-kit` overrides the shared library tsconfig with `moduleResolution: bundler` and `jsx: react-jsx`, because `next` ships no `exports` map and NodeNext cannot resolve `next/font/google`. ### T-012 — `ui-kit` core primitives and Storybook

- **Status:** Done (2026-10-05). Plan: `docs/superpowers/plans/2026-10-05-t-012-ui-primitives.md`. Nineteen primitives live in `packages/ui-kit/src/primitives/**`, each emitting only the token utilities `@komtru/config`'s Tailwind preset publishes. `packages/ui-kit/test/primitives-parity.test.tsx` renders every primitive, compiles its classes through the real preset and diffs the declarations against the rule the reference HTML declares for it — 132 parity checks — so a property a primitive does not reproduce has to be named in `DEVIATIONS` with a reason, a property it applies that the reference does not has to be named in `ADDITIONS`, and an entry in either that no longer applies fails too. `src/primitives/DEVIATIONS.md` is that list in prose, with the screen and line number T-016 should shoot each primitive against. Storybook 10.6.1 (`@storybook/react-vite`, Vite 8) has one story file per primitive with a story per documented state. 305 tests in `@komtru/ui-kit`.
- **Reviewed:** two independent whole-branch reviews. The second found that the parity harness modelled the cascade wrongly — it merged same-property utilities in the order they appear in the `class` attribute, where a browser uses stylesheet order — and that this was concealing live rendering bugs: `OtpInput`'s filled and invalid cells both lost their background to the base, so E3b's entire wrong-code treatment did not render. The harness now resolves by emission order, a new guard fails any element that claims a decisive property twice, and the invalid state is compared against E3b's own inline `style` attribute since the reference declares it in no rule. Earlier findings, all landed: (1) The parity harness only diffed one way, so it was blind to anything a primitive _adds_ — an invisible `hidden opacity-0` button passed. It now diffs both directions against an `ADDITIONS` table with the same reason-and-staleness rules as `DEVIATIONS`, and the reviewer's counter-example fails. (2) `Toggle` emitted both `bg-trust-emerald` and `bg-stone-gray` for a locked-and-on switch, leaving the cascade to pick — and Tailwind's order picked emerald, the opposite of `.m-switch.locked`. That is the only locked switch the reference draws. (3) `DEVIATIONS.md` claimed `Banner (info)` deviated in nothing while the component applied one body/icon treatment to all four tones; the info note is 11.5px at 1.5 behind a 15px icon, the alert banners 11px at 80% behind a 16px icon. Ten further suggestions were taken: a focus trap in `Sheet`, a throw when a class compiles to no rule, a guard against a misspelled `DEVIATIONS` property, the `.proof-thumb .play-badge`, the reference's own gate copy, `.ko-step-line`'s margins, and honest wording for `MediaGate`. Parity grew from 53 checks to 66.
- **Deferred:**
  - **No primitive has had a screenshot taken.** T-016's harness did not exist in this worktree. It does now — `pnpm visual-check --screen <id> --url <url>` closes the gap, and `src/primitives/DEVIATIONS.md` names the screen and line to shoot each of the nineteen against.
  - The reference declares no toast rule and says so out loud ("A real moment, not just a toast", line 3978). `<Toast>` borrows `.offline-banner`'s geometry, is scoped to small confirmations, and has no reference instance to shoot.
  - `.scope-note` is the design document's own page chrome, not a product component — its five copies disagree on `max-width` (700/760/780px). The product's info note is `.proof-compare-note`, which is `<Banner tone="info">`. The risk tone is an extrapolation: the reference has no banner in it.
  - **T-017 owes the app three things `ui-kit` cannot ship**, because it has no stylesheet beyond `tokens.css`. `.storybook/preview.css` carries all three so the stories are honest. (a) `@keyframes shimmer` and `@keyframes nodePulse`, or `<Skeleton>` and `<NodeLoader>` sit still. (b) The global `:focus-visible` rule — primitives carry the ring as a utility, but any focusable element a _screen_ adds gets it only from the global rule, so without it those elements have a ring in Storybook and none in the app. (c) The reference's element defaults (`body`, `h1–h4`, `p`, `img`/`svg`).
  - `className` on a primitive **appends, it does not override**: two utilities for one property are resolved by stylesheet order, so `<Card className="rounded-[10px]">` keeps `rounded-md` as often as not. Documented on `cx` with a test. Screens that need a different value need a prop, not a class.
  - `.ko-stepper` is restated three times in the reference as three different designs (`komtru-refinement-v2` numbered inline rail, `komtru-nav-v2` centred-dot rail, `.p0-stepper`). `<Stepper>` reproduces the first; the parity row names the `<style>` id so the choice is explicit.
  - The reference's global `:focus-visible` also sets `border-radius:4px`. It is not reproduced: that rule is declared before every component rule, so in the reference any element with its own radius keeps it, and baking 4px into a utility would invert the cascade.
  - `<Toggle>`'s knob is a real `<span>`, not `.m-switch::after`, and `<FileDropzone>`'s upload target is a `<label>` wrapping a visually hidden file input rather than the reference's non-functional `<div>`: a kit that ships no stylesheet cannot reach a pseudo-element, and a dropzone has to actually take a file.
  - `<Sheet>`'s scrim is `fixed`, not `absolute`, and drops its `border-radius`: the reference pins it inside the 340px phone frame it is drawn in, and a real screen has no frame.
  - Added beyond the HTML, consistently and deliberately: `motion-reduce:animate-none` on every animation, `aria-disabled` plus `opacity-55` on a disabled button (the reference never draws one), and an `aria-invalid` + risk-border error treatment on `TextField`/`Select` (the reference styles only the message).
  - **`TextField` and `Select` are client components**, which the plan's RSC list did not anticipate: both call `useId` to tie label to control. That makes every form field in the product a client component. The alternative is a required `id` prop on every field, which pushes the bookkeeping onto 200-odd screens; `useId` is the better trade, but it is a trade. `Toast` went the other way — it only forwards `onDismiss`, so it needs no boundary and now has none.
  - `FileDropzone` is finished rather than deferred: it takes a drop as well as a click, `onRemove` puts a wrong photo back, and `requiredCount` is **required** with no default — a gate that defaults open is a gate nobody set, and "a seller cannot accept sight-unseen" is too important to inherit by omission. The reference draws no drag state, so the dragging treatment borrows the focused-input look it does draw.
  - Parity rows address elements by position in the rendered markup (`node: 8`) and `classAttributes` skips class-less elements, so adding a class to a wrapper shifts every index below it. It fails loudly rather than silently, so this is a maintenance cost rather than a correctness risk; addressing by a `data-parity` attribute is the obvious later improvement.
  - `build-storybook` is a package script, not a turbo task: it is a 1s Vite build that nothing else depends on, and wiring it into `turbo run build` would put it on every ticket's critical path. Run `pnpm --filter @komtru/ui-kit build-storybook` to check it.
  - `packages/ui-kit/tsconfig.json` now includes `.storybook/*.ts` explicitly — TypeScript's `include` globs skip dot-directories, and typescript-eslint's project service refuses to parse a file the program does not contain.
- **Touches:** `packages/ui-kit/src/primitives/**`, `packages/ui-kit/.storybook/**`
- **Depends on:** T-011
- **Acceptance criteria:**
  - Components matching the HTML's classes: Button (`btn-primary`, `btn-secondary`, sticky footer), Chip (`protected`, `awaiting`, `risk`, `resolved`, `verified`), Avatar, Card, TradeRow (`trade-row` with amount, parties, 5-step progress), Stepper, OtpInput (`otp-cell`), TextField, Select, Toggle, Sheet/Modal, Toast, Skeleton plus node-pulse loader, EmptyState (explain → benefit → action), Banner/scope-note, FileDropzone with mandatory-media gate.

### T-013 — `ui-kit` layout shells

- **Status:** Done (2026-10-06). Plan: `docs/superpowers/plans/2026-10-06-t-013-ui-shells.md`. Four shells live in `packages/ui-kit/src/shells/**`, each a composition of reference-exact parts rather than one configurable component: `MobileShell` (+ `TopBar`, `LogoBar`, `TabBar`), `DesktopShell` (+ `SideNav`, `TopNav`), `PublicShell` and `ConsoleShell`. None has a device frame — the reference draws every screen inside a 340px phone or a 560/1040px mock browser, and those frames' heights and inner scrollers are the shells' only systematic deviation. `test/shells-parity.test.tsx` checks 47 rows across 44 reference selectors the way T-012's suite checks its primitives, but **at a width**: a shell's rule is conditional where a primitive's is not, and `.dweb-content` (24px) is the same element as `.tweb-content` (20px). `test/responsive-css.ts` is what makes that possible — `declarationsAtWidth(classes, width)` compiles the real Tailwind preset, keeps each rule's enclosing `@media` stack, evaluates both syntaxes in play (Tailwind's `(width >= 64rem)` and the reference's own `(max-width:900px)`) and merges the survivors in emission order, which is the cascade model T-012's second review forced on the width-blind reader. `referenceRule` gained the same `atWidth`, because the reference carries responsive overrides of its own and merging one into its base reads as the reference contradicting itself. The parity runner itself moved to `test/parity.tsx` so both suites share it; `primitives-parity.test.tsx` keeps its tables and is still 132 tests. `test/shells/four-widths.test.tsx` renders every shell at 640, 768, 1024 and 1440 and resolves the decisive element's cascade at each, and asserts the switch happens at 1024 and not 1023. 544 tests in `@komtru/ui-kit`, 231 of them parity.
- **Visual check:** the shells own no screen, so they were shot against the eight reference screens that draw them — E3, AC1, D9, T1, D8, T5, NAV, TO-PA9 — through a static Storybook build. 0.51% to 7.41% of pixels flagged. `docs/ui-review/T-013/README.md` is the index; the harness filed each review under the screen's _own_ ticket, which is where it belongs, because that ticket re-runs the same check and the prose survives the regeneration. Three findings account for most of the flagged pixels, and all three are places the reference's markup has no rule behind it: `.tb-icon` is only ever declared as `.scr-topbar .tb-icon`, so AC1's and Z1's logo-row bell is an unstyled `<div>` that renders as a zero-height box; `.ko-dweb-sidebar .ds-logo` declares no `svg` rule, so NAV's brand mark fills its box at ~56px; and `.btn-primary` is `width:100%` while three of these screens write `width:auto` inline, which `cx` cannot undo. Each is reproduced the way the markup plainly intends and written down.
- **Reviewed:** one fresh whole-branch review on `opus`, which checked ten reference rules by hand rather than trusting the suite and found no drift in any shipped component. Four findings landed. (1) **The width evaluator had a silent blind spot**: it recognised only `sm:`–`2xl:` as width-deciding and treated everything else as width-blind, so `max-lg:hidden` and `min-[900px]:w-[228px]` were dropped from the cascade, raised no addition, and escaped the "compiles to no rule" guard — `max-lg:bg-white` returned an empty map instead of throwing. It now allowlists the variants a width genuinely cannot decide and **throws** on anything it can neither resolve nor rule out. (2) **`MobileShell` rendered a configuration it cannot draw**: `StickyFooter` and `TabBar` are both `sticky bottom-0`, so a screen passing both gets them overlapping — measured in Chromium at 340×660 on a scrolling body, the footer pins to y=614–660 and the tab bar's top lands at y=618. It throws now, the way `soleCurrent` does, and the order test that had been rehearsing the broken combination is split in two. (The reviewer attributed the overlap to two `margin-top:auto` items splitting the free space; that is not the mechanism — `main`'s `flex-1` absorbs it first — but the bug is real by the sticky route.) (3) **A `badge` on `TopBar`'s `back` escaped its control**: only the trailing action carried `position:relative`, so the absolutely-positioned dot resolved against `MobileShell`'s root and landed in the page's top-left corner. Every control is positioned now and `back` cannot take a badge at the type level. (4) The ticket note itself was missing. Six smaller points were taken: a parity row for the `<button>` branch of a nav rail (which `w-full text-left` had been slipping past), the four-widths render assertion made width-sensitive instead of the same assertion four times, and the list-markup, landmark-naming, `<aside>` and `.scr-logo-row` decisions written into `src/shells/DEVIATIONS.md`, which had claimed to be complete.
- **Deferred:**
  - **`md` (768) is a token here, not a behaviour.** No shell carries an `md:` variant: the shape changes are at `lg` (the nav swap, the padding step, the console rail, D8's split) and at `sm` (the console page head). That is the reference's own rule — "tablet doesn't get bespoke screens, it inherits the desktop shell" — which means **`md` is the boundary at which an app swaps `MobileShell` for `DesktopShell`**, and nothing in `ui-kit` enforces that. `BREAKPOINTS.md` is exported so the app (T-017 and the screen tickets) can make the choice explicitly.
  - **The breakpoints are `rem`, not `px`.** Tailwind v4's `sm`/`md`/`lg` are `40rem`/`48rem`/`64rem`, which are the ticket's 640/768/1024 only at a 16px root. They are not overridden: moving with the reader's text size is the behaviour a reader who has scaled their type wants, and `packages/config/tailwind/preset.css` is generated from the HTML's `:root`, which declares no breakpoint token. `test/shells/breakpoints.test.ts` re-reads both of the reference's `.breakpoint-note` blocks and asserts the compiled media queries match.
  - **The TrustOps sheet has breakpoints of its own and they are not these.** `<style id="komtru-nav-v2">` collapses the rail under `@media(max-width:900px)` and stacks `.ko-page-head` under `@media(max-width:640px)`. The ticket's scale wins, so `ConsoleShell`'s rail collapses at `lg` — 124px later than the drawing — and the page head stacks below `sm`, one pixel earlier than `max-width:640px` (Tailwind's `sm:` fires _at_ 640; the reference's query stops after it).
  - **`.ko-dweb-sidebar` is 228px and `.ko-dweb-content` is `24px 28px 28px`**, not the "180px sidebar, 24px content padding" that section's own prose claims. The rules win: they are what every TrustOps screen in the file is drawn against. The 180px/24px pair is the _consumer_ shell (`.dweb-sidebar`, `.dweb-content`), which `DesktopShell` reproduces exactly.
  - **`.dweb-shell` has no parity row.** The reference declares it twice in one `<style>` block with `min-height:520px` and `560px` — two sections of the gallery sizing their own frames — so the harness refuses to merge it rather than pick. `shells-parity.test.tsx` asserts that it still refuses, so the day the reference agrees with itself the row can be written; `DesktopShell.test.tsx` asserts the `display:flex` directly.
  - **D8 states its two-column split inline, not in a rule**, so `PublicShell`'s 280px rail is asserted in its own test and at all four widths rather than by parity. D8 also draws no header at all — it leans on the mock browser chrome — which is why `brandLabel` is optional: omitted is D8, given is the brand-only bar T5 draws for the same page.
  - **`TO-PA9` is drawn in a desktop frame while showing the tablet state.** That is why `collapsed` is a prop and not only a breakpoint — and the reference draws a Collapse control in the rail, which implies the same prop. `ConsoleShell` takes a `navFooter` slot for it; the control itself is T-140's, because collapsing is state and no shell here holds any.
  - **Every shell is a server component and `sources.test.ts` keeps it that way** — no hooks, no `'use client'`, no inline event handler, only forwarding the caller's. A shell that grew state would push a client boundary around every screen in the product.
  - **Parity rows still address elements by position** (`node: 4`), inherited from T-012. Adding a class to a wrapper shifts every index below it; it fails loudly rather than silently, and a `data-parity` attribute remains the obvious improvement. It is also why the `<button>` branches needed a row of their own to be seen at all.
  - **`packages/ui-kit/eslint.config.mjs` now ignores `storybook-static/**`.** Git already ignored it; the linter did not, so running the Storybook build before `pnpm lint` failed the lint on bundled vendor code. Outside this ticket's stated file scope, and the one file here that could collide with T-014.

  - `.tb-icon` inside `.scr-logo-row`, the unsized `.ds-logo` mark, the list markup the tab bar does not use, the two identically-named landmarks in `DesktopShell` and the `<aside>` around a public page's hero are all argued in `packages/ui-kit/src/shells/DEVIATIONS.md`. Read that file before building a screen on these shells.

Without it `KOMTRU_BROWSER_TESTS=1` was set nowhere in CI, so the twelve tests that prove the harness still takes a correct screenshot — including "a screen against itself scores zero" — never ran. This also closes the same pre-existing gap for `scripts/test/playwright-browser.test.ts`.

  - Anti-aliased pixels are excluded from the score _and_ from the heat map (`aaColor`), because pixelmatch's default paints them yellow and on a text-heavy screen that is more highlighted area than the red it counts.
  - No threshold gate: the CLI reports the ratio and exits 0 unless it errors. What counts as an acceptable deviation is a judgement each screen ticket writes down, not a number the harness can hold.
  - Screenshots are deterministic on one machine, not across machines: Chromium rasterises text differently per platform. Compare a run against the reference, never against someone else's PNG.
