## What T-064 already did (reused, not rebuilt)

On a trusted delivery signal T-064 moves the trade to `INSPECTION`, stamps `inspection_deadline_at` from
the snapshotted `inspection_window_hours`, and opens an `INSPECTION` deadline row. Reaching
`UNCONFIRMED_DELIVERY` opens an `UNCONFIRMED_DELIVERY_GRACE` row from the snapshotted
`delivery_grace_hours`. T-065 owns the jobs that fire those rows, using the idempotent `openDeadline`.

## Migration 0046 (new enum only; no `ALTER TYPE ... ADD VALUE`)

- enum `trade.inspection_extension_status` (PENDING, ACCEPTED, DECLINED, CANCELLED, LAPSED), created and used in the same migration.
- `trade.inspection_extension_requests`: one row per inspection deadline **ever** (unique on `deadline_id`), so "once" (BEI1) is enforced by the database, not only the service. Extra hours, note, the deadline as it stood, requested date, status, responder.
- `trade.inspection_acknowledgements`: one per trade, **append-only** (trigger + grants from `appendOnly()`), FK `ON DELETE restrict`. The buyer's explicit Z5 acknowledgement is evidence a dispute can read.

## Rules

1. **Inspection window (BEI1/BEI2).** The window is the trade's snapshot; nothing here reads the live Trade Standard. The buyer may ask for extra hours once, between 1 and one original window, while the trade is `INSPECTION` and the deadline has not passed. The seller accepts (deadline row and `trades.inspection_deadline_at` move, `extension_count` + 1) or declines (the date stands). The window only ever grows. The migration's unique index makes a second request impossible even through a race.
2. **Compare (Z4).** `GET /trades/:id/inspection` (either party): the seller's pre-shipment proof (`trade_proof_media`), the delivery evidence (every recorded delivery signal, the self-arranged waybill and receipt photo; the driver's phone goes to the seller only), the window and any extension request, and `autoReleasePaused` (a boolean only: a hold's source and reason are not disclosed).
3. **Confirm and release (Z5).** `POST /trades/:id/accept-inspection` (M7 §9's name) with `{ acknowledged: true }`, buyer only. Writes the acknowledgement, moves `INSPECTION -> COMPLETED` with `COMPLETE`, closes the inspection deadline `MET`. A replay by the same buyer returns the trade as it stands. Refused with 409 while a hold or an open dispute exists (see open questions).
4. **Auto-complete (AR1).** The sweep body is `processInspectionDeadline` per due row, one transaction each: lock the trade `FOR UPDATE SKIP LOCKED`, lock the deadline, re-read status, active holds and the dispute seam, decide with the pure function, claim the row with a guarded `UPDATE ... WHERE status = 'PENDING' RETURNING`, apply `INSPECTION_ELAPSED -> COMPLETED`, and publish in the same transaction. A hold or an open dispute means `WAIT`: nothing is written and the row stays pending for the next sweep. A trade that already left `INSPECTION` closes the row `MET` (completed or settled) or `CANCELLED` (disputed and the rest). A pending extension request lapses when the original date passes (same default as T-064).
5. **Grace (M7 §6).** `processGraceDeadline`, same shape: an `UNCONFIRMED_DELIVERY` trade whose grace elapsed converts with `GRACE_ELAPSED -> INSPECTION`, reason `GRACE_PERIOD_ELAPSED`, stamps `inspection_deadline_at = now + snapshotted window` and opens the `INSPECTION` row. A hold or open dispute waits. Buyer confirmation already closes the grace row `MET` (T-064).
6. **`trade.completed` -> release.** Every transition publishes `trades.trade.state_changed`; T-074 subscribes to `to = COMPLETED`. T-065 additionally publishes `trades.trade.completed { via }` in the same transaction for notifications (AR1 is "distinct from manually tapping Confirm & Release"). T-065 does not build the release.
7. **SETTLED.** `trades.on-escrow-released` consumes `ledger.payment.escrow_released` and calls `settleTrade`: `COMPLETED -> SETTLED` with `SETTLE`, actor `LEDGER`. Already `SETTLED` is a no-op; any other status is logged and ignored (a dispute-split release belongs to T-080), never thrown, since a retry cannot fix it. The ledger is not imported: `ledger` already imports `trades`, so the reverse would be a cycle. The trades module therefore declares the event's name, version and the two fields it reads, and **T-074's merge should swap that for the ledger's exported definition**.

## Seams

- **SEAM(T-080)** `InspectionDeps.disputes.hasOpenDispute`: false until the dispute service exists. T-080 supplies a real read and the status `DISPUTED` check already in the machine covers the transition itself.
- Nothing re-drives auto-complete after a hold lifts except the next sweep (see question 2).

## Open questions for the owner (conservative default applied)

1. **Hold during manual confirmation.** T-064's question 5 asked whether a `PARK_EXCEPTION` hold blocks the buyer. For delivery it does not. For _completion_ I refuse with 409 `HOLD_ACTIVE`: T-074 will not release under a hold and nothing re-drives it, so a `COMPLETED` trade could sit unpaid. Confirm.
2. **After a hold lifts.** The inspection window has already elapsed, so the next sweep completes the trade at once and the buyer gets no fresh time. Literal reading of AR1 ("unless a hold exists"); a fresh grace is the alternative.
3. **Seller silent on a BEI1 request.** Default: the request lapses at the original deadline and the trade auto-completes on the original date. The alternative (a pending request blocks auto-complete) hands a buyer an unbounded lever over the seller's money.
4. **Extension size.** 1 hour to one original window. Not in the docs.
5. **Request after a decline or lapse.** Not allowed: "once" means one request per inspection window.
6. **Dispute during `UNCONFIRMED_DELIVERY` or `INSPECTION`** moves the trade to `DISPUTED` (T-080); this ticket only waits on the seam.
7. **Escrow action row.** No `escrow_action_requests` RELEASE row is written here; T-074 does not use that table yet.
