# T-031 Sessions, Tokens and Principal Resolution Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** A caller presents a 10-minute EdDSA access token; the platform re-reads that caller's session, status, epoch, roles and permissions from Postgres on every single request, enforces the route's `scope` and `permission` before the handler runs, and rotates an opaque refresh token in a way that makes a replay kill the whole rotation family.

**Architecture:** The platform owns the _shape_ of a caller (`Actor`/`Principal` in `src/platform/http/principal.ts`) and the _enforcement_ (`mountRoutes` checks `route.scope` and `route.permission` for every route at once, so no route can forget). The identity module owns the _resolution_: `createActorResolver` reads the bearer token, verifies it against the Ed25519 key, short-circuits a stale epoch against a Redis cache, then resolves session + user + live role grants in one indexed query. Nothing about the caller is trusted from the token. Refresh rotation is a single `UPDATE … WHERE consumed_at IS NULL RETURNING` — the row lock is what makes two simultaneous refreshes resolve to one winner, and the loser is by definition a replay, which kills the family and publishes `identity.session.reuse_detected` through the outbox.

**Tech Stack:** `jose` 6.2.12 (EdDSA sign/verify, JWK export), node:crypto (Ed25519 key from the 32-byte hex seed in `IDENTITY_SIGNING_KEY`), drizzle-orm 0.45 with raw `sql` for the rotation statements, ioredis for the epoch cache, Vitest 5 with the per-worker template-clone harness.

**Spec:** M1 D5, §5.8, §9.2, §10.1, §11, §14 (S8, S13), §17 "Sessions" in `docs/specs/module-01-identity-and-user-management.md`; design §7.3 and C2 in `docs/superpowers/specs/2026-10-05-komtru-platform-design.md`; m2 §2 (the `LOGISTICS` membership contract T-086 fills in) in `docs/specs/m2-logistics-module-spec.md`; ticket T-031 in `docs/tickets/03-identity.md`.

## Global Constraints

- **No migration.** T-030 created every table this ticket needs; another agent owns the next migration number. If a schema change looks necessary, stop and report it.
- Access token: JWT, `alg: EdDSA` (Ed25519), TTL `IDENTITY_ACCESS_TOKEN_TTL_SECONDS` (600), claims `sub` (userId), `sid` (sessionId), `scp` (session scope), `epc` (`users.sessions_epoch`), plus `iss`, `aud`, `iat`, `exp`.
- Refresh token: opaque, 256 bits from `randomToken(32)`, stored as unkeyed `sha256` (never HMAC — `src/platform/crypto/hmac.ts` states why), rotated on every use.
- TTLs: `CONSUMER` and `LOGISTICS` — 30-day idle, sliding on each refresh, 365-day absolute. `STAFF` — 30-minute idle, 8-hour absolute (M1 C3). The 365 days is **not** in the spec: M1 says "consumer 30 days sliding" and the column is `NOT NULL`, so it is one named constant for the owner to change.
- Status gate: a session may be used and refreshed only while `users.status` is `ACTIVE`, `PENDING_VERIFICATION` or `RESTRICTED` (M1 D5).
- 401 means "your credential is the problem, try refreshing" (`UNAUTHENTICATED`, `TOKEN_EXPIRED`, `SESSION_REVOKED`); 403 means "your credential is fine and the answer is still no" (`FORBIDDEN` for a scope mismatch or a missing permission). A 403 must never make the api-client refresh — `packages/api-client/src/client.ts` refreshes on 401 only.
- Exact dependency versions, no `^`. TypeScript 6 strict, ESM with `.js` extensions on relative imports, plain exported functions, zod 4. Comments are sparse and explain _why_.
- Module layout: `domain/`, `services/`, `http/{controllers,routes,validations}`, `infrastructure/`, with `src/modules/identity/index.ts` as the only way in (`komtru/module-boundaries`).
- Every infra test run: `KOMTRU_INFRA_TESTS=1 KOMTRU_TEST_DB_PREFIX=komtru_t031 KOMTRU_TEST_REDIS_URL=redis://localhost:56379/2`.

## Review Focus

1. **A consumer refresh token must never mint a staff or logistics session.** The rotated row's `user_id`, `scope`, `family_id` and `absolute_expires_at` are copied by Postgres from the parent row inside the `INSERT … SELECT`, never passed as parameters, so there is no code path where a request body can influence them (Task 5).
2. **Two simultaneous refreshes of the same token.** The winner is whichever `UPDATE … WHERE consumed_at IS NULL` commits first; the loser must get 401 _and_ kill the family, not retry into a second valid session (Task 5).
3. **A stale epoch cache must never admit a token the database would reject.** The cached epoch is a fast _deny_ path only: the authoritative `sessions_epoch` comes back in the principal query and is compared again (Task 4).
4. **`parent_session_id` may cross users** — M1 §5.8 defines the column that way and T-030 shipped it with no same-user constraint. A family must hold exactly one user and one scope, and the service is the only thing that can guarantee it (Task 5).
5. **Revocation must be prompt and must cover the family.** Logging out of one device, or a replay, revokes every row sharing the `family_id`, so the access token minted a second before the revocation stops working on its next request — not in ten minutes (Tasks 4, 5, 6).
