# T-074 — Release and settlement

Branch `t-074-release`, cut from `main` at `ccde536`. Depends on T-072, which merged earlier today
and moved the buyer protection fee onto its own per-trade liability account. No migration: the chart
of accounts, the journal and `postJournal` all exist already, and migration `0045` belongs to another
agent.

## What release is

A trade reaches `COMPLETED` (M7 `COMPLETE` or `INSPECTION_ELAPSED`). The ledger answers by
discharging everything it holds for that trade in **one journal**, and publishing
`ledger.payment.escrow_released`. M7 consumes that event and moves `COMPLETED → SETTLED`; the ledger
never transitions a trade (M8 D6).

Every amount comes from the trade's fee snapshot (design §6.5, T-047) — the nine frozen columns and
the `fee_snapshot` JSONB. Nothing is computed here, and `config/fees.yaml` is never read.

### The journal for a normal release

With the T-047 vocabulary — `itemMinor`, `commissionMinor`, `sellerProceedsMinor` (= item −
commission) and `buyerProtectionFeeMinor`:

```
DEBIT  USER_ESCROW_LIABILITY(trade)          itemMinor
CREDIT USER_PAYABLE(seller)                  sellerProceedsMinor
CREDIT PLATFORM_FEE_REVENUE                  commissionMinor            (omitted when zero)
DEBIT  BUYER_PROTECTION_FEE_LIABILITY(trade) buyerProtectionFeeMinor    (omitted when zero)
CREDIT BUYER_PROTECTION_FEE_REVENUE          buyerProtectionFeeMinor    (omitted when zero)
```

Debits `item + fee`, credits `(item − commission) + commission + fee`. Balanced.

**The escrow debit is the item, not the buyer total.** T-072's funding credited
`USER_ESCROW_LIABILITY(trade)` the item alone and `BUYER_PROTECTION_FEE_LIABILITY(trade)` the fee, so
the escrow liability's balance already _is_ the refundable item figure. Debiting the buyer total
against it would overdraw it by the fee and leave the fee liability standing forever — a
reconciliation finding at best, and the balance invariant would not catch it, because the posting
still balances line-for-line. The guard against getting this wrong is not a comment: before posting,
the service reads `accountBalance(USER_ESCROW_LIABILITY(trade))` and refuses unless it equals the
snapshot's `itemMinor` exactly.

With Q14's default (0% commission for both seller kinds) the commission line is absent in practice.
It is built, tested at a non-zero value, and omitted at zero because a ledger line is strictly
positive (`journalLineSchema`'s `min(1n)`).

### Idempotency

`trade:<tradeId>:release` — namespaced by the thing being replayed, per T-070's rule, and matching
`journalIdempotencyKeySchema`. One trade's escrow is settled exactly once, by exactly one journal,
whichever path settles it: the dispute split (below) uses the **same** key deliberately, so a trade
cannot be both released whole and split-settled. A second attempt with different lines raises
`IdempotencyKeyConflictError` out of `postJournal`'s own replay check rather than posting.

The service does not pre-empt that check with its own "already released?" short-circuit. It loads the
trade, builds the lines, and asks `postJournal`; `posted: false` means the identical posting already
exists, and the service returns `ALREADY_SETTLED` and publishes nothing (the first posting already
published). The pre-post guards (hold, status, balance) run only when `findJournalByKey` finds
nothing, because they describe the state before a posting and would all fail on a legitimate replay.

### Holds

An unreleased row in `trade.trade_holds` (`released_at IS NULL`, any of `PARK_EXCEPTION`, `RISK`,
`ADMIN`) blocks release. The service posts nothing, publishes nothing, returns `HELD` with the hold
sources, and logs a warning. It does **not** throw: a hold lasts hours or days, and throwing would
burn the subscriber's eight attempts in twenty minutes and dead-letter the event. The consequence is
a seam, recorded below: nothing re-drives release when the hold is lifted.

## The dispute-split capability (for T-080)

T-080 resolves a dispute with amounts. The capability built here is one journal that releases part
of the escrowed item to the seller and refunds the rest to the buyer:

```
DEBIT  USER_ESCROW_LIABILITY(trade)          itemMinor
CREDIT USER_PAYABLE(seller)                  releaseToSellerMinor
CREDIT PLATFORM_FEE_REVENUE                  commissionMinor            (omitted when zero)
CREDIT PLATFORM_ESCROW_POOL                  refundToBuyerMinor         (omitted when zero)
+ the fee leg, per the treatment below
```

with `releaseToSellerMinor + commissionMinor + refundToBuyerMinor === itemMinor` checked in the pure
domain before anything is posted — the "second check after M3's trigger" the ticket asks for — and
again against the live escrow liability balance in the service.

**The caller supplies the three amounts; the ledger computes none of them.** How a commission is
apportioned over a partial release is a fee rule, and fee rules do not live in this module (T-070).
T-080 hands over already-computed kobo from the snapshot, exactly as funding does, and the ledger's
job is to refuse a set that does not sum to what is escrowed.

**The protection fee on a split** follows design §12 Q4's default — _"refunded on every full refund;
retained on partial dispute outcomes"_ — expressed as `feeTreatmentForSplit()`:

- `refundToBuyerMinor === itemMinor` (nothing released) **and** the snapshot's
  `buyerProtectionRefundableOnFullRefund` is true → `REFUND`:
  `DEBIT BUYER_PROTECTION_FEE_LIABILITY(trade)` / `CREDIT PLATFORM_ESCROW_POOL`.
- otherwise → `RECOGNISE`: the normal revenue leg.

Read from the trade's snapshot, never from the live file: Q4's treatment is the one in force when the
trade was accepted. The treatment is also an explicit parameter, so T-080 can override a derived
default with a human's decision and the override is visible in the journal's description.

Either way the fee liability is **discharged to zero**. A trade that ends with a non-zero fee
liability is a reconciliation finding (T-076), not an arithmetic shortcut somebody forgot.

## Seams left open

- **T-075 (refunds).** Not in scope and not built. Two line builders in `domain/release.ts` are the
  refund-side primitives T-075 reuses rather than re-deriving: `escrowRefundLines(tradeId, amount)`
  (debit escrow liability, credit pool) and `feeRefundLines(tradeId, amount)` (debit fee liability,
  credit pool). The split composes them; a standalone refund composes the same two. T-075 owns the
  `refunds` table, the provider call, the cumulative-refund guard and the `payment.escrow_refunded`
  event — none of which exist here. Where a release and a refund race, the shared
  `trade:<id>:release` key is **not** the guard: T-075 must take the escrow-liability balance check
  as its own, and the two together are what keep item money from being paid twice.
- **T-080 (dispute resolution).** `releaseEscrow` takes a discriminated `settlement` input, and the
  `DISPUTE_SPLIT` arm is reachable today from a direct service call with no caller wired. T-080
  supplies the amounts and decides the trigger (`RESOLVED_RELEASED` / `RESOLVED_REFUNDED`, or its own
  event). `RELEASABLE_STATUSES` already names those two alongside `COMPLETED`.
- **Lifting a hold does not re-drive release.** Nothing exists to lift one (T-062 is Risk, T-080 is
  disputes, admin holds have no endpoint). Whoever clears a hold must call `releaseEscrow` again;
  T-076's "pending release" admin read is the backstop that makes a stuck trade visible. Flagged to
  the owner.
- **`trade.escrow_action_requests` is not written.** Design §6.4 has the _trade_ write the request
  and the ledger answer with an event; no trade-side ticket writes one yet, so `postJournal`'s
  `escrowActionRequestId` stays unset at release. When a trades ticket starts writing them, the
  release service should pass the open `RELEASE` request's id through to the posting — a one-line
  change at a named call site.

## A T-072 bug fixed in passing, which release does not depend on

`balancesRepository.scopeOf` reports the scope on the zero balance of an account nobody has posted
to yet. T-072 added `BUYER_PROTECTION_FEE_LIABILITY` as a second per-trade account without adding it
there, so that zero balance came back naming no trade. **Release is not affected**: both
`accountBalance` calls in `checkReleasable` read only `balanceMinor`, which was always right. It is
fixed here because this ticket is the first code to read that balance and the next reader —
T-075's refund decision, T-076's "fee liabilities still standing" sweep — would be reading the scope
too.

## Open questions for the owner

1. **Who re-drives a release after a hold is lifted?** Nothing does today (see the seam above). The
   default shipped here is "the release is simply not posted, and ops sees it in T-076's pending-
   release list". If the owner wants it automatic, the cleanest home is a `trades.hold.released`
   event the ledger subscribes to — that is a trades-side ticket, not this one.
2. **Commission on a partial dispute release.** No rule exists anywhere in the design for how a
   commission is apportioned when only part of the item is released. This ticket does not invent
   one: T-080's caller passes the commission it wants, and the ledger only checks the sum. Q14's
   default (0%) means nothing turns on it yet, but it must be answered before a non-zero commission
   ships.
3. **A full refund reached through the dispute-split path** (`refundToBuyer === item`) is treated as
   a full refund for Q4's purposes, so the fee goes back to the buyer. If the owner means Q4's
   "full refund" to cover only a pre-dispute cancellation, the split should retain the fee in every
   case and the derived default needs changing.
