# T-041 Avatars — implementation plan

Spec: M1 D7 (`docs/specs/module-01-identity-and-user-management.md`), M1 section 7.4 note on `provider_avatar_url`, M20 PROFILE_PHOTO category. Depends on T-040 (files) and T-030 (identity schema). No migration: `identity.user_profiles.avatar_file_id` already exists.

## Shape

- `POST /me/avatar { fileId }` sets the caller's avatar; `DELETE /me/avatar` clears it. Both answer `{ avatarUrl: string | null }`, where the URL is signed at that moment through M20 (`retrieveFile`), never stored.
- Identity cannot import files (files imports identity), so identity's service takes **ports** the registry (`modules/index.ts`) wires from the files barrel: `findFile`, `signUrl`, `tombstone`. Same pattern as `tombstoneUserFiles` (T-039).
- Set-avatar rules (pure, `domain/avatar.ts`): the file exists and was uploaded by the caller (otherwise the same 404 as a missing file), is category `PROFILE_PHOTO`, `upload_state = READY`, `status = ACTIVE`.
- One transaction: lock the profile row, swap `avatar_file_id`, audit row (`AVATAR_SET` / `AVATAR_REMOVED`, ids only), outbox event `identity.profile.avatar_changed`. The previous avatar file is tombstoned after commit (best effort, logged).
- Read time: `resolveAvatarUrls(ports, ...)` turns `avatar_file_id` into signed URLs; this is the function T-035's `PartyPorts.enrich` supplier (T-061/T-055) calls. No URL is cached or stored.
- Provider avatars (T-034 will call this): `importProviderAvatar` validates the provider URL (https only, no credentials, no private/loopback host), fetches it through an injected `fetchImage` port (size and content-type capped), hands the bytes to an injected `ingest` port (files-side upload, category PROFILE_PHOTO), then runs the same `setAvatar` flow. The raw provider URL is never stored. Failures never fail the login that triggered them: the function returns an outcome union.

## Steps (TDD, commit after each green step)

1. Shared contract: `packages/shared-types/src/avatar.ts` + api-client endpoints `setAvatar` / `removeAvatar`.
2. Domain: `checkAvatarFile`, `checkProviderImageUrl`, `checkProviderImage`.
3. Service `avatar.service.ts` with integration tests (real DB).
4. Routes/controller (`me.controller.ts`), wired into the identity module; registry wires files ports.
5. Final verification: lint, typecheck, test via turbo for backend-api, shared-types, api-client; `pnpm format:check`.

## Owner decisions pending

1. **Replacing or removing an avatar tombstones the old file** (frees Cloudinary quota, honours data minimisation). The spec is silent. Alternative: keep it.
2. **Wrong-owner and wrong-category fileId** answer 404 (not 403/422) so the endpoint is no existence oracle; a not-yet-READY file answers 409, a tombstoned one 410.
3. **Provider image limits**: JPEG/PNG/WebP only, at most 5 MiB, 10 s fetch timeout, https only. M20 has no avatar size figure of its own.
4. **No server-side upload exists in files yet** (uploads are client-direct, and only `files/jobs/` may hold the Cloudinary client). T-041 therefore ships the `ingest` port with tests against a fake; the real implementation (a files job that uploads bytes with a signed request and reconciles) is a follow-up for T-034 or a small files ticket.
5. **Party card avatars**: `resolveAvatarUrls` is provided and tested, but `PartyPorts.enrich` stays unwired (it also needs M7/M5 data that do not exist yet).
6. **Rate limit** 10 per minute per user and IP on both writes; `POST` is non-retryable (a repeat sets the same file), `DELETE` likewise.
