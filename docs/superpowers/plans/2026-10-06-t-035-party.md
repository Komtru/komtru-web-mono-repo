# T-035 — Party lookup and invitations: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let one person find the other party to a trade — by handle, email or phone — without the
lookup becoming a way to learn whether an account exists, and let them tag someone who has no
account yet through an invitation that binds when that person verifies the invited channel.

**Architecture:** One resolving statement for all three channels, run identically whatever the
answer; every subsequent step (the stats port, the velocity event) runs on the miss path too; the
visibility decision — status, `discoverable_by_*` — happens _after_ all of it, so a miss, a hidden
user and a suspended user are one code path with one body. `PartyCard` is assembled by a pure
function from the row that statement returned. Invitations are rows in T-030's
`identity.party_invitations`, keyed by an HMAC of the destination, claimed by the same HMAC when a
channel is verified, and expired by a daily job — all three publishing the events M7 needs.

**Tech Stack:** TypeScript strict, ESM with `.js` specifiers, zod 4, drizzle-orm, express,
`rate-limiter-flexible` over Redis, vitest.

**Spec:** `docs/specs/module-01-identity-and-user-management.md` §8 (all), §5.10, §10.1, §10.4, §11,
§17 "Enumeration", §S4, §S9, §S12; `docs/superpowers/specs/2026-10-05-komtru-platform-design.md`
§6.3; ticket `docs/tickets/03-identity.md` → `### T-035`.

## Review Focus

1. **A lookup that finds a hidden user must cost what a miss costs.** §17 names exactly this pair
   (`/parties/lookup` miss vs `discoverable_by_email = false`). Any `if (!row) return` placed before
   the stats port or the velocity event reintroduces it. Pinned in Task 5 and Task 10.
2. **A released or quarantined handle must not resolve.** T-033 moves a handle to
   `username_history` on change; a lookup that consulted that table would hand the old owner's card
   to whoever typed the retired handle. Pinned in Task 5.
3. **A `%`, `_` or `\` in the typeahead query must be a literal.** `LIKE 'jan%'` built by
   concatenation turns `%` into "every handle on the platform" — the namespace walk §8.4 forbids.
   Pinned in Task 5.
4. **An invitation must not claim onto the wrong person.** The link-forwarding attack §8.5 rule 6
   names: register with a different address, the invitation stays PENDING. Plus two the spec does
   not name — an inviter must not claim their own invitation (self-dealing, design C5), and a
   certified merchant must not claim a BUYER invitation (design §6.3's `CLAIM_BUYER_INVITATION`).
   Pinned in Task 6 and Task 9.
5. **A caller whose contact is unverified must be refused, and a non-existent target must not be.**
   §8.3 control 2 gates on the CALLER. Getting the two confused turns a 403 about the caller into a
   404 about the target, which is the oracle by another name. Pinned in Task 5 and Task 10.

- [ ] **Step 3: Implement `party.service.ts`**

`lookupParty` is one transaction in this exact order, with NO early return before the final line:

1. `deps.budget.charge(key.channel, [actorUserId, ip ?? actorUserId])`.
2. `assertLookupEligible(tx, actorUserId)`.
3. `resolveParty(tx, key)` — **one** statement for all three channels, built like
   `resolveLoginCandidate`: `users` LEFT JOIN `user_emails` on
   `(user_id, email_normal = $email, verified_at IS NOT NULL)`, LEFT JOIN `user_phones` on
   `(user_id, phone_e164 = $phone, verified_at IS NOT NULL)`, LEFT JOIN `user_profiles`, LEFT JOIN
   `user_capabilities` on `capability = 'MERCHANT'`, with
   `WHERE username = $handle OR user_emails.id IS NOT NULL OR user_phones.id IS NOT NULL` where each
   disjunct is `sql\`false\`` when its parameter is null. The badge facts (`emailVerified`,
`phoneVerified`) are `EXISTS` expressions in the same statement. **`username_history` is not
   consulted** — a handle resolves only while its current owner holds it, which is what keeps a
   released handle from resurrecting and a quarantined one from leaking (T-033).
4. `deps.enrich?.(tx, row ? [row.userId] : []) ?? new Map()` — always called.
5. `publish(tx, identityPartyLookupPerformedEvent, …)` with `found: visible`, `subjectHash:
sha256(channel + '\0' + canonical).toString('hex')` — §S12: Risk counts subjects, it never reads one.
6. `return visible ? { found: true, party: partyCard(...) } : { found: false, canInvite: canInviteOn(channel), maskedHint: null }`.

`suggestParties` runs one statement:
`WHERE lower(username::text) LIKE ${escapeLikePrefix(prefix)} || '%' ESCAPE '\'`
`AND status = 'ACTIVE' AND discoverable_by_username AND verification_level <> 'UNVERIFIED'`
`ORDER BY username LIMIT MAX_TYPEAHEAD_RESULTS`, then one `enrich` call for the ids it found.

`createInvitation` normalises the destination through `lookupKeyForEmail` / `lookupKeyForPhone`
(so the hash it writes is the same canonical form `claimInvitationsForDestination` recomputes),
rejects a destination the inviter has themselves verified (`findUserByVerifiedEmail` /
`findUserByVerifiedPhone` returning the inviter — the one existence check that leaks nothing,
because it is about the caller), writes the row, and publishes `.created`.

A comment records WHY the service does NOT check whether the destination belongs to somebody else
and claim immediately: a lookup miss can be a live account with `discoverable_by_email = false`, and
binding that person to a trade on the strength of an address they asked not to be found by would
defeat the flag the lookup honours one endpoint earlier. Such an invitation expires in 14 days and
M7 cancels, which is the honest outcome.

`claimInvitationsForDestination` is one `UPDATE … RETURNING` over
`status = 'PENDING' AND expires_at > now() AND destination_hash = $h AND channel = ANY($channels)
 AND inviter_user_id <> $userId`, filtered before the write by `canActAsBuyer` of the claimer's
MERCHANT capability for `intended_role = 'BUYER'` rows, then one `publish` per returned row.

`expireInvitations` loops `UPDATE … WHERE id IN (SELECT id … WHERE status='PENDING' AND
expires_at <= now() ORDER BY expires_at LIMIT $batch FOR UPDATE SKIP LOCKED) RETURNING …`,
publishing `.expired` per row inside the same transaction, until a batch comes back empty.
Default batch 200.
