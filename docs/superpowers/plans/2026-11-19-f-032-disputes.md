# F-032 — Report an issue and open a dispute: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A buyer or seller can report an issue on a live trade, open a dispute case, mediate it, exchange evidence inside a fixed window and see the outcome — with the event shapes and read models F-033/F-034/F-035 will consume already in place.

**Architecture:** A new `disputes` backend module owning the `disputes` Postgres schema (M3 §4) with a pure `canTransition` state machine extended by C13's `MEDIATION` first state. The module registers each case into the universal case index (`cases`), drives M7 through `trade.disputed` / `dispute.resolved` events and never writes to `trades` or the ledger itself. The frontend adds a `src/trade/dispute` area plus a `@komtru/api-client` `disputes` group, and closes the three named F-032 seams in the trade workspace.

**Tech Stack:** TypeScript, Express + the repo's `defineRoute` registry, Drizzle ORM on Postgres 15, BullMQ/Redis, zod 4, Next 15 App Router, React 19, TanStack Query, `@komtru/ui-kit`, Vitest.

**Spec:** `docs/specs/module-03-disputes.md` (M3). Note: the F-032 brief points at `docs/specs/module-09-*`, which is Orders; M3 is the disputes spec every dispute ticket cites. Conflict C13 and question Q10 come from `docs/superpowers/specs/2026-10-05-komtru-platform-design.md`. Tickets: `### T-080`, `### T-081` in `docs/tickets/09-disputes.md`; `### T-120` in `docs/tickets/13-web-app-ui.md`; `### T-196` in `docs/tickets/18-ui-master-v2.md`.

## Global Constraints

- One schema per module, never `public`. Cross-module references are soft (`uuid`, no `REFERENCES`); same-schema FKs are real, with explicit `onDelete`.
- Concurrency invariants are **partial unique indexes**, never check-then-insert in a service.
- Every list endpoint paginated from the first line; every mutating endpoint declares `retryable` explicitly; every attempt-shaped endpoint is Redis rate limited; every external I/O call goes through BullMQ.
- BullMQ rejects a custom job id containing `:`. Join id parts with `-`.
- Money is `bigint` minor units (kobo). M3 D4: `amount_to_buyer_minor + amount_to_seller_minor = disputes.total_escrow_minor`, enforced by a DB trigger, and the ledger re-checks independently.
- `dispute_decision_log` and `dispute_status_changes` are append-only via `appendOnly()` from `src/db/helpers/appendOnly.ts`.
- Dispute RBAC permissions already exist in `src/modules/identity/domain/rbac/catalog.ts` — do **not** add new ones. `dispute.submit_evidence` and `dispute.appeal` are held by no staff role deliberately; party routes check party membership in the service, not with `permission:`.
- `@komtru/api-client` and `@komtru/shared-types` are consumed from `dist`: after editing either, run `pnpm --filter @komtru/<pkg> build`.
- UI: ui-kit primitives and canonical tokens only, no raw hex. Mobile baseline (340px reference frame), base → sm 640 → md 768 → lg 1024. Loading, empty, error, offline **and permission-denied** on every data-backed screen. `frontend-design` skill invoked per screen. Copy taken verbatim from `docs/design-reference/Komtru — UI Living Master v2.html`.
- Commitlint: lower-case verb subject, header ≤ 100 chars. Commit after every green step.
- **Parallel-run rule for this cycle:** integration tests (`*.int.test.ts`, gated on `infraEnabled`) are written but **not executed** — F-005 owns the infra suite this round. Unit tests run normally.

## Split point

**Phase A (Tasks 1–11) is the backend and must land whole.** It is the thing six other features are blocked on. The feature is not "done" at the end of Phase A and no ticket status is set to Done; the run reports the split.

**Phase B (Tasks 12–20) is the frontend.** It begins only once Phase A is green and committed. If the run ends mid-Phase-B, the report lists exactly which of the 15 screens exist.

## Review Focus

1. **A second dispute opened on a trade that already has one.** Two concurrent `POST /trades/:id/dispute` calls must leave one case. Pinned by the partial unique index `disputes_one_active_per_trade` and a task-9 integration test, not by a service read.
2. **A decision whose amounts do not sum to the escrow.** A reviewer (or a replayed mediation agreement) submitting `buyer + seller ≠ total_escrow_minor` must be refused by the DB trigger even if the service check is bypassed. Task 3 tests the pure check; task 9 tests the trigger.
3. **Evidence submitted the second after the deadline.** Must be accepted but flagged `submitted_after_deadline = true` only when the reviewer has reopened collection; otherwise refused with 409. Clock-boundary equality (`now === deadline`) must be decided explicitly. Task 4.
4. **An appeal filed twice, or filed after the window.** One appeal only, and `appeal_deadline_at` is exclusive. Task 5.
5. **A reviewer who is a party to the case.** Assignment must refuse, and must also refuse the original reviewer on an appeal. Task 6.

The machine is M3 §3 with C13's `MEDIATION` prepended as the opening state:

```
MEDIATION → OPEN_EVIDENCE_COLLECTION → UNDER_REVIEW → DECIDED → CLOSED
   │                                                     │
   └── agreed outcome ──────────────────────────────────→ DECIDED
                                               APPEALED → APPEAL_UNDER_REVIEW → CLOSED
```

Actions: `OPEN` (→ MEDIATION), `AGREE` (MEDIATION → DECIDED), `WITHDRAW` (MEDIATION → CLOSED), `MEDIATION_LAPSED` (MEDIATION → OPEN_EVIDENCE_COLLECTION), `CLOSE_EVIDENCE` (OPEN_EVIDENCE_COLLECTION → UNDER_REVIEW), `REOPEN_EVIDENCE` (UNDER_REVIEW → OPEN_EVIDENCE_COLLECTION), `DECIDE` (UNDER_REVIEW → DECIDED), `APPEAL` (DECIDED → APPEALED), `ASSIGN_APPEAL` (APPEALED → APPEAL_UNDER_REVIEW), `DECIDE_APPEAL` (APPEAL_UNDER_REVIEW → CLOSED), `LAPSE` (DECIDED → CLOSED).

### Task 3: Decision arithmetic and outcome rules

**Files:**

- Create: `apps/backend-api/src/modules/disputes/domain/decision.ts`

**Interfaces:**

Rules, from M3 D4: a `*_FULL` outcome's amounts are determined, so `amountsForOutcome` computes them and a caller-supplied pair that disagrees is a mismatch; a `*_PARTIAL` outcome requires both amounts, both `>= 0`, and both strictly less than the total (a "partial" equal to the total is a full outcome mislabelled, and is refused).

  });
});
it('refuses amounts that do not sum to the escrow', () => {
  expect(() =>
    assertDecisionSums('REFUND_BUYER_PARTIAL', { toBuyerMinor: 1n, toSellerMinor: 1n }, 3n),
  ).toThrow(/do not sum/);
});
it('refuses a partial that is really a full outcome', () => {
  expect(() =>
    assertDecisionSums('RELEASE_SELLER_PARTIAL', { toBuyerMinor: 0n, toSellerMinor: 100n }, 100n),

  expect(() =>
