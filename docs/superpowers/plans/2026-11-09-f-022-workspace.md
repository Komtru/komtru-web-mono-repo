### Gaps filled on this branch

1. **`GET /trades/:id/activity`** (new). Sources `trade.trade_state_changes` (authoritative, written by trigger, one
   row per transition) plus an allowlist of `trade.trade_activity` rows (extension requested/answered/lapsed).
   Free-text `summary` and `metadata` are never passed through: `summary` is written by services and contains
   deadlines, risk wording and internal ids; the feed is built from enum labels only.
2. **Socket token.** The platform authenticates a socket with the same access token as HTTP. The web app keeps its
   access token in the client's token store (the refresh cookie is path-scoped, no layout can read it), so
   `KomtruProviders` now follows the token store to connect, and forwards `auth:token` on every refresh instead of
   reconnecting.
3. **`SocketLike` gains `emit`/`emitWithAck`**, needed to join rooms and to say `auth:token`.

## Activity route design

`GET /trades/:id/activity?limit=&cursor=` — consumer scope, rate limit as `GET /trades` (120/min user and IP).

- **Who:** the same rule as `GET /trades/:id` (`requireParty`: buyer, seller, or the initiator before binding); anyone
  else gets `404 Trade not found`, identical to a missing trade. Staff scope has no route (not a party).
  Held proposals: a counterparty gets the same 404 while the trade is `DRAFT`, `UNDER_PROPOSAL_REVIEW` or
  `REJECTED` (a rejected trade only comes from a review the counterparty never saw), so the feed cannot reveal what
  the list already hides (M7 R1). This closes the leak for this route only; `GET /trades/:id` is T-062's.
- **Row** (`tradeActivityItemSchema`, strict): `id` (`S:<n>` state change, `A:<n>` activity; opaque), `occurredAt`,
  `kind` (closed enum, see below), `actor` (`YOU | OTHER_PARTY | KOMTRU`), `toStatus` (status after, state changes
  only, else null), `reason` (string | null).
- **What is withheld:** actor ids; the actor of a SYSTEM, LEDGER, STAFF or LOGISTICS row is just `KOMTRU`, so a
  party cannot tell staff action from automation or learn a staff identity; `metadata` and `summary`
  never; `reason` only when it was written by a party (`BUYER`/`SELLER`) on `DECLINE` or `CANCEL` (the decline sheet
  promises "they'll see your reason"). A staff or system reason is never exposed. The initiator's `SEND` into
  `UNDER_PROPOSAL_REVIEW` is `PROPOSAL_HELD` to the initiator and absent for anyone else; `REJECT_REVIEW` is
  `PROPOSAL_NOT_SENT` to the initiator only; `CLEAR_REVIEW` reads as `PROPOSAL_SENT`.
- **Order and cursor:** `occurred_at desc, source desc, id desc`. Cursor `{t, id, f}` base64url: `t` the database's
  microsecond text, `id` the row id (`S:n`/`A:n`), `f` the **trade id** the cursor was issued for. Strict keys,
  `t` microsecond ISO, `id` matches `^[SA]:\d{1,18}$`, `f` a uuid equal to the request's; anything else is 422
  `VALIDATION_FAILED "Invalid cursor"` before any query. A cursor from one trade's feed on another trade is 422.
  The route's own tests walk pages containing rows that share one microsecond.
- **No migration.** Both tables are indexed `(trade_id, occurred_at desc)`.

## Client design

**One surface.** `TradeScreen` keeps deciding what a trade looks like from `status` and `yourRole`. The
pre-acceptance states (R1, Customer-2, G3, IF1, waiting, invite, closed) are untouched. Every status from
`PENDING_PAYMENT` onward renders `Workspace`, a sibling component in the same file family, behind the same route
`/trade/[id]`; `/trade/[id]/terms|activity|actions` render `TradeScreen` with a `tab`. Roles are branches inside
the one `Workspace` (copy and the action seam), never two components.

- `PENDING_PAYMENT` (CWT-01): the existing `TermsAgreed` body (TC-06 tests unchanged) inside the workspace chrome,
  where the funding action is a marked seam (F-024).
- `FUNDED` (CWT-02), `SHIPPED`/`UNCONFIRMED_DELIVERY` (CWT-03), `INSPECTION` (CWT-04), `DISPUTED` (CWT-05),
  `COMPLETED` (CWT-06 settlement processing), `SETTLED`/`RESOLVED_*` and refunds (Customer-5 / the outcome).
- Chrome: header (trade code), summary card (`TradeRow` without href: amount, status chip, counterparty, five-step
  progress), tab strip (Overview, Terms, Activity, Actions), then the state body.
- Tabs are routes, matching the reference URLs (`/trade/90428/terms`...). The reference reaches them from buttons;
  a tab strip is added because Activity and Actions need an entry that is not a button in one state.
- Customer-3 (Active Trade) and the CWT overview are one screen in v2 ("replaced the separate buyer and seller
  screens"); its "Next step" line is the state body's `NoteBanner`. Customer-5 is the `SETTLED` body.

**Seams, not dead buttons.** Funding (F-024), shipping (F-026), confirm-and-inspect/extension (F-027), delivery
tracking detail, disputes (F-032), reviews (F-038). Where a person would act, the screen says plainly what
happens next and that the step is not in the app yet; no button is drawn that does nothing. The Actions tab lists
each action with its availability computed from `status` and `yourRole`, and an unavailable-in-app one is a
"Not in the app yet" row, not a button. The only live actions: cancel before funding (`POST /trades/:id/cancel`,
PENDING_PAYMENT only, which the backend allows), and navigation.

**Realtime** (`useTradeLive` in `@komtru/api-client/react`, one implementation for the workspace and the list):

1. On every socket `connect` (first and reconnect): `emitWithAck('room:join', {prefix:'trade', id: code})` for
   every open code, then refetch each one. `{joined:false}` is recorded; the screen still works by refetch.
2. `trade:updated`: `tradeUpdateSchema.safeParse`; an invalid payload is dropped. A push whose `occurredAt` is not
   after the time of the last completed refetch of that trade is dropped. Otherwise: refetch trade + activity +
   the trade's deadline/inspection reads + the lists. Nothing is rendered from the payload.
3. Unmount: `room:leave` is not required (the gateway cleans on disconnect) but the listener is removed.
4. `MyTrades` joins every visible trade's room and refetches the list on push and on reconnect, as well as focus.

Proof by test: a fake socket whose `connect` fires twice must produce two joins per room and two refetches; a stale
push is ignored; a push never changes what is on screen until the refetch resolves; join refusal does not crash.

migration (so no `migration:safety` run).

**Built**
