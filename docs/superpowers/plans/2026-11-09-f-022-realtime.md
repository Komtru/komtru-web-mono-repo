# F-022 backend half — T-068: trade realtime, notifications and deep links

Branch `f-022-workspace`. Backend only; the workspace UI is built on this branch afterwards. F-022 and every
`- **Status:**` line are untouched.

## Findings that shape the design

- Every state change goes through `applyTransition`, which publishes exactly one `trades.trade.state_changed`
  in the same transaction. "Every state change pushes a trade update" is therefore one subscriber on that event.
  A test drives every edge of the machine and asserts a push for each, so a future second path is caught.
- T-064/T-065 add events that are not state changes and that the UI surfaces: delivery extension
  requested/responded, delivery overdue, refund requested, completed (with `via`), inspection extension
  requested/responded. No "inspection reminder" event exists anywhere, and nothing sends one.
- `trades.trade.state_changed` carries only ids, not party user ids, so notification recipients must be
  looked up. `NotificationBinding.recipients` is synchronous and payload-only; it is widened to
  `(payload, tx) => Recipient[] | Promise<Recipient[]>` (existing bindings are unaffected).
- Trades must not import notify (cycle: notify's `binding.ts` imports barrels). So
  `trades/infrastructure/notifications.ts` exports plain "plans" (event, template key, audience resolver) and
  notify's `binding.ts` wraps them with `defineBinding`.
- The trust module is the precedent for reaching the gateway: `createTradesModule` takes `gateway` as an
  option, `createModules` passes `socket.gateway`. Pushes happen from the worker and cross to API instances over
  the Redis adapter. Pushes are returned as the post-commit callback so a client that refetches never reads
  pre-commit data.

## Room authorisation (the dangerous bit)

Room `trade:<tradeCode>` (trade codes match `ROOM_ID_PATTERN`; the deep link uses the code too).
Authorizer, registered in `start()`:

1. Malformed code -> deny (before any query).
2. Trade does not exist -> deny (indistinguishable from "not yours": same `FORBIDDEN` ack).
3. Principal scope `CONSUMER` and `userId` equals `buyer_user_id` or `seller_user_id` -> allow. The initiator
   is always one of the two (DB check constraint), and an unclaimed counterparty is not a party.
4. Principal scope `STAFF` and `permissions.has('trade.view_all')` -> allow. The permission is read from the
   principal the gateway re-resolved from Postgres, never from a client field.
5. Anything else, and any thrown error (the registry already fails closed) -> deny.

Negative tests: a third user, a non-party staff member without `trade.view_all`, a logistics principal, a
party under a STAFF scope, an unknown code, a malformed code. The key test also runs through the real
registry. Proof of fail-closed: remove the check, watch the test fail, restore.

Push payload deliberately carries no `reason`, `actorId`, amounts or addresses: it says "this trade changed,
here is the status, refetch". Per-role disclosure stays in the HTTP read. That also bounds the one gap the
gateway has (below).

completed, inspection_extension requested/responded, inspection reminder.

## Inspection reminder (new, because no event exists)

Criterion 2 lists it and nothing publishes one, so it is built rather than left as a seam: migration `0047`
adds `trade.trade_deadlines.reminder_sent_at` (nullable `timestamptz`, no enum). Sweep `trades.inspection-reminders`
(every 15 min) finds PENDING INSPECTION deadlines for trades still in INSPECTION with no reminder, due within
`min(24h, window/2)`, locks the trade `FOR UPDATE SKIP LOCKED`, re-reads status, holds and the dispute seam,
claims the row with a guarded `UPDATE ... WHERE reminder_sent_at IS NULL RETURNING`, and publishes
`trades.inspection.reminder_due` in the same transaction. One reminder per due date: accepting an inspection
extension clears `reminder_sent_at`, so the buyer is warned before the NEW deadline too (review decision;
without it a buyer already reminded once would get no warning and the window would auto-complete and release
the money). A declined request does not re-arm it.

## Review amendments

### Criterion 2 is partly deferred

T-068's "every trade event the HTML surfaces" is **not fully met**. Park hub arrival and the pickup PIN are
deferred to T-093: no event, template, mapping or binding exists for them, and the PIN in particular is a
credential that does not belong in a generic feed. Also not covered because their producers are unbuilt:
"refund paid" (T-075) and dispute opened/resolved (T-080). Do not read T-068 as complete on this criterion.

### The wire contract (UI contract)

Import from `@komtru/shared-types`: `TRADE_ROOM_PREFIX` (`'trade'`), `TRADE_UPDATED_EVENT` (`'trade:updated'`),
`TRADE_UPDATE_KINDS`, `tradeUpdateKindSchema`, `tradeUpdateSchema` (strict zod), type `TradeUpdate`, plus
`TRADE_STATUSES`, `TRADE_ACTIONS`, `tradeStatusSchema`, `tradeActionSchema`, `canonicalTradeCodeSchema`. The
backend's `TRADE_STATUSES`/`TRADE_ACTIONS` are now re-exported from there, so there is one list. A backend
contract test (`realtime-update.contract.test.ts`) parses what every push produces with `tradeUpdateSchema`.

Rules the client implements:

1. **Join.** After connecting (handshake `auth.token`; send `auth:token` on every refresh), emit `room:join`
   with `{ prefix: 'trade', id: <canonical trade code> }`. The code must be exactly `KMT-<5-8 digits>-NG`.
   Ack is `{ joined: true }` or `{ joined: false, reason: 'FORBIDDEN' | 'INVALID_ROOM' }`. FORBIDDEN is also
   what a nonexistent trade returns; show "not found", not "forbidden".
2. **Rejoin.** Rooms are lost on disconnect. On every `connect` (including reconnects) re-join each open
   trade's room.
3. **Push means refetch.** A `trade:updated` is a signal, never a read model. On receipt, refetch the trade
   over HTTP and render only that. The payload carries no reason, actor, amount or address.
4. **Ordering.** Compare `occurredAt` with the time of your last completed refetch and ignore a push that is
   older. Pushes may arrive twice (redelivered events), out of order, or not at all.
5. **Reconnect contract.** A push is best-effort. If the emit fails, or the worker crashes after the commit
   and before the emit, it is dropped and is NOT retried: redelivery of the event is a no-op because the
   platform's `processed_events` claim is already committed. Therefore, **on every reconnect, after
   re-joining, refetch every open trade** (and the trades list). Without this a screen can show stale state
   indefinitely. This is the UI's job; the server will not replay missed pushes.
6. **Lists.** There is no trade-wide push. A trades list gets `trade:updated` only for rooms it has joined:
   join the visible trades' rooms, or refetch the list on focus and on reconnect.
7. **Kinds.** `STATE_CHANGED` carries `status`, `previousStatus`, `action`. `DELIVERY_OVERDUE` carries `status`
   and `dueAt`. `*_EXTENSION_REQUESTED` carries `dueAt` (the current deadline). `*_EXTENSION_RESPONDED` carries
   `decision` and, if accepted, `dueAt` (the new deadline). `COMPLETED` carries `via`. `INSPECTION_REMINDER`
   carries `dueAt`. `REFUND_REQUESTED` carries nothing extra.

### T-062 constraint (push side)

A proposal held for TrustOps review (`UNDER_PROPOSAL_REVIEW`) must not be visible to the counterparty until
staff clear it (M7 R1). The notification side is covered: `trades.cancelled` applies only from
AWAITING_ACCEPTANCE and PENDING_PAYMENT. The **push** side is not: `trades.push-state-changed` pushes every
edge into `trade:<code>`, and the counterparty can already be a joined party on a trade bound at SEND, so
a `UNDER_PROPOSAL_REVIEW -> CANCELLED/REJECTED` push would tell them a trade exists. T-062 must either
withhold pushes for these edges from the non-initiating party, or make the room authorizer refuse the
counterparty while the status is `UNDER_PROPOSAL_REVIEW`. (The authorizer today only checks party identity.)

### T-027 follow-up (joined rooms are never re-authorised)

`socket/services/revalidate.ts` (around line 128) re-validates each connection's credential but never
re-runs `authorizers.authorize` for the feature rooms the socket has joined, so a staff member who loses
`trade.view_all` stays in the room until they disconnect. T-068's mitigation is that no payload carries
anything sensitive. The fix belongs to T-027: on each sweep, re-run the authorizer for every joined feature
room and leave the ones that now fail.

## Follow-up: the trades list and lookup by code (from F-017's review)

Before this there was no `GET /trades`, so a second device saw nothing and an invited person could not reach
the trade at all (`send` returns no link; `GET /trades/:id` and `POST /trades/:id/claim` need an id only the
creator has). Two routes, both consumer scope, both declared in shared-types
(`tradeListResponseSchema`, `tradeByCodeResponseSchema`, `TRADE_LIST_STATES`, `TRADE_ATTENTION_KINDS`,
`counterpartyDisplaySchema`; the item schemas are strict).

### `GET /trades?state=ALL|OPEN|CLOSED&limit=&cursor=`

- Trades where the caller is buyer or seller (the initiator is always one of the two). A counterparty never
  sees a trade in `DRAFT` or `UNDER_PROPOSAL_REVIEW` (M7 R1); the initiator does. `GET /trades/:id` on a held
  proposal is T-062's to close.
- Order: `updated_at` desc, then `id` desc (newest-relevant: every transition bumps `updated_at`).
- **Attention is server-computed**, as `attention` on each row (`RESPOND_TO_PROPOSAL`, `PAY`, `SHIP`,
  `CONFIRM_DELIVERY`, `INSPECT`, `RESPOND_TO_EXTENSION`, or `null`). Reason: a pending extension request is
  not visible to a row, and the rule should not be copied into three clients. Grouping ("needs your
  attention" above the rest) is the client's job over the loaded pages; the server does not reorder by it,
  because a sort on a value derived from other tables would make the cursor unstable. `state=OPEN|CLOSED`
  filters on terminal status.
- Row: id, tradeCode, status, statusRevision, yourRole, initiatorRole, awaiting, attention, counterparty,
  item `{title, categoryCode, categoryName}`, `currency`, `itemAmountMinor` (current terms), `buyerTotalMinor`
  (once fees are frozen), sentAt, createdAt, updatedAt. `item.title` is the first non-blank string among
  `title`, `name`, `model`, `brand` in the free-form item details, bounded to 80 characters: a heuristic, since
  item details are per-category free-form.
- **Counterparty display (decision):** yes, `{publicId, username, displayName, avatarUrl}` and nothing else, the
  fields party lookup already returns to any signed-in user. Privacy rules applied: no email, phone, legal name,
  address or verification detail; `username` is withheld when the user turned off `discoverable_by_username`;
  an ANONYMISED or CLOSED account is shown as no one (`null`); the avatar URL is signed through the files
  module exactly as party lookup does. The other party is `null` until bound (a pending invitation has none).
- **Cursor:** `{t, id, f}` base64url JSON: `t` is the database's own microsecond text for `updated_at`
  (a JS Date would round to milliseconds and skip or repeat rows sharing one), `id` the trade id, `f` the
  `state` filter it was issued for. It is read strictly: exactly those three keys, `t` microsecond ISO, `id` a
  uuid, `f` a known filter equal to the request's. Anything else, including another list's cursor, an extra
  field or a cursor from another filter, is **422 `VALIDATION_FAILED` "Invalid cursor"**, checked before any
  query; it never falls back to page 1 (T-052's and T-107's finding). Tests walk pages including rows that
  share one microsecond and assert each trade appears exactly once.
- Rate limit: 120/min per user and per IP.

### `GET /trades/by-code/:code`

- `code` is `canonicalTradeCodeSchema` (exactly `KMT-<5-8 digits>-NG`). A malformed code is 422 for everyone,
  which says nothing about any real trade; the client should normalise with the lenient `tradeCodeSchema`
  first.
- Resolves for: a **party of record** (`access: 'PARTY'`, the trade as `GET /trades/:id` shows it) and the
  **named pending invitee** (`access: 'INVITEE'`): the trade is still `PENDING_COUNTERPARTY` and the
  invitation on it is `CLAIMED` **by this user**. Identity claims an invitation when the person verifies the
  address it was sent to; that, not the code, is what proves who they are. The invitee sees a preview with no
  addresses and no fee snapshot, `awaiting: 'YOU'`, and the trade `id` to call `POST /trades/:id/claim` with.
- Everyone else, including a guesser, a bystander on someone else's claimed invitation, the addressee of a
  still-`PENDING` invitation, and anyone once the trade has moved on, gets `404 NOT_FOUND "Trade not found"`,
  **byte-identical** to a code that does not exist, from one query whichever case it is. The tests assert the
  bodies are equal, and each of three mutations (removing the party/invitee check, the claimed-by-this-user
  check, the `CLAIMED` check) fails a test.
- Rate limit: 10/min per user and 30/min per IP (carrier NAT), far below the list's.
- `counterparty` in the response is the OTHER party; for an invitee it is whoever invited them.

### Shareable link (decision)

`TradeView` gains `shareUrl` = `https://app.komtru.com/trades/<code>`. It is only the code in a link, so it
opens nothing by itself: the by-code route answers parties and the named invitee only. **No token scheme was
invented.** Open product question for the owner: should an invitation also carry a one-time token so the first
click can claim without the invitee first signing up with the invited address? Identity already has
`token_hash` on `party_invitations` and `resolveInvitationToken`, but claims are deliberately keyed on the
verified destination, never the token (M1 8.5), so that is a security decision, not a wiring one.

### Open for T-062 / the owner

- `GET /trades/:id` (and by-code for a party) still shows the counterparty a proposal held for review.
- A trades list entry for an invitee who has claimed the invitation but not the trade is not shown (they are
  not a party yet); the by-code route is how they reach it. Listing pending invitations for the signed-in user
  would remove the need to hold the code at all; not built, since the brief asked for parties.

### Category on the trade view

`TradeView` (`GET /trades/:id`, by-code, and every action response) carries `categoryCode`, `categoryName` and
`standardVersion` (the Trade Standard version the trade pinned), all null together when a trade has no
category. Declared as `tradeCategoryFieldsSchema` in shared-types and part of `tradeByCodeResponseSchema.trade`.
A client reads the standard for exactly `(categoryCode, standardVersion)` instead of inferring a category from
the item details.
