# T-033 Usernames, reserved namespace and the RBAC catalogue — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A handle can be claimed, changed, quarantined and tombstoned under every rule in M1 §6, with confusable folding and the reserved namespace as the anti-impersonation guard; and the platform's permission catalogue — M1 §12's 22 identity permissions × 12 roles — exists as one typed table that `defineRoute({ permission })` strings resolve against, is seeded into `identity.roles` / `permissions` / `role_permissions` idempotently, and is pinned by an exhaustive matrix test.

**Architecture:** Pure domain functions under `identity/domain/username/` (skeleton folding, format policy, reserved matching, suggestions) and `identity/domain/rbac/` (the catalogue). One service, `identity/services/username.service.ts`, holds the database-touching rules and relies on the T-030 unique indexes rather than check-then-insert. Reference data reaches the database through a new optional `seed` hook on `KomtruModule`, run by `pnpm db:migrate` after the migrations as the owner — no migration number is consumed and re-running is a no-op. A thin `identity/http/username.controller.ts` declares the four §10.3 routes with `defineRoute`, reading `ctx.actor` until T-031 supplies a principal.

**Tech Stack:** TypeScript 6 strict, ESM with `.js` relative imports, zod 4, drizzle-orm 0.45, node-postgres, Vitest 5 with the per-worker template-clone harness (`test/support/db.ts`).

**Spec:** M1 §5.2, §6, §10.3, §11, §12, §17 in `docs/specs/module-01-identity-and-user-management.md`; ticket T-033 (and T-037, which extends the catalogue) in `docs/tickets/03-identity.md`. ## Global Constraints

- **No migration.** Another agent owns the next migration number. Every table this plan writes to exists already (T-030). Seed rows are applied by an idempotent seeder, never by a migration.
- Only `skeleton.ts` and `reserved.ts` are lifted. `policy.ts`, `suggest.ts`, the service, the controller, the catalogue and **every** test are written fresh. Both lifted files carry a `Cannibalized from …, adapted:` header naming the adaptation, and the commit message says so.
- Format rules (M1 §6.1), authoritative in the application: length 3–30; charset `a-z0-9._`; first character a letter; last character alphanumeric; no two consecutive separators; canonical lowercase. Regex `^[a-z](?:[a-z0-9]|[._](?=[a-z0-9])){1,28}[a-z0-9]$`. Non-ASCII rejected outright at launch (§6.3). The database CHECK (`^[a-z][a-z0-9._]{2,29}$`) is a looser backstop, not the policy.
- `users.username` is `citext` and `users_username_format` casts to `::text`, so a mixed-case handle is rejected by the **CHECK** before the unique index is reached: expect SQLSTATE `23514`, not `23505` (T-030).
- Change policy (M1 §6.4): cooldown 1 change per 30 days; lifetime cap 3 self-service changes; blocked while any non-terminal trade involves the user; old handle quarantined 90 days, reclaimable by the original owner for 30; verification level ≥ `IDENTITY_VERIFIED` **with** completed trades needs support approval.
- Skeleton versioning is per row (`users.skeleton_version`, `username_history.skeleton_version`), never per deploy. A new version is a new entry in `ALGORITHMS`; existing entries are never edited.
- Concurrency-sensitive rules are the database's unique indexes, not service-side check-then-insert (design §4.4).
- RBAC: deny by default, nothing implicit including for `SUPER_ADMIN` (M1 §12.3). Roles requiring dual approval to grant: `SUPER_ADMIN`, `FINANCE_ADMIN`, `COMPLIANCE_OFFICER` — and the seed must set `requires_dual_approval` **at insert time**, because T-030's `roles_dual_approval_backfill` trigger refuses to switch the flag on later while unapproved live grants exist.
- Exact dependency versions, no `^`. No new runtime dependencies are needed.
- Comments are sparse and explain _why_. Plain exported functions, no classes.
- Integration tests are `*.int.test.ts` under `test/modules/identity/`, inside `describe.runIf(infraEnabled)` with `useTestDatabase()`. Unit tests are `*.test.ts` and must not need Docker.
- Every infra test run in this worktree: `KOMTRU_INFRA_TESTS=1 KOMTRU_TEST_DB_PREFIX=komtru_t033 KOMTRU_TEST_REDIS_URL=redis://localhost:56379/3`.

## Review Focus

1. **Reserved matching folds only the candidate, not the reserved word.** The lifted `skeletonVariants()` compares a candidate's _narrow_ fold against a reserved row holding the _canonical_ fold. `narrow('fiutterwave') = 'fiuterwave'` and `canonical('flutterwave') = 'fluterwave'`, so `@fiutterwave` is claimable while `@flutterwave` is reserved — in a sans-serif font they are the same handle. Both sides must be folded (Task 2).
2. **`BLOCKED_SUBSTRING_SEED` entries are not themselves skeletons.** `officialsupport` can never be a substring of a skeleton, because the skeleton of any handle containing it is `oficialsuport` (run collapsing). Three of the four compound entries silently never match. The seeds must be folded before use (Task 2).
3. **A mixed-case handle must surface as a format rejection, not "taken".** The CHECK fires first (`23514`); a service that maps every rejected write to "already taken" tells a user their own free handle is gone (Task 7).
4. **An empty or separator-only input folds to the empty skeleton.** `skeleton('___')` is `''`, and `''` is a valid-looking value for a UNIQUE column: the first such write would claim the empty skeleton and block every later one. Format validation must run before folding ever reaches the database (Tasks 3, 7).
5. **A permission added to the catalogue without a row in the matrix must fail the build, not default to deny.** The matrix is typed `Record<PermissionCode, Record<RoleCode, Grant>>` with no `Partial`, so `tsc` rejects it; the matrix test additionally re-derives the cells from the spec's own §12.3 table and asserts the counts (Task 9).
