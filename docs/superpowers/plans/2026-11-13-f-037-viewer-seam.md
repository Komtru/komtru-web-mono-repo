# F-037 Get paid out — fill the viewer seam

**Feature:** F-037 (closing work). **Branch:** `f-037-viewer-seam`. **Owner decision (2026-11-12):** yes, fill the
viewer seam: `resolveViewer` returns the signed-in viewer, including `hasSold`. F-037 is Done once a signed-in seller
can reach `/account/payouts` from Account. No migration.

## The constraint that shapes the design

`resolveViewer` runs in a Server Component, and a page render holds no credential: the access token lives only in
the browser's memory, and the refresh token cookie (`komtru_rt`) is scoped to `/api/auth`, so a page never sees it.
The one thing every request does carry is `komtru_session`, the HMAC-sealed session hint the auth route handlers
write on every sign-in and every refresh (T-111).

So the viewer's facts ride in that sealed hint: the auth route handler, which holds a fresh access token at exactly
those moments, reads them from the backend and seals them alongside the scope. `resolveViewer` opens the hint and
maps it to a `Viewer`. Sealing means a facts value cannot be made up in the browser; the backend still authorises
every payout route, so a row shown is never a permission granted.

## Pieces

1. **Backend** (`apps/backend-api`, trades module): `GET /me/viewer` (CONSUMER) answers
   `{ hasSold, certifiedMerchant }` for the caller.
   - `hasSold`: the caller is the seller on at least one trade whose money reached them: `COMPLETED`, `SETTLED` or
     `RESOLVED_RELEASED` (the merchant note in `accountItemsFor`: nothing to do in Payouts before the first sale
     completes).
   - `certifiedMerchant`: the caller holds an `ACTIVE` `MERCHANT` capability (the same read `readTradePrincipal`
     makes; `canActAsBuyer` is its negation).
   - `parkAgent` has no backend read yet (T-091 is not built), so it is not answered and stays `'none'`.
2. **Contract:** `viewerFactsSchema` in `@komtru/shared-types`; `getViewerFacts` endpoint in `@komtru/api-client`.
3. **app-kit:** `SessionHint` gains optional boolean `facts`, sealed in the same `v1` token (an older hint without
   them opens as before). `AuthRouteOptions.describeSession(accessToken, signal)` is called in `issue` (cookie mode
   only), bounded by its own timeout; a failure or timeout signs the person in with no facts, never refuses.
4. **web-app-ui:** the auth route passes a `describeSession` that calls `GET /me/viewer` with the new access token.
   `resolveViewer` opens `komtru_session` with `KOMTRU_SESSION_SECRET`; anything missing, unverifiable, expired, not
   `CONSUMER`, or without facts is `ANONYMOUS_VIEWER`. Signature unchanged (`Promise<Viewer>`).

## Defaults chosen (product questions)

- `hasSold` counts released sales only (not a funded or in-flight trade, not a refunded one).
- Facts are as fresh as the last sign-in or token refresh. The client refreshes lazily (the first API call after a
  page load, and whenever the access token lapses), so a seller whose first sale completes sees Payouts after the
  next refresh, not instantly. Signing out clears the hint, so the shell goes back to anonymous at once.
- `certifiedMerchant` is filled too (it locks the shell to Sell, as design §6.3 says). `parkAgent` stays `'none'`.
