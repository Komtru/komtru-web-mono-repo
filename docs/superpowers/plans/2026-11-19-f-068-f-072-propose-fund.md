## 2. Shared components and where they live

All new files go under `apps/web-app-ui/src/trade/create/`, `src/trade/terms/`, `src/trade/funding/` or `src/home/` (my ownership). `src/trade/workspace/**` and `src/account/**` are not touched.

- **`create/ProposeWorkspace.tsx`** (new). One responsive frame for the propose and fund flow:
  - base: today's single column (`ScreenColumn`), stage rail on top, preview folded into the stage that shows it.
  - `md` (768): working column plus a contract-preview card beside it (TX-07 layout).
  - `lg` (1024): assembly rail (200px) | working column | contract preview (DX-10 layout).
  - Accepts `stages`, `current`, `preview`, `children`, `actions`. Uses `ui-kit` `TradeProgress`/`Stepper` where they fit; otherwise the existing `StageHeader` (v2 rail) is reused.
- **`create/ContractPreview.tsx`** (new). The "contract so far" card, built from the existing `Agreement` figures in `create/parts.tsx`, so the numbers stay the platform's.
- **`funding/FundLayout`** — the same frame for TX-10 / DX-15 / DX-16 / DX-17 (methods left, order summary right, sticky pay bar on tablet).
- **`create/SegmentedVersions.tsx`** (new) — the tablet segmented control used by DX-12 (listing vs offer) and DX-13 (three versions). Built on `ui-kit` `TabNav` if its semantics fit; otherwise a `role="tablist"` with focus rings matching the repo (`ui-kit` `focus.ts`), never `ring` utilities.

No edits to `ui-kit` are planned. If one turns out to be needed (a `ProposeWorkspace` primitive would belong there), I will stop and report rather than edit a shared package.

## 3. Build order (each step is a green commit)

Stage A — layout and the create pair (DX-10, TX-07, DX-11)

1. `ProposeWorkspace` + tests (renders rail, working column and preview landmarks; stage `aria-current`; the existing `StageHeader` contract is kept).
2. `BuyerStart` wrapped in `ProposeWorkspace`; stage 1 = DX-10/TX-07, stage 3 = DX-11. Existing `start-trade.test.tsx` must stay green.
3. `ContractPreview` and the fee rows, wired to the existing preview snapshot.

Stage B — the seller pair (DX-10B, TX-07B) and the offer (DX-12, TX-08) 4. `CompleteRequest` (CT-B7..B9 seller side) in `ProposeWorkspace` with the "Trade assembly" rail: DX-10B / TX-07B. 5. `SellerRequest` / offer review: DX-12 / TX-08, with `SegmentedVersions` at tablet.

Stage C — agreement and counter (DX-13, DX-14, TX-09) 6. Counter-proposal comparison (DX-13). Uses `ProposeChange` (TC-05) data; three versions, `VersionTimeline`-style history; tablet segmented. 7. Terms agreed (DX-14 / TX-09) on `AwaitingFundingBody` and `AgreementScreen` data.

Stage D — fund and protect (DX-15, TX-10, DX-16, DX-17) 8. `FundTrade` checkout layout (DX-15 / TX-10): sticky pay bar on tablet, summary rail on desktop. 9. Verifying (DX-16, AB3 state) and funds protected (DX-17, V3 state) under the same frame.

Stage E — tablet arrival and discovery (TX-01, TX-02..TX-06) 10. TX-01 log-in card. Touches `src/entry/components/LoginForm.tsx`, a shared file: kept minimal and additive, called out in the report. 11. TX-02..04 Home tablet layout (`HomeScreen`), TX-05 search results (`SearchTrades`), TX-06 seller profile.

**Stop point.** If room runs out, the cut goes at the end of Stage E: Stages A–D are the propose-and-fund core that both features are about. Stage E is the least coupled to the propose flow and can be taken in a follow-up without rework.

## 4. Per-screen definition of done

For each screen, in this order: frontend-design skill applied to that screen; unit test (behaviour and states: loading, empty, error, offline where data-backed); `pnpm visual-check` against the reference row, with the `.md` deviation list under `docs/ui-review/`; then commit. e2e and axe are added with the screen where the e2e harness covers that route; anything not covered is listed in the report.
