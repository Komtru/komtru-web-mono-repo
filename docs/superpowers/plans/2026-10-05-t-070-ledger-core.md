# T-070 Double-entry ledger core — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A `ledger` schema whose journal entries can only ever be balanced, append-only, posted once per idempotency key, and whose balances are derived from the journal rather than stored beside it.

**Architecture:** Three tables — `ledger_accounts`, `ledger_journal_entries`, `ledger_entries`. Account identity is a `GENERATED ALWAYS … STORED` column (`account_key`) the caller cannot write, with one UNIQUE index over it; a CHECK pins which scope column each account type carries. The balance invariant is two `DEFERRABLE INITIALLY DEFERRED` constraint triggers calling one `ledger.assert_journal_balanced(uuid)` function, so an unbalanced journal fails at COMMIT however the lines were written. The journal entry declares its own `line_count`, which closes the "append a line to a journal that committed last week" hole. Idempotency is a NOT NULL UNIQUE `idempotency_key` on the journal entry, claimed with `ON CONFLICT DO NOTHING`. Balances are never materialised: they are a `SUM` over `ledger_entries`, so they cannot drift (design §5 conflict C5 rejected a balance column as the source of truth).

**Tech Stack:** TypeScript 6 strict, ESM with `.js` specifiers, drizzle-orm 0.45 / drizzle-kit 0.31, zod 4, Postgres 15+, Vitest 5.

**Spec:** `docs/specs/module-08-payment-escrow-ledger.md` §4–5; `docs/specs/m8-payment-provider-adapter-plan.md` §4; `docs/superpowers/specs/2026-10-05-komtru-platform-design.md` §4.2, §4.3, §6.5; ticket `docs/tickets/08-ledger.md` → T-070.

## Global Constraints

- Money is `bigint` kobo end to end. A JavaScript `number` never holds an amount. `packages/shared-types/src/money.ts` (`koboSchema`, `applyBps`) is the only money vocabulary.
- Concurrency-sensitive invariants live in the database, never in a check-then-insert in a service.
- Cross-schema references (users, trades, payouts) are plain `uuid` with no `REFERENCES` (design §4.2).
- Hand-written SQL goes in its own `drizzle-kit generate --custom` migration. Generated migrations are never hand-edited; the schema `.ts` files are the source of truth.
- `grantRuntimeAccess()` applies every grant. No grant is hand-written outside `appendOnly()`'s output.
- Backend module layout: `domain/`, `services/`, `infrastructure/`, with an `index.ts` barrel. Plain exported functions, no classes. Exact dependency versions, no new dependencies.
- SQLSTATEs already taken: `KT001` append-only, `KT002` dual approval. This ticket adds `KT010` (unbalanced journal) and `KT011` (currency mismatch).
- Infra test runs: `KOMTRU_INFRA_TESTS=1 KOMTRU_TEST_DB_PREFIX=komtru_t070 KOMTRU_TEST_REDIS_URL=redis://localhost:56379/6`.

## Chart of accounts (M8 §4 plus the ticket's addition)

| Type                           | Nature (normal balance) | Scope column                  |
| ------------------------------ | ----------------------- | ----------------------------- |
| `PLATFORM_ESCROW_POOL`         | Asset (DEBIT)           | none — singleton per currency |
| `PLATFORM_FEE_REVENUE`         | Revenue (CREDIT)        | none — singleton per currency |
| `BUYER_PROTECTION_FEE_REVENUE` | Revenue (CREDIT)        | none — singleton per currency |
| `USER_ESCROW_LIABILITY`        | Liability (CREDIT)      | `trade_id`                    |
| `USER_PAYABLE`                 | Liability (CREDIT)      | `owner_user_id`               |
| `SETTLEMENT_CLEARING`          | Liability (CREDIT)      | `payout_id`                   |

No Park account exists: the Park handling fee is cash between buyer and agent (design C23), so nothing about it reaches this schema.

**`SETTLEMENT_CLEARING` is credit-normal, not the asset M8 §5's table calls it.** §5's label and §4's worked example disagree, and §4 is the one that balances: it credits clearing when a payout is initiated and debits it when the bank confirms, with `PLATFORM_ESCROW_POOL` credited only at confirmation. Between those two postings the cash is still in our provider balance and still owed to the seller, so clearing is an in-flight obligation, not cash in transit. Classified from the postings, not from the table. T-073 and T-074 post it as a liability.

## Review Focus

Five things the spec implies and no obvious happy-path test exercises; each has a test in the task named.

1. **A buggy caller inserting lines directly, bypassing `postJournal`.** The database must still refuse an unbalanced set, at COMMIT, with `KT010`. — Task 2.
2. **A line appended to a journal entry that committed in an earlier transaction.** The posting's line set must be closed once committed, even for a balanced pair. — Task 2 (`line_count`).
3. **Two concurrent transactions each posting half of one journal entry.** Neither may commit; both must fail closed rather than one seeing the other's uncommitted half. — Task 2.
4. **A retried job calling `postJournal` with the same key concurrently.** Exactly one journal entry exists afterwards, both callers get the same id, and the second posts no lines and publishes no event. — Task 6.
5. **An amount of zero, a negative amount, or a 20-digit amount.** `amount_minor > 0` is a CHECK, and the wire codec rejects anything outside bigint range before `BigInt()` sees it. — Task 1 and Task 4.

Column list, exactly:

`ledger.ledger_accounts` — `id uuid pk default gen_random_uuid()`, `account_type ledger_account_type not null`, `currency text not null default 'NGN'`, `owner_user_id uuid`, `trade_id uuid`, `payout_id uuid`, `account_key text GENERATED ALWAYS AS (currency || ':' || CASE account_type WHEN 'PLATFORM_ESCROW_POOL' THEN 'PLATFORM_ESCROW_POOL' … end || ':' || COALESCE(owner_user_id::text, trade_id::text, payout_id::text, '-')) STORED`, `created_at timestamptz not null default now()`. Unique index on `account_key`. Index on `owner_user_id`. CHECKs: `ledger_accounts_currency` (`currency ~ '^[A-Z]{3}$'`), `ledger_accounts_scope` — the four-branch disjunction pinning exactly which of the three scope columns is non-null for each account type (platform types: all three NULL; `USER_ESCROW_LIABILITY`: `trade_id` only; `USER_PAYABLE`: `owner_user_id` only; `SETTLEMENT_CLEARING`: `payout_id` only).

> `CASE account_type WHEN …` rather than `account_type::text`: the enum-to-text cast is not immutable and Postgres rejects it in a generation expression. Verified against the running Postgres before this plan was written.

`ledger.ledger_journal_entries` — `id uuid pk default gen_random_uuid()`, `idempotency_key text not null unique`, `description text not null`, `currency text not null default 'NGN'`, `line_count smallint not null`, `trade_id uuid`, `escrow_action_request_id uuid`, `provider payment_provider`, `provider_reference text`, `created_by text not null default 'SYSTEM'`, `posted_at timestamptz not null default now()`. Index on `trade_id`. Index on `(posted_at desc nulls first, id desc nulls first)`. CHECKs: `ledger_journal_entries_line_count` (`line_count >= 2`), `ledger_journal_entries_key_shape` (`idempotency_key ~ '^[a-z][a-z0-9_]*:[A-Za-z0-9:._-]+$'`), `ledger_journal_entries_currency` (`~ '^[A-Z]{3}$'`), `ledger_journal_entries_provider_pair` (`(provider IS NULL) = (provider_reference IS NULL)`).

`ledger.ledger_entries` — `id uuid pk default gen_random_uuid()`, `journal_entry_id uuid not null references ledger_journal_entries(id)`, `account_id uuid not null references ledger_accounts(id)`, `direction ledger_entry_direction not null`, `amount_minor bigint not null` (drizzle `mode: 'bigint'`), `created_at timestamptz not null default now()`. CHECK `ledger_entries_amount_positive` (`amount_minor > 0`). Index on `journal_entry_id`. Index on `(account_id, created_at desc nulls first, id desc nulls first)` — the per-account balance sum and the paginated history both walk it.

`DESC` indexes are `NULLS FIRST` throughout: drizzle's bare `.desc()` emits `NULLS LAST`, whose pathkeys `ORDER BY … DESC` cannot walk (the precedent and the measurement are in T-030's ticket entry).

Enum labels: `ledger_account_type` = the six in the table above, in that order. `ledger_entry_direction` = `DEBIT`, `CREDIT`. `payment_provider` = `PAYSTACK`, `FLUTTERWAVE` (M8 §5.1; declared here because this is the first migration in the `ledger` schema — T-071 ships types only, T-072's `payment_attempts` reuses it).

### Task 2: The balance invariant, enforced by the database

**Files:**

- Create: `drizzle/0017_ledger_balance_invariant.sql` (`--custom`)
- Test: `test/modules/ledger/balance-invariant.int.test.ts`

**Interfaces:**

- Produces: `ledger.assert_journal_balanced(p_journal_entry_id uuid) RETURNS void`; constraint triggers `ledger_journal_entry_balanced` on `ledger_journal_entries` and `ledger_entry_balanced` on `ledger_entries`, both `AFTER INSERT … DEFERRABLE INITIALLY DEFERRED FOR EACH ROW`.

`assert_journal_balanced` reads the journal entry's `line_count` and `currency`, then over its lines joined to their accounts computes the line count, the DEBIT sum, the CREDIT sum and the number of lines whose account currency differs. It raises `KT010` when the line count differs from `line_count` or the two sums differ, and `KT011` on a currency mismatch. Messages name the journal entry id and both sums, because this error is read in an incident.

Why both triggers: the one on `ledger_journal_entries` catches a journal committed with no lines or too few; the one on `ledger_entries` catches lines written without a journal of this transaction's making. Why `line_count` rather than "at least two lines": it closes the set. A balanced pair appended to a journal entry that committed last week would otherwise pass — the journal would still balance, but a posting's line set would not be final. With `line_count` NOT NULL on an append-only row, no later transaction can widen it.

## What T-071, T-072, T-074, T-075 and the trades tickets inherit

- `postJournal(tx, input)` is the only way to write to the ledger, and `idempotencyKey` is required. Namespace it by the thing that is being replayed, not by the attempt: `charge:<providerReference>` for a funding post, `trade:<tradeId>:release`, `payout:<payoutId>:initiated`, `refund:<refundId>:decided`. A webhook replay must reuse the key its first delivery used.
- A posting and the event announcing it share one transaction. Call `postJournal(tx, …)` with the caller's `tx` and `publish(tx, …)` for the module's own event in that same `tx`; never open a second transaction for the event.
- Fees are not computed here. Per design §6.5 the amounts come from the trade's fee snapshot and the calculator is `computeTradeFees(itemMinor, sellerKind, schedule)` in `packages/shared-types` (T-047, in flight). The ledger expects the caller to hand it already-computed kobo for the item, the buyer protection fee and the commission, and credits `BUYER_PROTECTION_FEE_REVENUE` and `PLATFORM_FEE_REVENUE` respectively. No fee rate, cap or floor appears anywhere in the `ledger` module.
- `payment_provider` (`PAYSTACK`, `FLUTTERWAVE`) is declared in migration `0016` under the `ledger` schema. T-071 imports the enum from the ledger barrel rather than declaring a second one; T-072's `payment_attempts` reuses it.
- Every provider-touching posting sets `provider` and `providerReference` on the journal entry; the CHECK refuses one without the other.
