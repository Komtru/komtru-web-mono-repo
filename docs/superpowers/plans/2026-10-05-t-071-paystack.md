# T-071 — Provider adapter and Paystack — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the provider-agnostic payment adapter interface, the Paystack implementation behind it, the registry that resolves a `ProviderCode` to an adapter, and the two jobs the adapter needs (bank-list cache, bank-name resolution) — with no ledger tables and no money flow.

**Architecture:** `domain/providerAdapter.ts` carries m8 §3 verbatim. The Paystack implementation is split three ways to satisfy T-028's boundary: `client.ts` holds every network call (and assembles the adapter) and is importable only from `ledger/jobs/`; `signature.ts` and `events.ts` are pure siblings a request handler may call directly. `providerRegistry.ts` is pure — it holds no adapter of its own; `jobs/providers.ts` is the one file that builds the Paystack adapter and hands it to the registry, which is what keeps `client.ts` inside `jobs/`. Every outbound call goes through `providerRequest`.

**Tech Stack:** Node 22, TypeScript 6 strict, ESM with `.js` specifiers, zod 4, BullMQ via the platform queue factory, vitest with `node:http` stub servers on port 0 (no Docker, no database, no live Paystack call).

**Spec:** `docs/specs/m8-payment-provider-adapter-plan.md` (§1 decisions, §3 interface, §5 endpoints, §6 registry, §9 non-goals); `docs/specs/module-08-payment-escrow-ledger.md`; `docs/superpowers/specs/2026-10-05-komtru-platform-design.md` §4.4 and conflict C8; ticket `docs/tickets/08-ledger.md` T-071.

## Global Constraints

- m8 §3's `PaymentProviderAdapter` and its input/result types are reproduced **verbatim**; nothing is added to or removed from that interface.
- No Paystack Subaccounts, Transaction Splits or Dedicated Virtual Accounts anywhere, in any form, including a stub (m8 §1/§9, design C8). A scanner test guards the whole repo's source.
- Network code lives only in `ledger/infrastructure/providers/paystack/client.ts`, imported only from `ledger/jobs/`. Every request goes through `providerRequest` from `src/platform/providers/http.ts`. `komtru/provider-clients` and `test/platform/provider-boundaries.test.ts` both must stay green.
- Webhook signature is HMAC-SHA512 of the **raw request body**, hex, compared to `x-paystack-signature`; fails closed with no secret; length-safe constant-time compare.
- Plain exported functions, no classes. Exact dependency versions, no `^`. Comments explain _why_, sparsely.
- `apps/backend-api/.env` holds live credentials: never printed, never committed, never called against.
- Out of scope, owned by other tickets: ledger tables and `postJournal` (T-070); `payment_attempts`, the funding flow, the `POST /webhooks/paystack` route and `webhookIngest` (T-072); payout accounts/preferences/payouts (T-073); the socket push for a resolved bank name (T-051). This plan stops at the adapter, the registry, the pure webhook readers, the two jobs, and the raw-body mechanism the T-072 route will use.

## Review Focus

Five inputs the spec implies but does not spell out, each pinned by a test in the task that owns the code:

1. **A webhook body that is valid JSON but not a Paystack envelope** (`null`, `[]`, `{"event":1}`) — the cannibalized parser destructures it and throws a `TypeError` out of the request handler. Must be a clean, caught failure. Task 4.
2. **A `charge.success` payload missing `amount` or `reference`** — the cannibalized parser coerces them to `0` and `''`, fabricating a zero-kobo credit with an empty reference. Must be rejected, not coerced. Task 4.
3. **A signature header that is not 128 hex characters** (empty, `"0x"`, a 300-char string, two headers joined by a comma) — must be a plain `false`, never a throw and never a lenient hex decode that compares a truncated buffer. Task 3.
4. **A Paystack bank list longer than one page** — the cannibalized `listBanks` reads page one and silently drops the rest. Must follow `meta.next`. Task 5.
5. **A `verify` body read that stalls after headers, and a non-2xx `{status:false}` envelope on a 200** — both must surface as errors the job can retry or dead-letter, never as a successful empty result. Task 5.
