# T-060 Trade schema, state machine and audit — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The `trade` Postgres schema exists with every table design §6 needs, and the reconciled state machine is one pure `canTransition(action, from)` that the database independently enforces — an invalid jump, a concurrent double transition, a rewritten audit row and a retroactively changed fee snapshot are all impossible at the database level, not merely unlikely in a service.

**Architecture:** Drizzle `pgSchema('trade')` declarations under `src/modules/trades/infrastructure/postgres/schema/`, one file per cluster, generated into migration `0016_trade_schema.sql`. Everything drizzle cannot express goes in its own `--custom` migration so it survives a regeneration: the append-only triggers (`0017`), the transition guard and audit trigger generated from the domain map (`0018`), the immutability trigger (`0019`), and the composite foreign key that pins the accepted terms version to its own trade (`0020`). The domain layer owns `canTransition`; `applyTransition()` in infrastructure is the single chokepoint every flow ticket uses — one conditional `UPDATE … WHERE id = $1 AND status IN (<states this action may leave>)`, never a read-then-write, with the event published through `publish()` in the same transaction.

**Tech Stack:** drizzle-orm 0.45 (`pgSchema`, `pgEnum`, `check`, partial `uniqueIndex`, `bigint({ mode: 'bigint' })`), drizzle-kit 0.31, node-postgres, Postgres 16 behind PgBouncer, zod 4, Vitest 5 with the per-worker template-clone harness (`test/support/db.ts`).

**Spec:** ticket T-060 in `docs/tickets/07-trades.md`; design §6 (and §4.2, §4.3, §6.3, §6.5, C1, C6, C19–C22) in `docs/superpowers/specs/2026-10-05-komtru-platform-design.md`; `docs/specs/module-07-trade-management.md` (M7) for the gates, the audit requirements and the delivery-trust rules.

## Global Constraints

- **Design §6 beats M7 where they disagree.** M7's `SELLER_ACCEPTED`, `READY_TO_SHIP`, `IN_TRANSIT`, `DELIVERED` and `UNDER_REVIEW` are not states. The §6.1 list is exactly 19 labels: `DRAFT`, `PENDING_COUNTERPARTY`, `UNDER_PROPOSAL_REVIEW`, `AWAITING_ACCEPTANCE`, `PENDING_PAYMENT`, `FUNDED`, `SHIPPED`, `UNCONFIRMED_DELIVERY`, `INSPECTION`, `COMPLETED`, `SETTLED`, `DISPUTED`, `RESOLVED_REFUNDED`, `RESOLVED_RELEASED`, `CANCELLED_REFUNDED`, `DECLINED`, `REJECTED`, `CANCELLED`, `EXPIRED`.
- Everything lives in the `trade` schema; nothing in `public`. Same-schema foreign keys are real with an explicit `onDelete`; cross-schema references (`buyer_user_id`, `seller_user_id`, `counterparty_invitation_id`, `order_id`, `category_id`, `shipment_event_id`, `file_id`) are plain `uuid` with no `REFERENCES` (design §4.2).
- Money is `bigint` kobo (`@komtru/shared-types` `money.ts`); no float, no `numeric`, no JS `number` anywhere near an amount.
- Trade codes use `tradeCodeSchema` from `@komtru/shared-types` — issued form `KMT-<7 digits>-NG`. No second format is invented; the ticket's `KMT-88213` is the shorter input form that schema already accepts.
- Concurrency-sensitive invariants are database constraints — partial unique indexes and conditional `UPDATE`s — never check-then-insert (design §4.4).
- Grants are never hand-written: `grantRuntimeAccess()` runs after every migrate and recognises an append-only table by its `komtru_append_only` trigger.
- Custom SQLSTATEs: `KT001` append-only (existing), `KT002` identity dual approval (existing); this module adds `KT010` invalid transition and `KT011` immutable column.
- Event types are three segments (`eventTypeSchema`): this module publishes `trades.trade.state_changed` and `trades.eligibility.blocked`. M7 §7's two-segment names map onto them.
- TypeScript 6 strict, ESM with `.js` import extensions, plain exported functions, zod 4. Comments are sparse and explain _why_.
- Integration tests are `*.int.test.ts` under `test/modules/trades/`, inside `describe.runIf(infraEnabled)` with `useTestDatabase()`. Run them with `KOMTRU_INFRA_TESTS=1 KOMTRU_TEST_DB_PREFIX=komtru_t060 KOMTRU_TEST_REDIS_URL=redis://localhost:56379/5`.
- T-060 adds no HTTP routes and registers no module: `trades/http` and `trades/services` are T-061's.

## Review Focus

1. **Two simultaneous transitions of the same trade must not both commit.** The second must fail even when its transaction read the trade before the first committed — the conditional `UPDATE`'s row lock plus re-evaluation is the thing that stops it, and the trigger is the backstop when a caller forgets the condition (Task 6).
2. **A caller that updates `status` directly, bypassing `applyTransition`, must still be refused an invalid jump and must still leave an audit row.** If the audit trail depends on the service remembering, it is decorative (Tasks 5 and 6).
3. **A fee snapshot must not change once written, and a trade must not reach `PENDING_PAYMENT` without one.** A later `config/fees.yaml` edit changing an open trade's maths is the failure the whole snapshot exists to prevent (Tasks 2 and 7).
4. **An inspection window may only ever grow.** BEI1 lets the buyer extend once; nothing may shorten the window a trade was created under (Task 7).
5. **A merchant certified mid-trade must still finish the buyer-side trade they were already in.** The block applies to acquiring a new buyer role, never to the transitions of a trade already in flight (Task 8).
