## Rules (and where each acceptance criterion lands)

1. **Dispatch guard (X1).** Every shipping endpoint, the options one included, goes through `assertDispatchOpen`: before `FUNDED` it is `409 INVALID_TRANSITION` with extension `reason: 'DISPATCH_LOCKED'`; from `SHIPPED` onward it is the plain `INVALID_TRANSITION`; a trade whose delivery deadline has elapsed (refund requested) is `409 CONFLICT` with `reason: 'DELIVERY_OVERDUE'`, so a seller cannot ship into a refund in flight. The database edge (`BEGIN_CUSTODY: FUNDED -> SHIPPED`) backs it.
2. **Ship step.** `GET /trades/:id/ship-options` (seller only): Park first (always present, `available` + `reason`), then every non-default enabled company, then `SELF_ARRANGED` (always available, lists required fields). `POST /trades/:id/ship/self-arranged` needs waybill number, receipt photo (the seller's own finished image upload), driver phone (normalised to E.164) and plate; writes the shipment, `BEGIN_CUSTODY -> SHIPPED`, activity. Replays by the same seller return the trade as it stands. **Seams left:** company branch (T-087: `POST /trades/:code/ship/company`, sets `fulfilment_substate`) and Park branch (T-093); both reuse `assertDispatchOpen` and the ports.
3. **Delivery signal consumer.** One function, payload per design §7.5 (plus `COURIER_API`, which M7 names). Recorded in `delivery_signals` first (replay-safe on `(trade, source, reference id)`), then weighted: `BUYER_CONFIRMATION`, `PARTNER_PORTAL`, `COURIER_API`, `PARK_CUSTODY` are trusted; `SELLER_SELF_REPORT` is trusted only when the trade already holds a partner, courier or Park-custody signal. From `SHIPPED`: trusted -> `INSPECTION` (stamps the inspection deadline from the snapshotted window), untrusted -> `UNCONFIRMED_DELIVERY` (grace deadline row from the snapshotted grace hours). From `UNCONFIRMED_DELIVERY` only the buyer's confirmation moves it (`CONFIRM_RECEIPT`). Anything else is recorded and changes nothing. Actor identity is checked (the buyer confirms, the seller self-reports). **Seam:** T-087 and T-093 subscribe to their own events in their module and call `applyDeliverySignal`; they are not built, so nothing subscribes yet. Human entry points: `POST /trades/:id/confirm-delivery` (buyer) and `POST /trades/:id/report-delivered` (seller).
4. **Deadlines.** On `trades.trade.state_changed` with `to = FUNDED` the trades module opens one `DELIVERY` deadline: `fundedAt + deliveryDeadlineDays` of the Trade Standards version the trade pinned. DE1: the seller requests one extension, before the deadline, to a later date no more than the original window past it. DE2: the buyer accepts (deadline moves, `extension_count` + 1) or declines (the original date stands). A decline after the date already passed makes the refund path run at once. Overdue (job): see "refund seam".
5. **Idempotent jobs.** `sweepDeliveryDeadlines` takes due `PENDING` rows `FOR UPDATE SKIP LOCKED`, one transaction each, re-reads trade status, active holds and pending extension requests, and closes the deadline with a guarded `UPDATE ... WHERE status = 'PENDING'`; the event is published in the same transaction, so a rerun, a second worker or a crash between steps produces it exactly once.
6. **Server-side options.** Park is available only when both the delivery city and the ships-from city of the accepted terms are serviceable; otherwise `reason = { code: 'PARK_NOT_AVAILABLE_IN_CITY', side: DELIVERY | SHIPS_FROM | BOTH, cities, message }` ("Park isn't available in Jos yet").

## Refund seam (T-066, T-075)

T-075 does not exist, so nothing here calls or stubs a refund service. An overdue `DELIVERY` deadline on a `FUNDED` trade (nothing shipped, no extension pending, no hold) publishes `trades.refund.requested` `{ tradeId, tradeCode, reason: 'DELIVERY_OVERDUE', scope: 'FULL', deadlineId }` and `trades.delivery.overdue`, marks the deadline `ELAPSED` and writes a `DEADLINE_ELAPSED` + `ESCROW_ACTION_REQUESTED` activity pair. It writes **no** `escrow_action_requests` row and **no amount**: the amount is a money rule (is the buyer protection fee refunded on an overdue delivery? the fee snapshot has `buyerProtectionRefundableOnFullRefund`, which is T-075's to apply), so it is derived by the consumer from the trade's fee snapshot. The trade stays `FUNDED`; **T-075 consumes the event, writes the `escrow_action_requests` REFUND row, and on the ledger's answer moves the trade with `applyTransition({ action: 'REFUND_CANCELLATION', to: 'CANCELLED_REFUNDED', set: { cancellationReason: 'DELIVERY_OVERDUE' } })`.** T-066's seller-can't-fulfil and approved-cancellation refunds should publish the same `trades.refund.requested` event with their own reason so T-075 has one intake.

## Open questions for the owner (conservative default applied)

1. **Overdue after dispatch.** DE4 says "nothing shipped". Design §6.2 has no `SHIPPED -> CANCELLED_REFUNDED` edge (T-060 flagged this). Default: an overdue deadline on a `SHIPPED` trade is closed `ELAPSED` with `trades.delivery.overdue` (`refundRequested: false`) and no refund. Needs an owner ruling and, if refunds are wanted, an edge via `DISPUTED` or a new one.
2. **Unanswered extension (default applied, revised after review).** A pending extension request no longer blocks the sweep. The deadline only moves when the buyer actively accepts, so once the original `dueAt` passes with the request unanswered, the request is marked `LAPSED` (history: `EXTENSION_LAPSED` activity, status `LAPSED`, buyer then gets `409 EXTENSION_LAPSED` if they try to accept) and the refund path proceeds as normal. Chosen because the alternative strands the buyer's escrow with no end. A default for the owner to confirm, not a rule found in the docs.
3. **Extension limits.** One extension per deadline, at most one original window long (the `delivery_deadline_days` of the category). Not in the docs; chosen to mirror BEI1's "once".
4. **Delivery deadline start.** From funding, length from the pinned Trade Standards. DE1 reads "Delivery due in 6 hours", which supports a delivery (not a ship-by) clock, but the docs name no start event.
5. **Holds and delivery signals (product rule, going to the owner; T-065 relies on the same answer).** As built: a delivery signal is applied even while a hold is active. A signal is a fact and is recorded and applied even with a hold on the trade; holds stop the clocks that move money (deadline job here, T-065's auto-complete). Confirm that a `PARK_EXCEPTION` hold must not block the buyer confirming receipt.
6. **Trusted partner signal while `UNCONFIRMED_DELIVERY`.** Design §6.2 draws only buyer confirmation or grace elapsing out of that state, so a courier delivered signal arriving then is recorded and does not move the trade.
7. **Grace and inspection deadline rows.** Reaching `UNCONFIRMED_DELIVERY` opens an `UNCONFIRMED_DELIVERY_GRACE` row and `INSPECTION` opens an `INSPECTION` row (and stamps `inspection_deadline_at`); T-065 owns the jobs that fire them and should use `openDeadline`, which is idempotent.
8. **Payment deadline (EXPIRE)** is still unset, as T-061 noted; unrelated to this ticket.
