# T-027 Socket Gateway Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One Socket.IO server attached to the API's HTTP server, authenticated with the same access token as HTTP, fanned out across instances by the Redis adapter, with a generic `emitToUser` / `emitToRoom` / `registerRoomAuthorizer` surface — and a live socket whose authorisation is re-decided on a timer so a session epoch bump disconnects it.

**Architecture:** `src/modules/socket/` is a normal Komtru module whose `index.ts` is the only way in. It builds an _unattached_ `socket.io` `Server` at registry-build time; `server.ts` attaches it to the listening `http.Server` in one line after `listen`. Authentication is not a second system: the handshake calls identity's `resolvePrincipal` through an injected `authenticate(token) => Promise<Actor>` port, so the socket's verdicts are literally the HTTP verdicts. Because a socket has no "next request" to re-check on, the gateway makes one: it keeps the credential the client presented and re-runs `authenticate` on every live credential on a fixed interval, bounding a socket's authorisation staleness to that interval. A `disconnectUser` call (cross-instance via the Redis adapter) is the immediate path for code that knows; the sweep is the guarantee.

**Tech Stack:** `socket.io` 4.8.4, `@socket.io/redis-adapter` 8.3.0, `ioredis` 5.11.1 (already present), `socket.io-client` 4.8.4 (devDependency, tests only), TypeScript strict ESM, zod 4, vitest 5.

**Spec:** `docs/specs/socket-module-backend-setup.md` (the backend socket guide, §§1–12), with `docs/superpowers/specs/2026-10-05-komtru-platform-design.md` §4.3 (in-process emitter is for lossy fan-out), §7.3 (nothing about authorisation is read off the token) and the "Stateless processes" row of the non-functional table (socket fan-out via the Redis adapter, proven by two API instances against one Redis). Ticket: `### T-027` in `docs/tickets/02-backend-platform.md`. Depends on `docs/superpowers/plans/2026-10-05-t-031-sessions.md`.

## Review Focus

1. **A client that presents a second token for a different user.** `auth:token` must never re-point a socket already sitting in `user:<A>`'s personal room at user B; the socket is disconnected instead. Covered in Task 5.
2. **A feature room whose prefix is `user` (or `staff`/`consumer`/`logistics`).** `registerRoomAuthorizer('user', …)` plus `room:join {prefix:'user', id:'<victim-uuid>'}` would put a client in another user's personal room. The guide's §8 has exactly this hole; reserved prefixes are rejected at registration. Covered in Task 2.
3. **A room id containing `:` or arbitrary length.** `room:join {prefix:'trade', id:'x:user:<victim>'}` must not be able to shape a room name. Ids are validated against a character class and a length bound. Covered in Task 2.
4. **An authorizer that throws, or a prefix with no authorizer.** Both must deny; a crash inside a feature module must never become default-allow, and must not take the socket down. Covered in Task 3.
5. **Redis away during the sweep.** `resolvePrincipal`'s epoch read already swallows Redis errors, but the sweep itself must not let one socket's rejected promise kill the timer and silently stop re-validating every other socket in the process. Covered in Task 4.

- [ ] **Step 4: Implement `revalidateConnections` in `revalidate.ts`**

The algorithm the signature does not determine:

1. Group `connections.all()` by `token`. One `authenticate` call per distinct credential — tabs of one browser share a token, and the sweep must not multiply the database by open tabs.
2. `Promise.allSettled` over the groups, so one rejected check never abandons the others (Review Focus 5). A rejected check is logged at `warn` and the group is _kept_: a sweep that cannot reach Postgres must not disconnect the whole fleet. The next sweep retries, and the grace window still bounds how long an unverifiable credential survives.
3. For a resolved `Actor`:
   - `principal !== null` and `principal.userId === connection.userId` → replace `principal`, set `verifiedAt = now()`, count as kept.
   - `principal !== null` and a _different_ user → disconnect (`auth:revoked`, code `TOKEN_INVALID`). A credential swap must never move a socket between identities while it sits in the first one's personal room.
   - `failure === 'TOKEN_EXPIRED'` and `now() - verifiedAt <= maxCredentialAgeMs` → emit `auth:refresh`, keep, count as `refreshRequested`.
   - any other failure, or `TOKEN_EXPIRED` past the window → emit `auth:revoked` with the code, then `disconnect()`.
4. Return the counts.

The file's header comment is the ticket's answer to "a socket has no next request" and must say so: HTTP re-decides authorisation on the caller's next request, a socket has none, so the gateway manufactures one on a timer and keeps the credential to ask with. The staleness bound is therefore the sweep interval, and it depends on nothing but this process being alive — unlike a pub/sub push, which a Redis blip or a forgotten call site silently loses.
