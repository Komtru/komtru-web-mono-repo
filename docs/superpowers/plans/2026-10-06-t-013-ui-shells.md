# T-013 — `ui-kit` layout shells Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the four layout shells every Komtru screen sits inside — mobile web, the consumer desktop/tablet shell, the public page, and the TrustOps console — reproducing the reference HTML's own chrome rules and changing shape at exactly 640 / 768 / 1024.

**Architecture:** Each shell is a composition of small, reference-exact parts (`TopBar`, `LogoBar`, `TabBar`, `SideNav`, `TopNav`) rather than one configurable mega-component, so a screen can reach past the shell when it has to. Nothing has a fixed height or a device frame: the reference draws every screen inside a 340px/560px/1040px gallery frame, and the product does not have one, so the gallery's `height`/`min-height`/`overflow` are the shells' only systematic deviation. Responsive behaviour is expressed as Tailwind `md:`/`lg:` variants, and the test harness grows a width-aware evaluator so parity can be asserted at the width the reference draws each screen at.

**Tech Stack:** React 19 (RSC-safe: no shell is a client component), Tailwind v4 via `@komtru/config`'s preset, Vitest + Testing Library, Storybook 10 (`@storybook/react-vite`), the T-016 visual-check harness.

**Spec:** `docs/tickets/01-shared-packages.md` § T-013, against `docs/design-reference/Komtru — UI Screens Living Master File.html` (screens located via `docs/design-reference/SCREEN_INDEX.md`).

## Review Focus

Five things the ticket implies and no obvious test covers. Each gets a test in the task that owns it.

1. **A shell with no content still lays out.** `MobileShell` with an empty body must keep the tab bar at the bottom rather than floating it mid-screen — that is what `margin-top:auto` on `.scr-tabbar` is for. → Task 3.
2. **Two active nav items, or none.** `SideNav`/`TabBar`/`TopNav` take a list; a caller can mark two `current` or forget to mark any. Silent is wrong: assistive tech reads two "current page"s. → Tasks 3 and 4 (throw on more than one).
3. **The desktop shell below `md`.** The reference says the app swaps to the mobile shell at `md`, and therefore never draws `DesktopShell` at 640. It still has to render something sane there, because a screen with no mobile design will be served it. → Task 4 (top nav from base up to `lg`).
4. **The console shell's collapsed rail must stay operable.** `.ko-dweb-sidebar.collapsed .ko-dweb-item > span:not(:first-child){display:none}` hides every label; a rail of unlabelled glyphs is unusable without an accessible name. → Task 6 (`title` + accessible name survive the collapse).
5. **A breakpoint stated in `rem` is not a breakpoint stated in `px`.** Tailwind's `sm`/`md`/`lg` are `40rem`/`48rem`/`64rem`; the ticket states 640/768/1024. They coincide only at a 16px root. → Task 1 pins the identity and the ticket note records the caveat.

```ts
// The reference states its breakpoints in prose, in two `.breakpoint-note` blocks. Both are parsed
// so a change to either fails here rather than drifting past review.
it('states the same three widths the reference does', () => {
  const notes = [...html.matchAll(/class="breakpoint-note"[\s\S]*?<\/div>\s*<\/div>/g)].map((m) => m[0]);
  expect(notes.length).toBeGreaterThanOrEqual(2);
  for (const note of notes) {
    expect(note).toContain('sm');
    for (const width of Object.values(BREAKPOINTS)) expect(note).toContain(String(width));
  }
});

it('maps each name to the pixel width the preset actually compiles', async () => {
  const css = await compileUtilities(['sm:block', 'md:block', 'lg:block']);
  // Tailwind v4 emits `@media (width >= 40rem)`; the ticket states 640px. They are the same width
  // only at a 16px root font size, which is what `REM` encodes.
  for (const [name, pixels] of Object.entries(BREAKPOINTS)) {
    const condition = new RegExp(`@media\\s*\\(width >= ([\\d.]+)rem\\)\\s*\\{[^}]*\\.${name}\\\\:block`);
    const found = condition.exec(css);
    expect(found, `${name} compiles no media query`).not.toBeNull();
    expect(Number(found![1]) * 16).toBe(pixels);
  }
});
```

- [ ] **Step 1: Write the failing test** `packages/ui-kit/test/shells/responsive-css.test.ts`:

```ts
it('ignores a variant whose media query the width does not satisfy', async () => {
  expect((await declarationsAtWidth(['p-[20px]', 'lg:p-[24px]'], 768)).get('padding-top')).toBe('20px');
});

it('applies it once the width does', async () => {
  expect((await declarationsAtWidth(['p-[20px]', 'lg:p-[24px]'], 1024)).get('padding-top')).toBe('24px');

it('resolves two satisfied variants by emission order, as a browser does', async () => {
```

- [ ] **Step 2: Run `pnpm --filter @komtru/ui-kit test -- shells/responsive-css`** — Expected: FAIL, module not found.

- [ ] **Step 3: Implement `declarationsAtWidth` in `packages/ui-kit/test/responsive-css.ts`**

Walk the compiled stylesheet keeping each rule's stack of enclosing at-rule preludes. A rule counts when every `@media` prelude in its stack is satisfied at `width` and every other at-rule in the stack is `@layer`/`@supports`. Satisfaction supports the two forms Tailwind v4 emits: `(width >= Nrem)` and `(min-width: Npx)`; `1rem = 16px`. Then merge the matching rules whose unescaped selector is `.{className}` in emission order — the same model `compiledDeclarations` uses — resolve `--tw-border-style`/`--tw-outline-style`, and `canonicalise` with the sheet's own theme variables. Throw the same "compiles to no rule" error for a class that matched nothing _at any_ width, so a typo cannot pass by being filtered out.

- [ ] **Step 4: Run the test** — Expected: PASS, 5 tests.

- [ ] **Step 5: Move the parity runner into `packages/ui-kit/test/parity.tsx`**

Cut `ParityRow`, `classAttributes` and the three `describe` blocks that consume them out of `primitives-parity.test.tsx` into `describeParity({ html, rows, deviations, additions, declarations })`, where `declarations` is the width-aware or width-blind evaluator the caller passes. `ParityRow` gains one optional field, `width?: number`, which the runner passes to `declarations`. `primitives-parity.test.tsx` keeps its `ROWS`, `DEVIATIONS` and `ADDITIONS` tables verbatim and ends with one `describeParity(...)` call using `compiledDeclarations`.
