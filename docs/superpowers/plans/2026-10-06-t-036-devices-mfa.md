# T-036 — Devices, MFA and passkeys: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the device registry, the four MFA factors (TOTP, SMS OTP, WebAuthn passkey, recovery codes), step-up authentication for §S7 actions, and the `mfaRequired` login branch T-032 deliberately left unbuilt — without turning that branch into a second account-enumeration signal.

**Architecture:** MFA is a **post-authentication** branch. `LoginResult` keeps exactly one failure variant; `MFA_REQUIRED` is added as a second _success_ variant, and every statement that could reveal whether an account exists or whether it has MFA runs strictly after the single `return { outcome: 'REJECTED' }`. The `mfaToken` is an `otp_challenges` row — the same "short-lived single-use secret with an attempt cap" T-032 made that table mean — so there is no migration. Step-up is a second such row of purpose `SENSITIVE_ACTION`, presented as a `stepUpToken` on the sensitive request, because T-031's `Principal` carries no recency and `amr` is true for a session's whole 30 days. Device rows are written in the transaction that creates the session, never before it.

**Tech Stack:** TypeScript strict, ESM with `.js` specifiers, zod 4, drizzle-orm 0.45, Express 5, `@simplewebauthn/server` 14.0.3 (new dependency, exact version, no `^`). TOTP is hand-written against RFC 6238 so it can be proved with the RFC's own test vectors rather than trusted.

**Spec:** `docs/specs/module-01-identity-and-user-management.md` (§5.8, §7, §9, §10.1, §10.5, §11, §12, §14 S4/S6/S7/S9/S10/S11/S13/S15, §17, D2 C1–C6), `docs/tickets/03-identity.md` § T-036, and the T-031/T-032 status notes in that file.

## Global Constraints

- **No drizzle migration.** T-030 created `devices`, `mfa_factors`, `passkey_credentials`, `otp_challenges`, `account_recovery_requests` and the `mfa_factor_type` / `mfa_factor_status` / `device_status` / `otp_purpose` enums. If a schema change looks necessary, STOP and report.
- **Never run the infra-gated suite.** Write `*.int.test.ts` files; do not set `KOMTRU_INFRA_TESTS=1`, do not run `pnpm infra:up` / `infra:down`. Postgres and Redis are shared with other agents.
- Do not run `pnpm tickets:index`. Do not merge. Do not push. Commit on `t-036-devices-mfa` only.
- Conventional commits; commitlint rejects a sentence-case subject — start the subject with a lower-case verb.
- Exact dependency versions, no `^`.
- Module layout: `domain/`, `services/`, `http/{controllers,routes,validations}`, `infrastructure/`. `src/modules/identity/index.ts` is the only way in.
- Every route is declared with `defineRoute`. A caller's identity comes from `actor.principal` via `requireUserId(actor, detail)`, never from parsing `actor.key`.
- Any `catch` on a constraint violation uses `isUniqueViolation` / `pgErrorIn` from `src/db/errors.ts`. drizzle wraps the driver error with the `pg` error on `cause`; `error.code` at the top level is `undefined`.
- Every route returning a collection must declare `paginated` — `assertRouteInvariants` fails the process otherwise.
- Every mutating route must decide `retryable: true | false`. Anything whose response carries a token is `false` (T-031's reasoning: the idempotency gate stores a completed response as plaintext jsonb for 24 hours).
- §S10: every auth-sensitive action writes `identity_audit_log` **in the same transaction** as the thing it describes. §S12: no email, phone, code, secret or token in `metadata` or in any log line — ids, hashes, counts, reasons and enum values only.
- Sparse comments, explaining _why_.
- Verify with `--force`: turbo's cache is shared across worktrees.

## Review Focus

Five things the spec implies, that no obvious happy-path test exercises, and that would bite a real user. Each has a test pinned to the task that owns the code.

1. **A wrong password against an MFA-enrolled account must cost exactly what a wrong password against a non-MFA account costs, and what a wholly unknown identifier costs.** If the factor lookup creeps above the rejection return, `mfaRequired` becomes an "is this account hardened?" oracle measurable in latency. — Task 6.
2. **A TOTP code replayed inside its own 30-second step must be refused.** RFC 6238 codes are valid for a window; without a last-used-step check, shoulder-surfing one code gives a second login. — Task 2.
3. **Two activations racing for `is_default`** hit the partial unique index `mfa_factors_one_default` and raise 23505 wrapped by drizzle. Read through `cause` or the user sees a 500 where the right answer is "the other one became default". — Task 4.
4. **Removing the last factor from an account that holds a live admin role** must be refused while `IDENTITY_STAFF_REQUIRE_MFA` is on (C4), and removing the last _real_ factor must take the recovery-code row with it — recovery codes alone are not a second factor. — Task 5.
5. **A step-up token belonging to another user, or minted for a different purpose, must not be spendable.** `consumeProofToken` checks neither; a copied token must fail without being burnt. — Task 7.
