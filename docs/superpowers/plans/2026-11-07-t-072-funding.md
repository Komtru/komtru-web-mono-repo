## Migration needed (next free number after T-061, e.g. `0040_ledger_payments`)

Drizzle-generated from two new schema files under `ledger/infrastructure/postgres/schema/` (`payments.ts`, `webhooks.ts`), then a `--custom` companion for grants and triggers. Every table is in the `ledger` schema.

```sql
CREATE TYPE ledger.payment_attempt_status AS ENUM (
  'INITIATED',      -- reference issued, buyer has not reported paying
  'PENDING',        -- buyer's Inline callback or a webhook arrived; verify job queued (AB3)
  'SUCCEEDED',      -- verified and posted
  'FAILED',         -- provider says failed (AB4)
  'ABANDONED',      -- superseded by a newer attempt, or expired with the trade's payment deadline (AB4).
                    -- NOT set from Paystack's 'abandoned': a pay-with-transfer can still land, so that
                    -- leaves the attempt PENDING with last_provider_status = 'abandoned' (AB4)
  'NEEDS_REVIEW'    -- verified success that does not match the attempt (amount, currency, reference,
                    -- or a reversed charge). Nothing posted; ops resolves. (AB4 to the buyer)
);

CREATE TABLE ledger.payment_attempts (
  id                          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  trade_id                    uuid NOT NULL,          -- soft ref to trade.trades(id)
  buyer_user_id               uuid NOT NULL,          -- soft ref to identity.users(id)
  provider                    ledger.payment_provider NOT NULL,
  reference                   text NOT NULL UNIQUE,   -- OUR reference, `fund-<attempt uuid>`
  provider_reference          text,                   -- what the provider calls the charge
  currency                    text NOT NULL DEFAULT 'NGN',
  fee_schedule_version        text NOT NULL,          -- copied from the trade's snapshot
  item_amount_minor           bigint NOT NULL,
  buyer_protection_fee_minor  bigint NOT NULL,
  amount_minor                bigint NOT NULL,        -- what the buyer is charged
  status                      ledger.payment_attempt_status NOT NULL DEFAULT 'INITIATED',
  last_provider_status        text,                   -- raw verify status, e.g. 'ongoing'
  last_verified_at            timestamptz,
  verified_amount_minor       bigint,
  verified_currency           text,
  journal_entry_id            uuid REFERENCES ledger.ledger_journal_entries(id),
  failure_reason              text,
  initiated_at                timestamptz NOT NULL DEFAULT now(),
  pending_at                  timestamptz,
  confirmed_at                timestamptz,
  closed_at                   timestamptz,            -- FAILED / ABANDONED / NEEDS_REVIEW
  updated_at                  timestamptz NOT NULL DEFAULT now(),

  CONSTRAINT payment_attempts_currency CHECK (currency ~ '^[A-Z]{3}$'),
  CONSTRAINT payment_attempts_amounts CHECK (
    item_amount_minor > 0 AND buyer_protection_fee_minor >= 0
    AND amount_minor = item_amount_minor + buyer_protection_fee_minor),
  CONSTRAINT payment_attempts_reference_shape CHECK (reference ~ '^fund-[0-9a-f-]{36}$'),
  CONSTRAINT payment_attempts_succeeded_posted CHECK (
    (status = 'SUCCEEDED') = (journal_entry_id IS NOT NULL AND confirmed_at IS NOT NULL))
);

CREATE INDEX payment_attempts_trade_idx ON ledger.payment_attempts (trade_id, initiated_at DESC);
CREATE UNIQUE INDEX payment_attempts_provider_ref
  ON ledger.payment_attempts (provider, provider_reference) WHERE provider_reference IS NOT NULL;
-- At most one live attempt and at most one success per trade: the second is the double charge.
CREATE UNIQUE INDEX payment_attempts_one_open
  ON ledger.payment_attempts (trade_id) WHERE status IN ('INITIATED', 'PENDING');
CREATE UNIQUE INDEX payment_attempts_one_success
  ON ledger.payment_attempts (trade_id) WHERE status = 'SUCCEEDED';

CREATE TABLE ledger.payment_provider_webhooks (
  id                 bigserial PRIMARY KEY,
  provider           ledger.payment_provider NOT NULL,
  provider_event_id  text NOT NULL,       -- paystackEventId(): `<event>:<data.id>`
  event_type         text NOT NULL,
  payload            jsonb NOT NULL,       -- the parsed body; the signature was checked on the raw bytes
  signature_valid    boolean NOT NULL,     -- always true today: an unsigned delivery is refused, not stored
  received_at        timestamptz NOT NULL DEFAULT now(),
  processed_at       timestamptz,
  processing_error   text,
  duplicate_count    integer NOT NULL DEFAULT 0
);

CREATE UNIQUE INDEX payment_provider_webhooks_dedup
  ON ledger.payment_provider_webhooks (provider, provider_event_id);
CREATE INDEX payment_provider_webhooks_unprocessed_idx
  ON ledger.payment_provider_webhooks (received_at) WHERE processed_at IS NULL;
```

Custom companion: `grantRuntimeAccess()` for both tables; `REVOKE DELETE` from `komtru_app` on both; a `BEFORE UPDATE` trigger on `payment_attempts` that refuses changes to `trade_id`, `buyer_user_id`, `provider`, `reference`, `currency`, `fee_schedule_version` and the three amount columns, and refuses leaving a terminal status (`SUCCEEDED`, `FAILED`, `ABANDONED`; `NEEDS_REVIEW` may move to `SUCCEEDED` only through an ops action, T-076); a `BEFORE UPDATE` trigger on `payment_provider_webhooks` allowing only `processed_at`, `processing_error` and `duplicate_count` to change.

Nothing in the existing ledger tables changes, unless the owner picks a dedicated fee-liability account (decision 1 below), which is a separate and heavier migration.

## Shape

- **Trades read port (ledger-owned, read-only).** `ledger/infrastructure/postgres/tradeFunding.ts` selects `id, trade_code, status, buyer_user_id, currency, fee_schedule_version, item_amount_minor, buyer_protection_fee_minor, buyer_total_minor` from the trades barrel's `trades` table by code. No trades-module file changes. M8 D6 says M8 never touches M7's tables; reading the fee snapshot through the barrel is how §6.4 says the amounts arrive, and nothing is written there.
- **`charge.service.ts` — `initiateFunding(tx, { tradeCode, buyer })`.** Trade must exist and the caller must be its buyer (anyone else gets 404, not 403); status must be `PENDING_PAYMENT` (else 409 `TRADE_NOT_PAYABLE`); a `SUCCEEDED` attempt already present is 409 `TRADE_ALREADY_FUNDED`. An open `INITIATED` attempt with the same snapshot is returned as is (a retried tap does not mint a second reference); an open `PENDING` attempt is returned as is (the buyer may already have paid — AB3). Otherwise insert a new attempt with the amounts from `fundingAmounts()`. Returns the Inline payload: `{ reference, amountMinor, currency, email, publicKey, channels: ['card','ussd','bank_transfer'], attemptId }`. No provider call from the request (design §4.4): Paystack Inline starts client-side with the server-issued reference. Route declares `retryable: true` (idempotency key) and is buyer-session authenticated.
- **`POST /trades/:code/payment/confirm`** (buyer's Inline `onSuccess`) moves `INITIATED → PENDING` and enqueues the verify job. **`GET /trades/:code/payment/status`** returns `paymentDisplayState()` for the latest attempt (AB3/AB4). The "check again" button on AB4 posts confirm again, which re-queues a verify for a `PENDING` attempt.
- **`webhookRoutes.ts` — `POST /v1/webhooks/paystack`.** Raw bytes from `platform/http/raw-body.ts`. Signature fails → 401, nothing stored (M8 §11: signature before the dedup insert). Then `paystackEventId(raw)`; `INSERT … ON CONFLICT (provider, provider_event_id) DO UPDATE SET duplicate_count = duplicate_count + 1` (counts replays; no second job). A body that parses as an envelope but fails event validation (`ApiError(400)` from `parsePaystackEvent`) is stored with `processing_error` and answered 200 (T-071 note). New row → enqueue `ledger.process-payment-webhook` with the row id; respond 200. No provider call, no ledger write in the request.
- **`webhookIngest.service.ts` + `jobs/process-payment-webhook.job.ts`.** Load the row; re-parse; only `charge.succeeded` / `charge.failed` act in T-072 (transfer and refund events are recorded and left for T-073/T-075). Look the attempt up by our `reference`; unknown reference → `processing_error = 'unknown reference'`, no posting. Call `verifyCharge` (jobs may import the client), run `assessVerifiedCharge(attempt, verified)`, then in one transaction under `SELECT … FOR UPDATE` on the attempt:
  - `POST`: `postJournal(tx, { idempotencyKey: 'charge:<reference>', lines: fundingJournalLines(...), tradeId, provider, providerReference })`, mark `SUCCEEDED` with `journal_entry_id`, publish `ledger.payment.escrow_funded` in the same transaction.
  - `FAILED` / `NEEDS_REVIEW`: close the attempt with the reason; nothing posted.
  - `NOT_CONFIRMED` (Paystack `abandoned`): keep the attempt `PENDING`, record `last_provider_status`, stop retrying; a later webhook or the buyer's "check again" re-verifies.
  - `PENDING`: record `last_provider_status`, throw a retryable error so the queue's backoff re-verifies.
  - `NO_OP`: the attempt is already settled; mark the webhook processed and stop.
  - Mark the webhook row processed.
    The same verify path backs the confirm route's job, so a lost webhook still funds.
- **Replay safety, three deep:** the webhook dedup index (no second job); the attempt row lock plus terminal-status trigger (a second job finds `SUCCEEDED` and stops); `postJournal`'s idempotency key `charge:<reference>` (even a raced second post writes nothing and publishes nothing). Tests: the same delivery twice, two deliveries with different event ids for one charge, the confirm job and the webhook job racing.
- **Stock reservation (T-056).** T-056 (listings and stock) is not built. `ledger.payment.escrow_funded` carries `tradeId` and is published in the posting transaction; T-056's reservation consumer subscribes to it and to the trade's `orderId`. No separate stock event is emitted from the ledger — the ledger knows nothing about listings, and an event named for stock coming out of M8 would couple the two. Ticket text says "emitted for merchant"; if the owner wants a dedicated event, it is one more `publish` in the same transaction.
- **Trade transition.** The ledger never transitions a trade (design §6.4). T-061/T-062's consumer of `ledger.payment.escrow_funded` moves `PENDING_PAYMENT → FUNDED` and completes the escrow action request.

## Money rules (decided here, from the specs)

- **Total charged** = the trade's snapshotted `buyer_total_minor`, re-checked as `item_amount_minor + buyer_protection_fee_minor` before use (design §6.4, §6.5; `trades_fee_snapshot_arithmetic`). A trade without a snapshot, or one that does not add up, is refused — never recomputed from the live fee file.
- **Currency:** NGN only (`trades_currency` CHECK). Anything else is refused.
- **Posting at funding:** debit `PLATFORM_ESCROW_POOL` the total; credit `USER_ESCROW_LIABILITY(trade)` the item amount; credit the fee as a liability (decision 1). The fee line is omitted when the fee is zero (a ledger line is strictly positive). Nothing is recognised as revenue at funding: T-074 recognises it at release and Q4 says it is refunded on a full refund, so it is still owed.
- **Verify before posting:** the job posts only when Paystack's verify says `success`, the verified reference equals ours, the verified currency equals the attempt's, and the verified amount equals the attempt's amount exactly.
- **Rounding:** none happens here; every amount is integer kobo from the snapshot.

## Owner decisions pending

1. **Which account holds the buyer protection fee between funding and release.** The ticket says "fee liability"; the chart of accounts (T-070) has no fee-liability type. Default implemented: a second credit line on the trade's own `USER_ESCROW_LIABILITY`, so the fee is a liability scoped to the trade, refundable under Q4 and recognised by T-074 at release. A dedicated `BUYER_PROTECTION_FEE_LIABILITY` per-trade account is cleaner for reporting but needs a new enum value and a rewrite of the generated `account_key` expression (T-070 notes this is a table rewrite before PG 18).
2. **Under-payment and over-payment.** Not specified anywhere. Default: a verified success whose amount differs from the attempt's in either direction is `NEEDS_REVIEW` — nothing posted, ops decides (refund the difference, or refund all). Never a partial credit.
3. **A `reversed` verify status, or a success on an attempt already closed or superseded.** Default: `NEEDS_REVIEW`, nothing posted.
4. **Paystack reference charset.** Paystack accepts only alphanumerics, `-`, `.` and `=`. The adapter's doc comment example `trade_fund_${tradeId}` would be refused. Default: `fund-<attempt uuid>`, one reference per attempt (a trade can need a second attempt after an abandoned one).
5. **Dedicated stock-reservation event** vs T-056 consuming `ledger.payment.escrow_funded` (see Shape). Default: the latter.
