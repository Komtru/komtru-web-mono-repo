# F-024 plan: fund escrow, end to end

Feature: `docs/tickets/FEATURE_MAP.md` F-024 (absorbs T-072, done, and T-117). Screens V1, V2, V3, AB3, AB4
(Living Master v2, lines 4455–4600). Backend contract: `docs/superpowers/plans/2026-11-07-t-072-funding.md`.

## What was missing

T-072 shipped the money: `POST /trades/:code/payment/initiate`, `POST …/confirm`, `GET …/status`, the
webhook, the verify job and the escrow posting. Two things stood between that and a buyer who can pay:

1. **No screen.** `AwaitingFunding` carries `SEAM(F-024)` and the Actions tab lists "Fund trade" as later.
2. **Nothing moves the trade.** T-072's plan says the ledger never transitions a trade and that "a trades
   subscriber to `ledger.payment.escrow_funded` must move `PENDING_PAYMENT → FUNDED`", and names no ticket for
   it. Without it a paid trade stays `PENDING_PAYMENT` for ever: the seller is never told to ship, the delivery
   clock never opens, and the workspace keeps asking the buyer to pay. Under the end-to-end rule (2026-11-09)
   F-024 is not done without it, so it is built here.

## Backend: the FUND transition

Mirrors `settleTrade` (T-065's answer to `ledger.payment.escrow_released`) exactly.

- `trades/domain/ledgerEvents.ts`: the consumer's declaration of `ledger.payment.escrow_funded` v1 (`tradeId`,
  `paymentAttemptId`, `journalEntryId`, `reference`, `currency`, `amountMinor`). Not imported from the ledger:
  the ledger imports trades, so the reverse import is a cycle (the same reason the release event is declared
  there). A contract test parses the ledger's own `paymentEscrowFundedEvent` payload through it.
- `fundTrade(tx, input)` in `trades/services/funding.service.ts`, under `SELECT … FOR UPDATE`:
  - `PENDING_PAYMENT`, and the amount and currency equal the trade's snapshotted buyer total →
    `applyTransition(FUND → FUNDED)`, actor `LEDGER`, reason `ESCROW_FUNDED`, context the attempt, journal and
    reference; `funded_at` is stamped by `applyTransition`.
  - Already funded (`FUNDED_OR_LATER`, derived from the state machine as everything reachable from `FUNDED`,
    and pinned by a test to shared-types' `FUNDED_TRADE_STATUSES`, which the web app reads) → `ALREADY_FUNDED`.
  - Any other status (cancelled or expired after the posting) → `IGNORED`; no such trade → `UNKNOWN_TRADE`;
    amount or currency not the snapshot's → `AMOUNT_MISMATCH` (the trade is not funded). Each is **held for
    review durably**, in the transaction that claims the ledger's event: an outbox event
    `trades.funding.review_required` (reason, trade status, paid and expected amounts, attempt, journal,
    reference) and, when the trade exists, an internal activity row. The subscriber also logs a warning.
    **Never refunded automatically** (T-072 decision 8). Trades publishes its own event rather than the
    ledger's `ledger.payment.review_required`, which means "nothing was posted"; here the posting has happened.
  - A hold does not stop funding: like the settle, it records money that has already moved.
- **Activity rows key on `metadata.event`, not on the type.** Both rows use the existing
  `ESCROW_ACTION_SETTLED` label, with `metadata.event` `ESCROW_FUNDED` or `ESCROW_FUNDING_REVIEW`. A dedicated
  label would need `ALTER TYPE … ADD VALUE`, which every migration since T-072 has avoided (the migrator runs
  every pending migration in one transaction). Readers must key on `metadata.event`; the party activity feed
  already does, through its allowlist, and neither event is on it, so both rows are internal.
- `trades/module.ts`: subscribe `trades.on-escrow-funded` in the event's own transaction. `FUNDED` then flows
  through what already exists: `trade.state_changed` opens the delivery deadline, notifies the seller and is
  pushed to both workspace tabs. An infra test drives the ledger's payload through the module's subscriber.

No migration.

## api-client

`packages/api-client/src/payments.ts`, mirroring `ledger/http/payment.validation.ts` field for field:
`initiatePayment` (`POST /trades/:code/payment/initiate`, retryable, body `{ restart? }`), `confirmPayment`
(`POST …/confirm`, retryable), `getPaymentStatus` (`GET …/status`). Money stays digit-string kobo; the one
number is `inline.amount`, passed to Paystack untouched. React hooks in `react/payments.ts`:
`usePaymentStatus(tradeId, enabled = true)` (under `tradeKeys.one(id)` so a trade invalidation refetches it;
it polls every `PAYMENT_POLL_MS`, 4 s, while the display state is `VERIFYING`, and only then),
`useInitiatePayment`, `useConfirmPayment` (both write the answer into the status cache).

## web-app-ui

Route `/trade/[id]/fund` (static, so it wins over `[tab]`), one client screen `FundTrade` whose step is the
platform's `displayState`, not local state, except V1 → V2 (choosing a method costs nothing on the server):

| displayState               | Screen                                                       |
| -------------------------- | ------------------------------------------------------------ |
| `NONE`, `AWAITING_PAYMENT` | V1 choose a method, or V2 after choosing bank transfer       |
| `VERIFYING`                | AB3, polling the status every 4 s                            |
| `NOT_CONFIRMED`            | AB4: check again (confirm) or start again (`restart: true`)  |
| `CONFIRMED`                | V3 funds protected                                           |
| `UNDER_REVIEW`             | a held-for-review note (no reference screen; see deviations) |

- **Money is read, never computed.** V1's lines are the trade's fee snapshot (`trade.fees`: item, buyer
  protection fee, buyer total); V2, AB3 and V3 use the attempt's own `amountMinor` once there is one. No rate is
  on the wire, so the fee line has no "(1.5%)".
- **Checkout** is a port (`Checkout`): the default loads Paystack Inline v2 once and calls `newTransaction`
  with the server's `inline` object as given, narrowing `channels` to the chosen method (`bank_transfer`, or
  `card` + `ussd`) and never adding one the server did not send. Inline's success callback → `confirm` → AB3.
  Tests inject a fake.
- Not the buyer → the screen says so and links back. A funded trade shows V3 (with a note when another payment
  is under review). A trade no longer awaiting payment whose payment is `CONFIRMED` or `UNDER_REVIEW` shows the
  under-review screen, never "isn't waiting for payment".
- V3 on `CONFIRMED` before the trade has moved re-reads the trade every 3 s, at most ten times, and says the
  seller "will be told" until it is `FUNDED`.
- V2's back control steps to V1 inside the screen; `?via=transfer` opens V2 directly.
- `AwaitingFunding` gets a "Fund this trade" link for the buyer (the SEAM), and the Actions tab's `fund` row
  becomes live with that href. The seller's view is unchanged.

## Known deviations (pre-approved or documented defaults)

- No "Logistics fee" line (C7, Q5). V2 is Paystack pay-with-transfer (C8, Q6): Paystack's checkout shows the
  one-time account, so our card shows the exact amount and opens it instead of printing an account number.
- No Komtru Wallet option (Q3 default: wallet off, AB7 is F-025).
- "Get help" / "Contact support" are not drawn as buttons: support is F-047. AB4 shows the trade code to quote.
- No "NDIC-insured partner bank" claim: nothing in the specs states it.

## Owner questions

1. Money escrowed for a trade that was cancelled or expired after the posting, or that does not match the
   snapshot, is held for review (`trades.funding.review_required` plus an internal activity row) and never
   refunded automatically (T-072 decision 8). Should it instead open a case for ops automatically, and who
   consumes the event (T-076 reconciliation is the likely owner)?
2. `UNDER_REVIEW` has no screen in the reference. Built as a plain "We're checking this payment — you don't need
   to pay again" screen; redraw if wanted.
3. The trade view carries the buyer protection fee amount but not its rate, so V1 cannot print "(1.5%)" without
   computing it. Should the trade view return the rate?
