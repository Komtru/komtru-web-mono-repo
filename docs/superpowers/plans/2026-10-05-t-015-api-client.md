# T-015 `api-client` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `@komtru/api-client` gives the five Next.js apps one typed way to call the platform: zod-contract endpoints, RFC 9457 problems as typed errors, an in-memory access token with a single-flight refresh, an `Idempotency-Key` that is stable across every retry of one user action, a durable IndexedDB replay queue, and TanStack Query plus Socket.IO bindings.

**Architecture:** Three entry points. `.` is isomorphic and safe in a React Server Component: contracts, transport, auth, idempotency, retry policy and the storage-agnostic replay queue. `./browser` holds the IndexedDB queue store. `./react` holds the `"use client"` TanStack Query helpers and the Socket.IO provider. Every piece of logic that matters lives in a framework-free function with its clock, randomness, `fetch` and storage injected; the React layer is a thin binding over it.

**Tech Stack:** zod 4.6, `uuid` 14 (v7), TanStack Query 5, socket.io-client 4.8, React 19 (peer), Vitest 5, `node:http` stub server, `fake-indexeddb`, jsdom + Testing Library.

**Spec:** `docs/tickets/01-shared-packages.md` (T-015); `docs/specs/socket-notifications-frontend-setup.md`; design `docs/superpowers/specs/2026-10-05-komtru-platform-design.md` §4.4, §7.3. Backend contracts this client must match: `packages/shared-types/src/{errors,pagination}.ts`, `apps/backend-api/src/platform/http/{idempotency,route,mount,rateLimit,paginate}.ts`.

## Global Constraints

- TypeScript 6 strict, ESM, `.js` extensions on every relative import (NodeNext).
- Exact dependency versions, no `^`, matching the rest of the repo.
- zod 4 only. Every contract is a zod schema with its inferred type beside it.
- An `Idempotency-Key` must satisfy the server's own rule, `/^[\x21-\x7e]{8,255}$/` (`apps/backend-api/src/platform/http/idempotency.ts`). A UUID v7 is 36 chars and qualifies.
- A retry of a mutating call sends **the same key and the same body**; a different body under the same key is the server's 422 `IDEMPOTENCY_KEY_REUSED`, which is a client bug and is never retried.
- `409 CONFLICT` on a request that carries an idempotency key means "a duplicate is still in flight, retry shortly" — it is a retry, not a failure.
- `nextCursor` is `string | null`, never omitted; `null` means the last page.
- Clients branch on `problem.code`, never on `title` or `detail`. A `code` this client version does not know must still parse (`receivedProblemSchema`) and fall back to generic handling.
- Nothing in the `.` entry may import `socket.io-client`, `react`, `@tanstack/react-query` or touch `indexedDB`, `window` or `document` at module scope.
- No `console`; the package takes an injected `onEvent`/logger callback instead.
- Comments are sparse and say _why_.

## Review Focus

1. A second 401 arriving on a request that was already in flight when another request refreshed the token must retry with the **new** token and must not trigger a second refresh (Task 4: generation counter test).
2. A refresh that itself answers 401 (the refresh cookie expired) must end the session once, surface `UNAUTHENTICATED` to every waiting caller, and never loop (Task 4).
3. A response body that is not problem details on a 5xx — an HTML error page from a proxy — must surface as a typed error with `synthetic: true`, not a JSON parse crash (Task 2).
4. A `Retry-After` given as an HTTP-date rather than seconds must still produce a delay (Task 5).
5. A queue entry whose replay fails permanently (a 422 or a 403) must be dropped and reported, not block the queue forever, while a retryable failure must block it so a park agent's receive/release pair can never invert (Task 7).

```ts
export interface TokenStoreOptions {
  refresh: () => Promise<AuthSession | null>; // null = the session is over
  onSessionEnded?: () => void;
}
export interface TokenSnapshot {
  accessToken: string | null;
  generation: number;
}
export interface TokenStore {
  read: () => TokenSnapshot;
  set: (session: AuthSession | null) => void;
  /** Single-flight. `seen` is the generation the caller read before its request. */
  refreshOnce: (seen: number) => Promise<TokenSnapshot>;
  subscribe: (listener: (session: AuthSession | null) => void) => () => void;
}
export const createTokenStore: (options: TokenStoreOptions) => TokenStore;
export const createRouteHandlerRefresh: (options: {
  fetch?: typeof globalThis.fetch;
  base?: string;
}) => () => Promise<AuthSession | null>;
```

The generation counter is the whole design. Every read of the token returns the generation it belongs to. `refreshOnce(seen)` returns immediately with the current snapshot when `seen < generation` — someone else already replaced the token this request was using, so there is nothing to refresh and the caller just retries. Otherwise it joins or starts the one in-flight refresh. A refresh that resolves `null` sets the session to `null`, bumps the generation, calls `onSessionEnded` once and returns `{ accessToken: null }`. A refresh that rejects clears the in-flight promise so the next 401 may try again, and rethrows to every joined caller.

`createRouteHandlerRefresh` POSTs to `authRoutePaths().refresh` with `credentials: 'include'`, parses `authSessionSchema`, and maps 401 to `null`.

### Task 5: Retry policy

**Files:**

- Create: `packages/api-client/src/retry.ts`
- Test: `packages/api-client/test/retry.test.ts`

**Interfaces — consumes:** Task 1's errors.

**Interfaces — produces:**

```ts
export interface RetryPolicy {
  maxAttempts: number; // default 3, i.e. two retries
  baseDelayMs: number; // default 300
  maxDelayMs: number; // default 10_000
  random?: () => number; // injected for deterministic tests
}
export const DEFAULT_RETRY_POLICY: RetryPolicy;
/** `idempotent` is true for GET/HEAD, or for a mutating call that carries an Idempotency-Key. */
export const isRetryable: (error: unknown, idempotent: boolean) => boolean;
export const retryDelayMs: (attempt: number, error: unknown, policy: RetryPolicy) => number;
export const sleep: (ms: number, signal?: AbortSignal) => Promise<void>;
```

`isRetryable` is true for `NetworkError`/`TimeoutError`, and for a `ProblemError` with status 408, 429 or >= 500. It is additionally true for 409 **only when `idempotent`** — that is the backend's "a duplicate is still in flight, retry in a moment". It is false for every other 4xx, and explicitly false for 422 `IDEMPOTENCY_KEY_REUSED` whatever else is true. When `idempotent` is false nothing is retried: a `POST` with no key may have landed.

`retryDelayMs` returns the server's `retryAfterMs` when the error carries one (that is `Retry-After` on a 429 or 503), otherwise exponential with full jitter: `random() * min(maxDelayMs, baseDelayMs * 2 ** attempt)`.

The key lifecycle, which is what this task exists to get right:

- A key is minted **once per `call()`**, before the first attempt, and only when `endpoint.retryable` is true. Every attempt inside that `call()` — the auth retry, a 429 backoff, a 409 "still in flight" — sends that same key and the same serialised body. `options.idempotencyKey` overrides the minted one, which is how a "try again" button and the durable queue continue the _same_ user action across calls and reloads.
- `callWithMeta` returns the key it used, so a caller can persist it.
- A 401 triggers at most **one** refresh-and-retry per `call()`, using the generation the attempt read: `tokens.refreshOnce(seen)`. A null access token afterwards means the session is over, and the original `ProblemError` is thrown. A second 401 after the retry is thrown, never retried again.
- `Authorization: Bearer <token>` is set only when a token exists; a `PUBLIC` endpoint is called without one.
- The retry budget and the auth retry are independent: a refresh does not consume a policy attempt.

The ordering rules, which the test pins:

- Replay is strictly FIFO by `seq`, one entry at a time, never concurrent. A park agent's "parcel received" must reach the server before "parcel released".
- A **retryable** failure stops the flush at the head: the entry stays, its `attempts` rises, and nothing behind it is sent. Head-of-line blocking is the point, not a flaw.
- A **permanent** failure (anything `isRetryable` says no to — a 403, a 422, a validation failure) or exhausting `maxAttempts` **drops the head**, emits `dropped`, and the flush continues with the next entry. One dead entry must not strand the queue forever.
- `enqueue` mints the key once and stores it; every replay sends that stored key through `client.call(..., { idempotencyKey })`, so the server replays the first result rather than acting twice.
- `enqueue` rejects an endpoint that is not `retryable`: queueing a call with no key would be a second trade.
- `flush` is single-flight; a second concurrent call joins the first.
- The IndexedDB store assigns `seq` from an `autoIncrement` key, so order survives a reload. `browser.ts` imports nothing React or Node specific and `isIndexedDbAvailable()` guards every entry point.

## Deliberately left to other tickets

- **Real endpoints.** No endpoint definitions ship here, because no route exists yet. Each module ticket defines its endpoints with `defineEndpoint`, mirroring its backend `defineRoute` one-for-one. The intended end state is one shared contracts module per domain that both sides import; this ticket builds the client half of that seam.
- **T-017 (app foundation)** owns the `/api/auth/*` route handlers. This package supplies `authRoutePaths()`, `createRouteHandlerRefresh()` and `backendLoginPath(scope)`; the handler that reads the httpOnly refresh cookie and calls the backend's scoped login route is T-017's.
- **T-027 (socket gateway)** owns the server. The provider is built against `docs/specs/socket-notifications-frontend-setup.md` and tested with an injected `SocketLike`, never a running gateway. Minting the 5-minute socket token stays in the app (guide §6).
- **T-031/T-034 (auth)** own the login and refresh endpoints and the session payload beyond `{ accessToken, scope, expiresAt }`.
- **Numbered pagination** (`Paged<T>`) has no helper here; cursor pagination is the default and the admin tables that need page numbers arrive with the operations-app tickets.
- **Automatic flush triggers.** The queue exposes `flush()`; wiring it to `online`/`visibilitychange` is `park-agent-app`'s (T-16x), which owns the UI that shows queued, sent and confirmed.
