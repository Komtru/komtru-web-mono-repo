# F-029 Capture and compare proof media (T-197) implementation plan

**Ticket:** T-197 (`docs/tickets/18-ui-master-v2.md`), feature F-029. **Screens (v2):** PM-1, PM-2, PM-3, PM-4 (seller
captures), PM-5 (buyer reviews at request stage), PM-6 (evidence trail), PM-7 (inspection compare), PM-8 (Trade record).
**Branch:** `f-029-proof-media`. **Backend:** T-040/F-008 (files), T-064, T-065/F-027, merged. Frontend only: no
migration, no `apps/backend-api` change, no api-client change.

**Goal:** one self-contained capture-and-compare component set that fulfilment, inspection and disputes mount: the
seller shows the item (guided camera, checks, ready), the buyer reviews and compares it, and everyone can see the
evidence trail and the record kept after completion.

## How it sits on the platform

- Proof media are files uploaded straight to storage (`uploadFile`, `PRIVATE_CASE`) and attached by id on
  `POST /trades`, `/send`, `/accept` or `/counter` (`proofFileIds`). There is no endpoint that attaches proof to an
  existing trade on its own, so PM-1 to PM-4 are the body of the existing proof step (`ProofUpload`), not a route.
  `ProofUpload` keeps its props and becomes a thin wrapper, so `StartTrade`, `SellerStart`, `CompleteRequest` and
  `TradeScreen` need no change.
- Reads: `GET /trades/:id/inspection` returns the seller's proof (file ids and attach times), the dispatch waybill
  receipt and the delivery signals once the trade has shipped; `GET /files/:id` signs each file. That is the whole
  evidence the platform can state, so PM-6 and PM-8 draw exactly that and nothing else.
- Not backed by the platform, so not drawn as fact: an originality ("stock image") check, a human review request, hub
  scan photos, the buyer's inspection photos, the 12-month retention claim, and the buyer seeing the seller's media
  before accepting (the trade view carries only `proofMediaCount`). See the owner questions.

## Owner questions (defaults taken)

- **O1** The buyer already holds access grants on the seller's proof before accepting (granted after send and counter), but no read lists the file ids: `TradeView` has only `proofMediaCount` and the inspection read is empty until shipment. PM-5 is built and says so; it draws the files the moment a read lists them. Exposing the ids is an owner decision.
- **O2** No originality check or review request exists. PM-3 is driven by client checks (type, size, resolution,
  duplicate); "ask for a review" is told plainly as not in the app yet, with no button.
- **O3** The buyer's own inspection photos have nowhere to go. PM-7's "My photos" is a compare aid held on the device and
  says so; it is not uploaded.
- **O4** "Kept for 12 months" is not a platform rule anywhere; the Trade record states only what is true.

## As built

- `CameraSheet` portals its `Sheet` to the body: the tab bar shares the sheet's z-20 and, being later in the page, covered the sheet's actions. `ui-kit` is untouched (its parity test pins z-20 to the reference).
- `"Record the video next"` uses the device's own recorder (a `capture` file input); there is no in-page recorder.
- No Playwright e2e (no harness in the repo, as T-192 and T-193); the happy path is held by jsdom component tests against a mocked api-client.
